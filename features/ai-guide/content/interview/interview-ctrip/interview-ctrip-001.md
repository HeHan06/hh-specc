## 面试概览

- 公司：携程
- 岗位：机票Agent
- 轮次：一面
- 时间：未知
- 流程：个人介绍 → Agent 提问（14 问，纯 Agent 深挖面 + 记忆/检索专项，无八股/算法）→ 反问

> 这场与「企业效能 Agent」面试的最大差异：携程偏「记忆、检索(RAG)、长上下文、编排调用链」——因为机票是强多轮、强上下文的 C 端交易场景，用户会「先查航班、再比价、又问行李、回来改签」跨多轮，记忆和检索是刚需。这解释了为什么本次把「记忆」连挖四问（实现/更新/动态压缩/稳定性）。

## 面试问题与回答

### Q1：RAG 做过吗？你在其中负责哪些部分？

- 严格讲没叫 RAG 这个名字，但做的是 RAG 核心——检索增强，负责检索这一侧。
- 某业务线 200 多个行业、30w 日均对话，Agent 不能靠模型脑补「今晚某行业有没有这家、这个服务人员能不能约」，必须查真实供给，所以检索是独立的：意图 → 结构化查询 → 检索层（供给搜索/服务人员排班/商品召回）→ 模型推理。
- 负责两块：① 索引与检索（服务人员排班 5min 粒度时间片模型，一天 288 时间片用 64 进制压缩编码进 ES 索引，货架/详情/服务人员页 TP99 100ms 内；商品召回不同行业各自有召回规则）；② 检索与推理解耦（检索结果不全线堆进上下文，按相关度排序、过滤无关行业）。
- 一句话：RAG 关注的是检索质量（召回准确）+ 检索结果怎么进上下文，而不是只有个向量库就完事。

### Q2：你在其中负责哪些部分？

- 某公司某业务线 C 端 Agent 从 0 到 1，负责三块。
- ① Multi-Agent 架构与上下文治理：协调者 + 子智能体（供给搜索/预约预订/交易履约），上下文全量堆砌 → 隔离精简 → 动态增补，单次 Token 70k→1.5k。
- ② 某项目预订推品链路：搭预订商品查询框架，支持不同行业商品召回与展示；推品工具和预约要素收集工具并行化改造，配 P0/P1 分级告警，上线 0 P0。
- ③ 评测体系：分层指标体系 + 自动化平台（数据集管理/任务编排/LLM 自动化评估/报告），LLM-as-Judge 校准后人机一致率 40%→90%。

### Q3：讲讲 Agent 系统架构？

- 基于 ReAct 的 Multi-Agent：协调者 + 子智能体。
- 协调者只干意图识别 + 任务规划；子智能体各管一段（供给搜索召回门店/商品、预约预订收集要素/查 slot/下单、交易履约下单取消改派）。
- 为什么拆而不是单 Agent 大杂烩：单 Agent 要同时懂选店/预订/履约，Prompt 越堆越乱（上下文爆炸）；拆开后每个子智能体上下文窄、职责单一、好单独评测、出问题好定位，协调者只传「要什么」不传「怎么做」。
- 映射到机票：意图/行程规划（协调者）+ 航班检索（供给）+ 价格/行李/改签政策（多维查询）+ 交易（下单）。

### Q4：讲讲你们 Agent 有几次模型调用？

- 按环节拆开数，单轮典型 5 次左右：① 协调者意图识别(1)；② 任务规划(1)；③ 子智能体执行(N 次，ReAct 每个工具调用前后各一次 think/act)；④ 最终响应生成(1)。
- 关键是区分「一次用户交互」和「一次模型调用」：一次输入背后可能触发多次模型调用（意图 → 规划 → 多次工具决策 → 汇总）。
- 调用次数直接决定成本和延迟：开始一次交互打十几二十次模型，后通过压缩上下文 + 减少冗余工具调用优化，配合 Token 70k→1.5k；能说出「成本 = 调用次数 × 每次 token」说明真算过账。

### Q5：Agent Loop 什么时候结束？

- 四类退出条件：① 任务完成（工具调完、槽位满足、能直接回复）；② 达到最大步数（step 上限 8~10 步，最重要的兜底）；③ 信息不足且无法继续（追问过用户还没给，就把已收集信息反馈，不硬编）；④ 工具失败且重试耗尽（走降级或告知用户）。
- 关键原则：宁可提前结束（把确定性交还给人），也不要无限循环浪费 token；监控有「平均步数」「异常轮数」指标，卡住的 case 回流成评测差 case 去修。

### Q6：上下文如何治理的？

- 三阶段演进：全量堆砌 → 隔离精简 → 动态增补。
- 最早检索/工具结果/历史全塞进去，单次 70k Token 模型走神（用户问「今晚某行业有没有房」，前面塞了服务人员排班历史，回着回着开始讲服务人员）。
- 隔离精简（协调者与各子智能体各自维护上下文、互不污染）、动态增补（命中哪个工具/行业才补哪段）。
- 结果 Token 70k→1.5k、成本掉 98% 反而更准；核心不是「截断」而是「按需分层组织上下文」。

### Q7：记忆如何实现的？

- 诚实：在某公司做到的主要是短期记忆（当轮上下文 + 跨轮业务预约信息暂存），如「帮我约周五下午的服务人员」的「周五下午」「哪个服务人员」暂存在会话上下文，后续补全槽位，做得比较扎实。
- 长期记忆（跨多次会话、用户偏好沉淀）当时做得不够，理解应分层：业务态记忆（预约/订单/历史消费，存业务库直接查）；偏好/画像记忆（常去门店/偏好价格/常约服务人员，弱结构化 + 需检索，向量化存储）；对话摘要记忆（长对话滚动摘要保留关键事实）。
- 有效设计：业务库确定性用 SQL 拿、偏好类用向量检索拿、对话类用摘要，不同性质记忆不同存储，不一股脑塞 vector db。

### Q8：记忆是如何更新的？

- 三原则：① 什么时候写——关键节点写（槽位确定/预约成功/订单变化/用户明确表态），不是每轮都写，避免闲聊当记忆；② 怎么更新——尽量新增 + 幂等而非覆盖，识别修正（约周五改约周六要更新不产生两条冲突），结构化记忆条目 + 时间戳/版本；③ 如何防脏——写入前过滤（不写噪音、不写需实时查的时效数据）、可撤销、审计（可追溯来源）。
- 呼应评测：记忆正确性最终靠回放/校验保证（注入旧记忆看是否影响正确回答），就像用人机一致率 40%→90% 校准评测一样。

### Q9：动态记忆压缩如何保证记忆的稳定性？

- 风险：压缩完把关键事实丢了，或压缩后表达变味导致模型下次回答漂移。
- 四个手段：① 结构化而非自由文本压缩（固定字段人/事/时间/状态，如「周五下午已约某行业某服务人员」而非「用户后来约了个服务人员」）；② 分层保留 + 分级压缩（核心事实槽位/订单/偏好不长时间压缩，上下文细节才滚动摘要）；③ 压缩后校验（跑同一批可回放用例看是否退化，用分数说话）；④ 保留原始快照回溯。
- 一句话：让压缩只作用于「可降级的细节」，绝不让压缩动「核心事实」。

### Q10：评测集和指标如何构建的？

- 按场景 × 环节 × 维度分层评估：场景层不同行业/算子分开评（混平均分会掩盖短板）；环节层（意图识别/任务规划/工具路由/参数提取/最终响应）各打各的分；维度层（工具路由 97%、参数提取 96.6%、任务完成率、人机一致率、成本、延迟）。
- 平台侧：从 0 到 1 搭自动化评测平台，串起数据集管理、任务编排、大模型自动化评估、报告生成。
- 机票强多轮场景额外加两类指标：多轮任务完成率（整条改签/比价流程走通没）、跨轮槽位继承准确率（第二轮能否记住第一轮的条件）。

### Q11：如何保证评测的准确性和稳定性（文档性）？

- 两点保证可信：① 案例驱动校准（先写死人工评测标准，再拿人工标注案例让模型照标准打、逐轮迭代评分 Prompt，人机一致率 40%→90%）；② 能程序化判定就不靠模型（工具路由/参数提取有标准答案用规则精确判断，只有开放性最终响应用 LLM-as-Judge）。
- 稳定性靠三样：固定评测集 + 固定评分 Prompt 版本 + 跑回归；评分 Prompt 要版本化管理，否则数字没法比，评测最大的坑是没有基线、评分随缘。

### Q12：评测任务的检索和推理解耦里，检索是如何检索的？

- 解耦理解：检索是独立、可评测的环节，跟大模型推理分开，模型不直接参与「找」，只负责「根据找到的推理」。
- 检索四步：① 先定 Query（意图转结构化查询：行业/时间/地点/人商品）；② 多路召回（供给搜索按规则召回、服务人员排班按时间片查 ES，不靠单一向量库）；③ 过滤 + 排序（剔无关行业、按相关度/时间取 Top-N）；④ 评测闭环（检索环节单独评召回准确率，检索坏归检索、推理坏归推理）。
- 为什么解耦：检索准不准是系统性、可优化、可单独回归的，耦合在一起出问题定位不到是模型还是检索。

### Q13：长上下文窗口如何管理的？

- 长上下文本质是把有限预算分配给最有价值的内容。
- 做法：固定开销（系统 Prompt + 当轮意图）优先保住；核心工具结果按相关度排序尽量多留；次要的（历史摘要/候选列表）用摘要或 Top-N；超预算裁最不相关或分块截断 + 摘要降级；长历史用滚动摘要而非整段重放。
- 单次 Token 70k→1.5k 证明核心不是「窗口多大」而是「预算内放最关键的」，上下文越长模型越容易在无关信息里走神，宁可做窄做准。

### Q14：工具如何提参的？

- 提参分两层：① 参数提取（自然语言提取结构化参数：时间/人数/地点/服务项目，准确率 96.6%）；② 参数校验 + 槽位判断（判槽位是否满足，缺必填就追问，不带着残缺参数调工具）。
- 做得好的是参数提取（路由 97%、提取 96.6% 靠强约束 + 评测逼出来）；做得不够好的是槽位判断：多轮补槽不顺（判断不出优先追问哪个）、没做好最小必要信息策略（追问优先级不稳）、槽位修正（中途改主意直接覆盖可能前后矛盾）。
- 补强方向：槽位 schema + DST + 最小必要追问 + 幂等覆盖 + 评测指标（见复盘「下一步」）。

## 复盘总结

### 做得好

- 架构/调用链/Loop（Q3/Q4/Q5）：把「一次交互=多次调用」讲成可数设计，Loop 终止条件 4 类，成本=次数×token 点出来。
- RAG/检索解耦（Q1/Q12）：结构化 query → 多路召回 → 过滤排序 → 检索单独评测，明说用 ES/供给搜索而非只有向量库。
- 上下文治理/长上下文（Q6/Q13）：三阶段演进 + 预算管理，服务人员排班 288 时间片、几十个 POI 举例。
- 评测/准确性（Q10/Q11）：案例校准、人机 40%→90%、能程序化就程序化、评分 Prompt 锁版本。

### 待改进

- 记忆（Q7/Q8/Q9）：简历表述薄弱，本次被连挖四问，需补短期/长期分层、更新（关键节点写 + 幂等 + 可撤销 + 审计）、压缩稳定性（结构化 + 核心事实不压缩 + 可回放校验）。
- 工具提参槽位判断（Q14）：本场唯一明确短板，需补槽位 schema + DST + 最小必要追问 + 幂等覆盖 + 评测指标。

### 下一步

- 重点补记忆：短期/长期分层、记忆更新（关键节点 + 幂等 + 可撤销 + 审计）、压缩稳定性（结构化 + 核心事实不压缩 + 可回放校验）。
- 专项补预约预订 workflow 槽位判断：① 定义槽位 schema（必填/选填 + 类型校验）；② 用对话状态追踪 DST 维护「已填/缺啥」；③ 槽位满足判断（缺必填触发追问 + 最小必要）；④ 追问用「明确 + 缺省引导」结合检索结果；⑤ 槽位修正走幂等覆盖 + 留痕；⑥ 加「槽位继承准确率」「最小追问轮数」评测指标。
- 把「一次交互=多次模型调用 + 成本=次数×token」讲清楚。
- RAG 检索讲成「结构化 query + 多路召回 + 独立评测」，别只讲向量库。
- 每个答案绑定一个具体业务场景 + 一个可验证数字，避免背面经。
