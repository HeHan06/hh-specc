> 核心结论：企业效能 Agent 与 C 端导购 Agent 的根本差异在于——C 端追求「体验/转化」，企业效能追求「安全可控 + 成本 + 可复用的工具编排」。这解释了为什么 9 问里 4 问（Q5/Q6 沙箱、Q3 压缩、Q7/Q8 评测）都在问实际搭建过程中踩坑的点。

## 面试问题与回答

### Q1：介绍下你做的 Agent 项目，说说你负责的部分内容，重点说挑战和解决方案

- **开场一句话（30 秒）**：某公司某业务线 C 端 Agent 从 0 到 1 建设，覆盖 200 多个行业、日均 30w 次对话，跑选店→选品→交易→履约整条链路；核心开发，扛三块（架构、上下文治理、评测）。
- **挑战一（上下文爆炸怎么压下来）**：最早全量堆砌检索/工具结果/历史对话，单次 70k Token，模型中途走神（用户问「今晚某行业有没有房」，前面塞了服务人员排班历史，回着回着开始讲服务人员）。后按业务拆开重做：全量堆砌 → 隔离精简（协调者与子智能体各自维护上下文，互不污染）→ 动态增补（命中哪个工具/行业才补哪段）。单次 Token 70k→1.5k，成本降 98% 反而更准。
- **挑战二（评测不可信）**：人工抽检一致率仅 40% → LLM-as-Judge + 先写死人工评测标准 + 人工标注案例逐轮校准评分 Prompt → 人机一致率 40%→90%。
- **收尾主动带出**：长期记忆（还靠全量重放当轮上下文，跨轮易丢）、工具执行安全边界（工具全是内部白名单 API，未放开任意代码执行）是后续最想补的两块。

### Q2：Agent 项目技术选型

- 项目落在某业务线既有技术栈：Java 微服务 + GraphQL 导购架构（内部供给/交易/履约能力都通过 GraphQL 网关暴露，Agent 作为编排层）。
- 自己拍板的两条选型：① 用 Multi-Agent 拆任务而非单 Agent 大杂烩；② 把工具路由和参数提取单独做成可控环节。
- 中间件：MySQL 存业务数据、Redis 会话上下文缓存与热点、Kafka 异步与消息回流、ES 做服务人员排班多维检索（288 个 5 分钟时间片用 64 进制压缩编码，TP99 100ms 内）。
- 底层模型不是最纠结的，重点放在工具路由 97%、参数提取 96.6% 两个可控环节，再用评测兜底；企业效能要数据不出域/私有化，选型把合规/私有化排最前。

### Q3：上下文的压缩策略是什么，在哪些场景会压缩，如何保障压缩后的质量？长工具结果的预算管理机制是什么？

- **压缩策略总述**：三阶段演进（全量堆砌 → 隔离精简 → 动态增补），核心不是「截断」而是「按需、分层组织上下文」，Token 70k→1.5k。
- **三类压缩场景**：① 多轮历史（只留当轮 + 历史摘要）；② 工具返回长结果（服务人员排班一天 288 时间片、商品召回几十个 POI，不全量放）；③ 检索内容（进上下文前做相关度过滤，剔除不相关行业）。
- **保障压缩质量**：能结构化就结构化（抽成「哪天/几点/可约」紧凑字段）；先放摘要按需拉原片（RAG 思路）；压缩前后跑同一批可回归用例对比指标，用分数说话。
- **预算管理机制**：每轮设 Token 预算按优先级分配——固定开销（系统 Prompt + 当轮意图）优先保住；核心工具结果按相关度排序尽量多留；次要的用摘要/Top-N；超预算裁最不相关的或分块截断 + 摘要降级。

### Q4：Agent 项目有哪些工具，Agent 项目的运行部署环境是什么？

- **工具体系**（对应导购链路）：选店/选品（供给搜索）；预约预订（预订推品链路，重点做预订商品查询框架 + 推品/预约要素收集工具并行化改造）；交易履约（下单/取消/改派）。
- **三方服务人员预订**：独立做了一套标准化 API 工具（服务人员同步/排班同步/库存同步/预订下单/取消/改派），接入效率 40PD→5PD，沉淀 10+ 可复用能力。
- **一句话**：工具本质是把「用户意图 → 结构化参数 → 具体操作」规范化，路由准确率 97%、参数提取 96.6%。
- **部署环境**：跑在某公司自研微服务环境，Java + GraphQL 网关，MySQL/Redis/Kafka/ES；专属监控大盘 + P0/P1 分级告警（0 P0 事故）；灰度开关 + 一键回滚。
- **补课（如被追问在线/离线）**：长任务可拆「在线交互 + 离线异步执行」，离线走 Kafka 削峰。

### Q5：一些危险的 skill 操作，你们有什么保护机制吗？（想考察沙箱）

- **承认（自然带出）**：做的是 C 端导购，工具全是内部白名单 API（选店/查排班/下单），参数强约束，模型不能拼命令/任意执行代码；走的是「把执行面收窄到白名单」路线，从源头不给模型乱来的空间，不是容器沙箱路线。
- **做过的安全控制（四层）**：① 能力白名单（工具和参数枚举死，路由 97% 挡住不安全输入）；② 参数校验（缺必填/越界/非法直接拒掉）；③ 审计 + 分级告警（敏感操作全程留痕）；④ 人工兜底（真实变更走灰度开关 + 一键回滚）。
- **如果上沙箱的完整方案**：权限最小化（白名单命令/路径、禁 shell 拼接）→ 隔离执行（容器/wasm，配额、非特权、断网或白名单出网、用完即毁）→ 内容安全（不可信输入转义过滤、工具返回校验）→ 审计告警（敏感操作二次确认）→ 高危操作人工审批。核心：模型只生成意图，执行边界与权限完全由代码层控制。

### Q6：沙箱有使用过吗？如何保障 skill 安全的？

- **诚实回答**：严格说没有；C 端导购工具是强类型、参数约束的标准化 API，没有「模型生成任意代码再去跑」的场景，沙箱未实际部署过。
- **把安全内核讲成真实实践**：沙箱要解决的是「把模型能力边界收窄到可控集合」，这点做到了——推品/预约要素收集工具并发调 + 参数强校验（路由 97%、提取 96.6%）；三方服务人员预订库存一致性做四级保障（自动重试 + 延迟双写 + 每日全量对账 + 异常告警），库存一致率 100%。
- **落地沙箱的分层**：权限最小化 → 容器/wasm 隔离 → 内容防注入 → 审计告警 → 高危动作人工审批，并配评测回归兜底。

### Q7：Agent 评测体系如何搭建的？

- **定指标（场景 × 环节 × 维度）**：场景层不同行业分开评（避免平均分掩盖短板）；环节层（意图识别/任务规划/工具路由/参数提取/最终响应）单独打分；维度层（工具路由 97%、参数提取 96.6%、任务完成率、人机一致率、成本、延迟）。
- **搭平台**：从 0 到 1 搭自动化评测平台，串起数据集管理、任务编排、大模型自动化评估、报告生成。
- **让评分可信（关键）**：主观评价优先 + 案例驱动校准——先写死人工评测标准，再用人工标注案例让模型照标准打、逐轮迭代评分 Prompt，人机一致率 40%→90%；有标准答案的环节用规则/程序化判定，只有开放性最终响应才用 LLM-as-Judge。
- **落地价值**：改代码跑回归看指标退没退，坏 case 回流数据集，Token 70k→1.5k 功能没劣化就是靠它测出来的。

### Q8：评测数据集是哪里来的？

- **四类来源**：① 线上真实对话采样（从日均 30w 对话按行业/场景/难度分层抽）；② 坏 case 回流（评测失败/用户投诉回流当重点回归样本，最值钱）；③ 人工构造难例（模糊描述跨工具、不同行业混在一个问题里）；④ 带标准标签的程序化样本（工具路由/参数提取用规则精确判定）。
- **配套能力**：数据集分层管理（训练/验证/测试分开、按场景难度打标），形成「采集 → 标注 → 评测 → 坏 case 回流 → 再评测」数据闭环。

### Q9：内部 AI coding 用的什么工具？

- **按实际用说**：日常用 Copilot / 通义灵码 / Cursor 做补全和片段生成；完整任务用 Claude Code / Trae 这类 coding Agent。
- **用 Agent 视角点评**：AI coding 本质就是 Agent（指令理解 + 上下文管理 + 工具调用 + 评测），最在意两点——长上下文/多文件改动下稳不稳、是不是真理解了已有代码；内部建 coding 工具倾向按 Agent 框架做（前置上下文管理 + 后置测试闭环验证）。
