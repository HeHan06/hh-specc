## 二、根本原因

1. **技术视野局限**：之前做的Agent是公司内部封闭环境的Agent，工具链受限，业务场景单一（如内部RAG问答、固定流程自动化），没有接触过对外的、开放任务的Agent系统。
2. **缺乏产品化思维**：没考虑过Agent作为产品交付时需要的能力——沙箱安全、会话管理、hook扩展点、多租户隔离等。
3. **对AI工程化前沿关注不足**：Claude Code、Cursor、Copilot Chat等AI编程工具已经成为行业标杆，它们的架构设计（Agent loop、tool use protocol、sandboxing）是当前Agent工程化的最佳实践参考。

## 三、高频问题标准口述答案

### Q1：新出的 Agent 框架了解哪些？有什么特点？

**口述**：最近比较关注的有 LangGraph、AutoGen、CrewAI、MCP 协议。

**LangGraph**：
- 核心是把 Agent 工作流建模成有向有环的状态图（StateGraph），每个节点是纯函数，接收 State 返回 State 的部分更新。内部用一个 `TypedDict` 或 Pydantic 模型定义 State schema，每个节点返回的字段通过 reducer 合并回全局 State，比如消息列表用 append 策略，其他字段用覆盖策略。
- 边分为普通边（固定路由）和条件边（根据当前 State 动态决定下一个节点），天然支持循环和分支。
- 内置 Checkpointer 做状态持久化，每一步执行后自动打 checkpoint，支持中断后从任意节点恢复和时间旅行调试。底层可以对接 SQLite、Postgres 等存储。这也是它能做 Human-in-the-loop 的基础——在关键节点暂停等人工审批，审批后从 checkpoint 继续。

**AutoGen**：
- 核心是 ConversableAgent 抽象，每个 Agent 有 system_message 定义角色，通过 `generate_reply` 方法接收消息、调用 LLM、执行工具、返回回复。多 Agent 间通过消息队列传递，像一个对话版的生产者-消费者模型。
- 支持 GroupChat，用一个 GroupChatManager 控制发言顺序，通过一个 selector LLM 动态决定下一轮谁发言，防止多个 Agent 同时抢话。
- 工具注册通过 `register_for_llm` 和 `register_for_execution` 两步，前者把工具 schema 注入 prompt，后者绑定实际执行函数，实现了声明和执行分离。

**CrewAI**：
- 抽象了三层：Agent（角色+目标+背景故事）、Task（描述+期望输出+分配给哪个 Agent）、Crew（编排多个 Agent 按顺序或层级执行任务）。
- 底层是顺序执行或层级执行，层级模式中有一个 Manager Agent 负责拆分任务和委派，比 AutoGen 的 GroupChat 更简单直接。

**MCP 协议（Model Context Protocol）**：
- 这是 Anthropic 推的 Agent 与外部工具/数据源的标准化协议，基于 JSON-RPC 2.0。分为 Server 端（暴露 resources、tools、prompts）和 Client 端（Agent 宿主）。Server 通过 `tools/list` 告诉 Client 自己能做什么，Client 通过 `tools/call` 调用。传输层支持 stdio 和 HTTP+SSE 两种方式。
- 核心价值：以前每个 Agent 框架都要自己写工具适配层，MCP 让工具提供方只写一次 Server，所有兼容 MCP 的 Agent 都能用，类似 USB 协议之于外设。

### Q2：Claude Code 给你们带来了什么启发？

**口述**：从架构设计和工程化角度，三点核心启发——

**1. 权限模型的分层设计**：
Claude Code 的权限不是简单的"允许/拒绝"，而是分三级：allow（始终允许）、ask（每次询问）、deny（始终拒绝）。工具可以按路径模式匹配（如 `Bash(rm:*)` 匹配所有 rm 命令），支持通配符。这个设计背后是"最小权限原则"——默认大部分操作为 ask，只有用户明确信任的才 allow。我们在做内部 Agent 时没考虑过权限粒度，所有工具一视同仁，这其实是个安全漏洞。

**2. Tool Use 的协议化而非函数调用**：
Claude Code 和底层模型之间的工具交互不是简单的 JSON function call，而是一个结构化的消息协议。工具定义包含 name、description、input_schema（JSON Schema），模型返回 tool_use 消息块，Agent 执行后返回 tool_result 消息块，内容块通过 content_block 数组排列，每个块有独立 ID。这个设计的精妙之处在于：同一个工具可以被多次调用，每次调用和结果都能通过 content_block_id 精确关联，不会出现"第二个 grep 的结果覆盖了第一个"的问题。整个对话历史是一条完整的、可审计的因果链。

**3. Hook 作为中间件模式**：
Hook 本质上是把 Agent 的工具调用链路变成了可插拔的中间件管道。每个 hook 是一个外部脚本（shell 或 Python），通过 stdin 接收 JSON 输入，stdout 输出 JSON 结果，退出码决定允许/拒绝。这种设计不侵入 Agent 核心代码，企业可以写自己的 hook 而不需要 fork Agent 源码。相比直接在 Agent 代码里写 if-else，Hook 让安全策略和业务逻辑完全解耦。

### Q3：Claude Code 的 Hook 钩子函数作用是什么？哪些场景使用？

**口述**：Hook 是 Agent 运行时在特定事件点触发的用户自定义脚本，本质是事件驱动的中间件模式。

**Hook 的类型与触发时机**：
- **PreToolUse**：在工具调用参数校验通过后、实际执行前触发。Hook 拿到工具名和参数，可以修改参数、拒绝执行、或放行。实现上，Agent 把工具调用信息序列化为 JSON 通过 stdin 传给 hook 脚本，脚本 stdout 返回 JSON 包含 decision（allow/deny）和可选的 modifiedInput。退出码 0 表示 allow，非 0 表示 deny，2 表示 block 并终止整个会话。
- **PostToolUse**：在工具执行完成后、结果返回给模型前触发。可以做结果审计、脱敏、日志持久化。
- **Notification**：在 Agent 状态变更时触发，如会话开始、结束、用户空闲超时等，用于外部系统集成。

**Hook 的输入输出协议**：
每个 hook 收到的是标准 JSON 结构，包含 `session_id`、`transcript_path`（对话记录的路径）、`hook_event_name` 和事件相关的 payload。比如 PreToolUse 的 payload 包含 `tool_name`、`tool_input`。PostToolUse 额外包含 `tool_response`。这种统一协议让 hook 之间可组合——一个企业可以写 10 个 hook 脚本，每个只做一件事，通过配置按顺序链式执行。

**进阶场景**：
1. **敏感信息脱敏**：PostToolUse hook 在工具返回结果中检测手机号、身份证、API key 等正则模式，自动替换为 `***` 后再返回给模型，防止敏感数据进入 LLM 上下文。
2. **成本追踪**：PreToolUse + PostToolUse 组合，记录每次 LLM 调用和工具调用的 token 消耗、耗时，写入成本监控系统，按 session 维度出账单。
3. **动态工具注入**：在 PreToolUse 阶段，hook 可以根据当前上下文动态决定是否允许某个工具，比如"只在代码仓库根目录下允许 git 操作，子目录禁止"。
4. **合规检查**：在金融/医疗场景，PreToolUse hook 对工具调用做合规检查，比如检测到对生产数据库的写操作，要求提供 change ticket 编号。

### Q4：沙箱的作用与实现细节？

**口述**：沙箱的核心目标是让 Agent 执行的不可信代码在受限环境中运行，实现"最小权限执行"。关键要隔离的是四个维度：文件系统、网络、进程、资源。

**隔离层级与实现原理**：

**1. 进程级隔离（seccomp + chroot）**：
- seccomp（Secure Computing Mode）：Linux 内核特性，通过 BPF（Berkeley Packet Filter）规则限制进程可用的系统调用。比如只允许 read、write、exit 等 20-30 个 syscall，禁止 fork、execve、ptrace 等危险调用。seccomp 有两种模式：strict 模式只允许 read/write/exit/_exit；filter 模式可以用 BPF 程序精确控制，比如"允许 socket 但只允许 AF_INET 且端口 443"。一旦设置，进程本身不可撤销，子进程自动继承。
- chroot：把进程的根目录改到指定路径，但 chroot 是用户态概念，root 用户可以逃逸（通过 mknod 创建设备文件、chroot 后再 chdir 出去等），必须配合 seccomp 和 privilege drop 才有意义。
- 优点：零额外开销，无需启动容器。缺点：隔离弱，共享内核，内核漏洞可导致逃逸。

**2. 容器级隔离（Docker / gVisor）**：
- Docker 底层依赖 Linux namespace（7 种：PID、NET、IPC、UTS、MNT、USER、Cgroup）实现视图隔离，每个 namespace 让进程看到自己的"独立世界"。比如 PID namespace 让容器内进程认为自己是 PID 1，NET namespace 让容器有独立网卡和 IP。cgroup 负责资源限制，通过 cgroup v2 的 `cpu.max`、`memory.max`、`io.max` 文件设置配额。
- 文件系统隔离用 OverlayFS：下层是只读镜像层，上层是读写层，容器删除后上层丢弃，镜像层不变。配合 tmpfs 挂载 `/tmp`，确保临时文件不落盘。
- gVisor（Google 出的容器运行时）：不走 Docker 直接共享内核的路线，而是在用户态实现了一个用 Go 写的"内核"（Sentry），拦截应用的所有系统调用，在用户态模拟执行。每个系统调用都要经过 Sentry 的判断，开销比原生 Docker 高约 10-30%，但安全性大幅提升，因为即使应用触发了内核漏洞，漏洞也发生在 Sentry 进程中而非宿主内核。
- 缺点：共享宿主内核（Docker 原生模式），容器逃逸本质上就是内核漏洞利用。

**3. 微虚拟机级隔离（Firecracker）**：
- Firecracker 是 AWS 为 Lambda/Fargate 设计的轻量级 VMM（Virtual Machine Monitor），基于 KVM。每个 microVM 有独立的精简 Linux 内核，不共享宿主内核，安全边界是硬件虚拟化（Intel VT-x / AMD-V）。
- 和传统 QEMU 的区别：Firecracker 只保留了运行一个 Linux 客户机的最小设备模拟集（virtio-net、virtio-block、串口、键盘），没有 BIOS、没有 GPU、没有 USB。启动时间 125ms 以内，内存开销约 5MB。特别适合"一次执行一个任务就销毁"的 Agent 场景，因为每次执行后整个 VM 销毁，状态完全清零。
- 缺点：每个 VM 需要自己的内核和 rootfs 镜像，镜像管理和冷启动是工程挑战。

**4. WebAssembly 沙箱**：
- Wasm 的沙箱是语言级而非操作系统级的。Wasm 模块只能访问自己线性内存空间，不能直接读写宿主内存，不能调用系统 API，除非通过宿主显式导入函数。Wasm 运行时（如 Wasmtime、Wasmer）在编译时静态验证字节码，保证不会有越界访问。
- 适合场景：让 Agent 执行用户上传的代码片段（如数据分析脚本），Agent 动态生成 Wasm 模块，注入有限的 API（如只读数据库查询函数），在 Wasm 运行时执行，结果通过共享内存传出。
- 缺点：只能运行编译到 Wasm 的语言（Rust、C/C++、Go 等），Python 等动态语言目前支持有限。

**工程实践要点**：
- 文件系统：用 OverlayFS 给每次 Agent 执行创建一个临时层，执行结束后丢弃。工作目录白名单挂载（只读或读写），其他路径不可见。
- 网络：默认创建一个无外网的 network namespace，只允许 localhost。需要外部 API 时，通过 HTTP 代理白名单放行，代理层做请求审计。
- 进程：禁止 fork、execve、clone 等创建子进程的系统调用，防止沙箱内启动新进程逃逸监控。
- 超时与资源：每个沙箱实例设 3 个硬限制——wall time（总执行时间）、CPU time（实际 CPU 时间）、内存上限，三者任一超限即 SIGKILL。

### Q5：Agent Runtime 的机制是什么？

**口述**：Agent Runtime 是连接大模型和工具执行环境的桥梁，核心是一个"思考-行动-观察"的循环引擎。我从五个维度讲：

**1. Agent Loop（事件循环）—— 核心骨架**：
```
while not task_complete and step < max_steps:
    response = llm.chat(messages)           # 模型思考
    if response has tool_calls:             # 模型决定用工具
        for each tool_call:
            result = execute_tool(tool_call) # 执行工具
            messages.append(tool_result)     # 结果追加到上下文
    elif response has final_answer:         # 模型认为任务完成
        break
    else:
        messages.append(assistant_msg)      # 纯文本追问
```
这个循环的关键设计决策：
- **max_steps**：防止无限循环，Agent 可能在"执行工具 → 结果不对 → 再执行"中死循环，必须设硬上限。
- **early_stop 条件**：除了模型主动输出 final_answer，还要检测是否连续 N 步没有实质性进展（如反复调用同一个工具同样的参数），此时强制终止并让模型总结。
- **并行工具调用**：如果模型在一次响应中返回了多个 tool_use 块（比如同时读 3 个文件），且这些调用之间没有依赖关系，Runtime 应该并行执行而非串行，这能显著降低延迟。

**2. 工具注册与调度**：
- 工具定义采用 JSON Schema 描述参数：`{name, description, parameters: {type: "object", properties: {...}, required: [...]}}`。这个 schema 会被注入到 system prompt 中，模型根据 description 选择工具，根据 parameters 生成参数。
- 调度器维护一个工具注册表（map[name] → handler），handler 是标准函数签名 `async (params: dict) -> ToolResult`。执行前做参数校验（pydantic 或 jsonschema validate），执行后统一包装成 ToolResult（包含 output、error、metadata）。
- 高级设计：工具分本地工具和远程工具。本地工具在 Agent 进程内执行（如读文件），远程工具通过 HTTP/MCP 调用外部服务（如 Jira API）。调度器对调用方透明，只暴露统一接口。

**3. 上下文窗口管理**：
- 大模型上下文窗口有限（如 200K tokens），对话历史、工具调用结果、system prompt 共享这个窗口。超出窗口时模型会丢失早期信息，导致"遗忘"。
- 策略一：**滑动窗口**——只保留最近的 N 条消息，旧消息丢弃。缺点是丢失关键上下文（如用户最初的需求）。
- 策略二：**自动摘要**——当上下文接近限制时，用一个小模型对历史消息做摘要，把摘要压缩成一条 system 消息追加，原始消息归档。摘要是不可逆的有损压缩，但关键信息保留率高。
- 策略三：**结构化归档**——把工具调用结果中的重要信息（如文件路径、关键数据）提取到结构化存储（如 key-value），后续步骤通过工具查询，而不是始终依赖上下文窗口。

**4. 会话持久化与 Checkpoint**：
- 每次 Agent Loop 迭代后，Runtime 把当前 messages 数组、已执行步骤数、工具调用历史序列化持久化。底层用 SQLite 存 JSON 即可，关键是原子写入——先写临时文件再 rename，防止写入中断导致损坏。
- Checkpoint 粒度：每步一个 checkpoint 太重，可以每 N 步或每完成一个子任务（语义边界）做一个 checkpoint。恢复时加载最近 checkpoint，重放之后的步骤。
- Human-in-the-loop 依赖这个机制：到达审批节点时持久化状态、暂停循环、通过 WebSocket 或轮询通知前端，人工操作后从 checkpoint 恢复继续。

**5. 流式处理与中断**：
- Agent Loop 中有两处需要流式：LLM 的输出（用户不想等 5 秒看一个完整回答）和工具执行结果（大文件读取逐步返回）。
- LLM 输出用 SSE（Server-Sent Events）逐 token 推送，Runtime 在收到完整 tool_use 块之前缓存 token，块完整后触发工具调度。支持用户中途打断——发送 cancel 信号，Runtime 在下一个迭代开始时检查取消标志，优雅退出循环并持久化当前状态。
- 流式与非流式混用：LLM 调用用流式，工具执行用非流式（等完整结果），工具结果用流式推送（如 tail -f 日志文件）。

**总结**：Agent Runtime 的工程难点不在单一机制，而在于这五个维度的协调——循环控制不能太死也不能太松、上下文管理要用最少的 token 保留最多的信息、持久化要保证一致性、工具执行要安全可控。本质上是在做一个分布式的、事件驱动的、有状态的有限状态机。
