## 6 个不足点的标准口述答案

### 1. 单机 QPS 优化 5 倍，具体怎么做的？

> 先说明场景：这是 Beam（美团独立生活助手 APP）接入服务零售 Agent 的项目，我负责"店内预订推品链路"。这里的"单机 QPS"指**服务零售 Agent 子 Agent 的单机承载能力**——压测时端到端请求 QPS 只有 1~2，也就是单台机器每秒只能扛 1~2 个完整请求。
>
> 我通过压测定位到两个瓶颈：一是 **CPU 高负载**，二是**推品工具和预约要素收集工具串行调用**导致端到端 RT 过长。
>
> 对应做了两个动作：
>
> 第一，**用阻塞队列缓解 CPU 高负载**。服务零售 Agent 在处理模型流式输出等环节存在瞬时高并发的处理压力，我用有界阻塞队列做缓冲，配合消费任务按固定节奏拉取处理，实现削峰填谷，避免线程池被瞬间打满、CPU 峰值飙高。
>
> 第二，**推品工具和预约要素收集工具并行化改造**。原来这两个工具串行调用，端到端 RT 等于两者之和；改成并行后同时发起，RT 从"求和"降到"取最大值"，吞吐随之提升。
>
> 结果是**单机 QPS 从 1~2 提升到 10+，约 5 倍**；同时推品工具首 token 时延下降 33%，预约要素收集工具下降 38%。

### 2. 评测平台的系统设计难点

> 难点有三个：
>
> 第一，评测数据集的质量和覆盖度。Agent 覆盖 200+ 行业，保证评测集多样、有代表性最难。做法是分层构建——从线上真实对话抽样沉淀，按行业、意图、难度分层采样，并建标注规范。
>
> 第二，LLM-as-Judge 的一致性和校准。大模型裁判最大问题是"评得不准、和人的判断不一致"，所以一开始人机一致率只有 40%。解法是案例驱动校准——用人工标注的黄金案例校准评分标准，通过 few-shot 和 rubric 对齐，把一致率拉到 90%。
>
> 第三，大规模评测的任务编排。要支持数据集管理、批量执行、失败重试、并发调度，还要可追溯每次评测用的版本和数据。用任务编排把流程标准化，做到可复现、可回溯。
>
> 核心难点是"怎么让机器评得和人类一样准"，这是评测平台能否被信任的关键。

### 3. 大模型裁判（LLM-as-Judge）的提示词最佳实践

> 五条最佳实践：
>
> 第一，明确评估维度和评分标准（rubric）。把评估拆成具体维度（准确性、完整性、格式符合度），每个维度给明确分值和扣分标准。
>
> 第二，结构化输出。要求同时输出"评分 + 理由"，固定成 JSON，评分和理由分离，方便统计追溯。
>
> 第三，few-shot 示例校准。给几个已人工标注的黄金案例，让裁判对齐评分尺度，这是提升一致率最有效的手段。
>
> 第四，单一职责。一次只评一个维度，避免多维混在一起互相干扰。
>
> 第五，防偏见。大模型裁判有位置偏见（偏好排前答案）和长度偏见（偏好更长答案），要交换候选答案顺序做双向评估取平均，并在 rubric 里明确"长度不等于质量"。
>
> 落地核心是"主观评价优先 + 案例驱动校准"，先用人的判断定标准，再用 few-shot 固化给模型，最终一致率 40%→90%。

### 4. MVCC 原理 + 如何解决读已提交和可重复读

> MVCC 核心思想是"读不加锁、通过版本快照实现一致性"，靠三样东西：
>
> 第一，每行记录有两个隐藏列：trx_id（最近修改这行的事务 id）和 roll_pointer（回滚指针，指向 undo log）。
>
> 第二，undo log 版本链。每次修改生成一个旧版本，通过 roll_pointer 串成版本链，每个版本有各自的 trx_id。
>
> 第三，ReadView（读视图）。判断某版本对当前事务可不可见的依据，四个字段：m_ids（活跃未提交事务集合）、min_trx_id（活跃最小 id）、max_trx_id（下一个要分配的事务 id）、creator_trx_id（创建者自己）。
>
> 可见性规则：版本 trx_id 等于 creator → 可见；小于 min_trx_id → 已提交可见；大于等于 max_trx_id → 未来事务不可见；落在中间看是否在 m_ids 里，在则未提交不可见，不在则已提交可见。
>
> RC 和 RR 的区别在 ReadView 生成时机：
> - RC：每次 SELECT 都生成新 ReadView，能读到别的事务最新提交，但可能前后读不一致，出现幻读、不可重复读。
> - RR：只在事务第一次 SELECT 生成一个 ReadView 并一直复用，事务内快照一致，解决不可重复读。
>
> 补充：RR 下普通 SELECT（快照读）靠 MVCC 解决幻读；SELECT FOR UPDATE、UPDATE、DELETE 这类当前读 MVCC 管不住，要靠 next-key lock（记录锁 + 间隙锁）防幻读。

### 5. Kafka 场景：3 partition + 3 consumer，怎么加速？变 6 个会更快吗？

> 结论：变 6 个消费者不会更快，反而有 3 个空闲。
>
> 原因：同一消费组内，一个 partition 同一时刻只能被一个 consumer 消费，partition 是并行度上限。3 个 partition 最多 3 个 consumer 并行，多出的分不到 partition、处于空闲。
>
> 加快的正确做法：
> 第一，增加 partition 数量（根本手段）。从 3 扩到 6，consumer 也加到 6 才真正并行。但 partition 只能增不能减，且增加会触发 rebalance、短暂中断，要评估。
> 第二，提升单条消息处理效率。瓶颈在消费者处理逻辑时，优化代码比加 consumer 更有效。
> 第三，批量消费。调 fetch.min.bytes、max.poll.records 一次拉更多，减少网络往返。
> 第四，异步化。消费和处理解耦，消费线程快速拉取投递内部队列，处理线程并行处理。
>
> 一句话：consumer 数超过 partition 数没意义，并行度上限由 partition 数决定。

### 6. Redis ZSet 原理 + 各操作复杂度 + 为什么不用 hash

> ZSet 是有序集合，底层用两种结构组合：哈希表（dict）存 member→score 映射，跳表（skiplist）按 score 排序。哈希表保证 O(1) 查分数，跳表保证排序、范围查询、排名。元素少时（默认 128 内）用紧凑 listpack 省内存。
>
> 操作复杂度（N 元素数，M 返回数）：
> - ZADD：O(log N)
> - ZSCORE：O(1)
> - ZRANK / ZREVRANK：O(log N)
> - ZRANGE / ZREVRANGE：O(log N + M)
> - ZRANGEBYSCORE：O(log N + M)
> - ZREM：O(log N)
> - ZCARD：O(1)
>
> 为什么不用 hash：hash 只能 O(1) 按 field 取单个值，但没有顺序概念——无法排序、范围查询、按排名取。ZSet 的价值就在"有序"，适合排行榜、延时队列、滑动窗口限流、按优先级取 TopK。hash 解决"按键取"，ZSet 解决"按序取"，不互相替代。
