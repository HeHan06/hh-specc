### 一、四象限上下文治理方法（待提升点1）

> "上下文膨胀是我在 Agent 优化中遇到的第一个大问题。MVP 阶段我们为了快速验证，把所有信息——用户画像、历史行为、历史订单、7 类卡片总结规范——全部塞进上下文，单次输入 Token 最高到 70k。结果模型'智商下降'：指令遵循变差、幻觉增多、时延飙升到 26 秒。
>
> 怎么解决？我借用了 Karpathy 的一个类比——**LLM 是 CPU，上下文窗口是 RAM，上下文工程就是内存管理器**。目标不是把 RAM 塞满，而是通过调度算法决定：什么时候加载、什么时候换出、什么优先。
>
> 基于这个思路，我把所有上下文信息按**两个维度**分类：一是**时效性**——信息是静态不变还是会随对话变化；二是**Token 长度**——信息占多大空间。这样就形成了四个象限，每个象限用不同的治理策略：
>
> **第一个象限，长且静态**——比如 7 类卡片的总结规范，总共 6000 Token，但每次对话不一定都用得到。策略是**懒加载**：不再全量注入 System Prompt，而是下沉到工具层，调用门店搜索工具时才注入门店卡片规范，调用交易工具时才注入订单规范。
>
> **第二个象限，长且动态**——比如用户行为序列有 10k Token，但大部分对当前 Query 没有价值。策略是**隔离压缩**：只保留入口关键信息（用户从哪个页面进来的），其他行为数据不注入；历史订单从默认注入改为通过工具按需拉取。
>
> **第三个象限，短且静态**——比如需求澄清话术，原来设计成一个工具要额外调用一次，500 Token 的开销。策略是**固化**：直接写进 System Prompt，零延迟、强确定性。
>
> **第四个象限，短且动态**——比如用户实时位置、入口环境。策略是**结构化高亮**：用 XML 标签标记，比如 `<location>北京市朝阳区</location>`，提升模型对这个信息的注意力权重。
>
> 四个象限治理完之后，单次输入 Token 从 70k 降到 1.5k，压缩率 97%。关键是**丢的不是关键信息，而是噪声**——体验分反而从 2.14 回升到了 2.38。
>
> 这里有一个血泪教训：中间我们为了省 Token，把 Tool Result 融合进了 Assistant Message，破坏了标准对话协议，导致模型出现'记忆错乱'。后来严格恢复了 `User → Assistant → Tool Call → Tool Result → Assistant` 的标准流，问题才解决。所以**上下文工程不是越省越好，协议完整性是底线**。"

### 二、Agent 设计中遇到的问题和解决方法（待提升点2）

#### 问题 1：工具路由不准确（准确率从 90% 跌到 67%，再拉回 97%）

> "工具路由不准确是我遇到的最棘手的问题，而且出现了两次。
>
> **第一次是国产模型替换时**。从 GPT-4.1 切到 DeepSeek-V3，工具路由准确率从 90.2% 直接掉到 67.2%。根因是国产模型对长 Prompt 的指令遵循能力弱——GPT-4.1 读 6000 字 Prompt 还能严格遵守，DeepSeek 在相同长度下会'漏掉'部分约束，工具 description 理解也偏差更大。
>
> 我的解决方案分三步：
> 1. **上下文重构**：把 System Prompt 从 9000+ Token 精简到 5000 Token，去掉冗余描述，只保留核心约束。
> 2. **强化指令结构**：用 XML 标签包裹关键约束，比如 `<constraint>...</constraint>` 包裹工具使用规则，`<format>...</format>` 包裹输出格式要求。DeepSeek 对结构化标记更敏感，这个改动效果明显。
> 3. **增加格式校验层**：在模型输出后加一层 Function Call schema 校验，不合法格式自动重试，弥补国产模型容错性差的短板。
>
> 这三步做完，准确率从 67% 拉回到了 90%+。
>
> **第二次是架构融合后**。CA 和 SA 融合，工具池从几个膨胀到十几个，模型开始出现工具混淆——比如把'名词解释'意图路由到'供给搜索'，因为 Query 里提到了品类关键词。
>
> 这次我用了两个手段：
> 1. **工具 description 重构**：每个工具的 description 第一句写'做什么'，第二句写'什么时候用、什么时候不用'。负向约束往往比正向约束更能减少误调用。
> 2. **工具检索式路由**：工具数量多了之后，不把所有工具 definition 都塞给模型，而是先用 Query 做语义召回，只把最相关的几个工具喂给模型选，既降 Token 成本也减少选错概率。
>
> 最终工具路由准确率稳定在 97%。剩下 3% 的失败主要是意图边界模糊的 case，比如'最近爆火的法式美甲是什么'——到底是名词解释还是供给搜索，人工标注也有分歧。"

#### 问题 2：长上下文导致模型"智商下降"

> "这个问题我在四象限治理里已经详细讲了，这里补充一个关键细节。
>
> MVP 阶段上下文膨胀不只是 Token 多的问题，更致命的是**信噪比太低**。模型在 70k Token 的上下文里'迷失'了——它看到了太多信息，反而不知道该关注什么。具体表现是：指令遵循变差（该调工具时不调）、幻觉增多（编造不存在的门店）、时延飙升（26 秒首 Token）。
>
> 我的核心思路是**减噪不是减信息**。不是粗暴截断上下文，而是按信息的'当前 Query 相关性'做筛选。最终 Token 从 70k 降到 1.5k，但体验分从 2.14 回升到 2.38，说明丢的都是噪声。
>
> 这里有一个重要的工程教训：中间我们为了省 Token，把 Tool Result 融合进了 Assistant Message。这个 hack 破坏了 LLM 原生的对话协议，导致模型出现'记忆错乱'——它分不清哪些是自己说的、哪些是工具返回的。后来严格恢复了标准消息流，问题才解决。所以**上下文工程有底线，协议完整性不能牺牲**。"

#### 问题 3：多 Agent 串行调用导致时延过高（26 秒首 Token）

> "MVP 阶段用的是 Multi-Agent 架构，一次 Query 触发 4-5 次模型调用：主 Agent 规划 → 找供给 Agent 搜索 → 主 Agent 审阅 → 预约 Agent 收集要素 → 主 Agent 总结。全链路端到端首 Token 延迟 26 秒，C 端完全不可接受。
>
> 我做了四层优化：
> 1. **减少调用次数**：把预约 Agent 和交易 Agent 合并，通过工具合并减少 1-2 次调用。
> 2. **并行化改造**：把可以并行的工具调用并行执行。比如推品工具和预约要素收集工具并行后，首 Token 时延分别降了 33% 和 38%。
> 3. **AI 搜索透传**：高频搜索场景中，主 Agent 不再二次总结 AI 搜索结果，直接透传给用户，省掉一次模型调用。
> 4. **架构融合**：最终 CA 与 SA 融合，从根本上消除跨 Agent 调用开销。
>
> 这套优化让首 Token 时延从 26 秒降到了可接受的范围，上线后 0 P0 事故。"

#### 问题 4：国产模型替换后的效果回退

> "从 GPT-4.1 切到 DeepSeek-V3 时，不只是工具路由准确率下降，整体效果都有回退。团队内部一度争议'要不要回退到 SOTA 模型'。
>
> 我当时的判断是：合规是红线，不能回退。所以选择硬抗，通过工程手段补偿模型能力差距。具体做了三件事：
> 1. **Prompt 精简 + 结构化**：国产模型对短而结构化的 Prompt 遵循更好，把 9000 Token 的 Prompt 精简到 5000，用 XML 标签强化关键约束。
> 2. **上下文治理**：就是四象限模型，把 Token 从 70k 压到 1.5k，让国产模型在它能处理的窗口长度内工作。
> 3. **增加工程兜底层**：Function Call 格式校验、工具结果合理性判断、失败自动重试——用工程确定性弥补模型不确定性。
>
> 花了一个多月把核心指标拉回来，工具路由准确率从 67% 回到 97%，参数提取准确率 96.6%。这段经历让我深刻理解到：**模型能力不够，工程来凑——但工程补偿是有上限的，选模型时就要考虑工程适配成本**。"

### 三、LeetCode 简单题刷题指南（待提升点3）

#### 面试算法题口述框架（通用）

不管遇到什么题，按这个框架说：

> 1. **先复述题意**，确认理解无误："这道题是给定一个 XX，要求找到 XX，输出 XX。"
> 2. **说暴力解法**："最直接的做法是 XX，时间复杂度 O(XX)。"
> 3. **分析瓶颈**："瓶颈在于 XX，可以优化的方向是 XX。"
> 4. **说优化思路**："我用 XX 方法/数据结构，核心思路是 XX。"
> 5. **说复杂度**："时间 O(XX)，空间 O(XX)。"
> 6. **写代码前说边界**："需要注意的边界情况有：空输入、单元素、全相同元素等。"

这个框架即使没做出最优解，也能让面试官看到你的思考过程——**面评里说你"简单题未找对最优解"，但如果思考过程清晰，评价会好很多**。

#### 1. 二维数组/矩阵类（本次面试栽的题型）

**核心思路**：二维数组题目 90% 可以用**"从合适的起点出发"**来简化。常见起点：
- **右上角**：搜索二维矩阵（每行递增、每列递增）——从右上角出发，大了往左走，小了往下走
- **左下角**：同上，对称思路
- **左上角**：BFS/DFS 遍历起点

**必刷题**：

| 题号 | 题目 | 核心技巧 |
|------|------|----------|
| 74 | 搜索二维矩阵 | 当成一维有序数组做二分 |
| 240 | 搜索二维矩阵 II | 从右上角出发，O(m+n) |
| 54 | 螺旋矩阵 | 四个边界指针收缩 |
| 48 | 旋转图像 | 先转置再翻转 |
| 73 | 矩阵置零 | 用第一行第一列做标记 |

**口述模板（以 240 为例）**：

> "这道题的关键是找到一个合适的起点。矩阵每行从左到右递增、每列从上到下递增。如果从左上角出发，往右和往下都变大，没有排除方向。但如果从**右上角**出发，往左变小、往下变大——每次比较都能排除一行或一列。所以从右上角开始，target 大了就往下走，小了就往左走，时间复杂度 O(m+n)。"

#### 2. 二分查找类（本次面试也栽的题型）

**核心思路**：二分的关键不是"折半"，而是**"每次排除一半的搜索空间"**。写二分最容易错的是边界条件。

**万能模板**：

```python
def binary_search(nums, target):
    left, right = 0, len(nums) - 1
    while left <= right:
        mid = left + (right - left) // 2  # 防溢出
        if nums[mid] == target:
            return mid
        elif nums[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
    return -1
```

**变体模板（找左边界/右边界）**：

```python
# 找第一个 >= target 的位置（左边界）
def lower_bound(nums, target):
    left, right = 0, len(nums)
    while left < right:
        mid = left + (right - left) // 2
        if nums[mid] < target:
            left = mid + 1
        else:
            right = mid
    return left

# 找最后一个 <= target 的位置（右边界）
def upper_bound(nums, target):
    left, right = 0, len(nums)
    while left < right:
        mid = left + (right - left) // 2
        if nums[mid] <= target:
            left = mid + 1
        else:
            right = mid
    return left - 1
```

**必刷题**：

| 题号 | 题目 | 核心技巧 |
|------|------|----------|
| 704 | 二分查找 | 标准模板 |
| 35 | 搜索插入位置 | 左边界二分 |
| 34 | 在排序数组中查找元素的第一个和最后一个位置 | 左右边界各一次 |
| 33 | 搜索旋转排序数组 | 先判断哪半边有序 |
| 153 | 寻找旋转排序数组中的最小值 | 和右端点比较 |
| 162 | 寻找峰值 | 和相邻元素比较，往大的方向走 |

**口述模板（以旋转数组为例）**：

> "旋转数组的二分，核心是**每次判断哪半边是有序的**。取 mid 后，如果 nums[left] <= nums[mid]，说明左半边有序；否则右半边有序。然后在有序的那半边判断 target 是否在范围内——在就缩到那半边，不在就去另一边。这样每次都能排除一半，时间复杂度 O(log n)。"
