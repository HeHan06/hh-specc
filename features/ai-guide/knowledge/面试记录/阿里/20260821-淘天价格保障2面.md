## 复盘

本场是「价格保障 2 面」，面试官围绕服务零售 Agent 项目做了深挖，三个失分点都集中在"体系化表达"和"概念边界"上，不是项目本身没做过，而是没有按面试官能快速理解的结构讲出来。

- **运营指标**：答得散，没有先抛"分层体系 + 北极星指标"的总框架，导致面试官听下来像在报数，抓不住主线。
- **四象限**：原理理解是有的，但"为什么用时效性分"没讲透，且把"懒加载（长静态）"和"隔离压缩（长动态）"两套针对不同信息类型的策略讲混了，属于概念边界不清晰。
- **评测平台**：只讲了"做了个平台、能提效"，没有把"价值 / 意义 / 难点"拆开讲，尤其是"难点"部分缺了 LLM-as-Judge 准确率和机评成本这两个最能体现深度的点。

## 标准回复答案（口述版）

### Q1：你们 Agent 的运营指标是怎么设计的？

我把 Agent 的运营指标分三层来管，最上面挂一个北极星指标。

最顶层是**北极星指标**，也就是端到端体验分，这是产品从用户视角定义的"这次对话整体好不好用"。它分两块：客观的任务完成度，和主观的体验感受，另外用 GSB（更好/一样/更差）横向对比竞品和不同版本。

往下第二层是**业务环节层**，评估中间环节的文本生成效果。比如供给推荐看需求覆盖度和相关性、排序质量，预约预订看追问必要性和要素提取准确率。这层要兼顾客观项和业务需求。

再往下第三层是**算法层**，就是工具路由和参数提取。工具路由本质是个分类任务，我用准确率、召回率、F1，再加混淆矩阵来看哪些工具容易互相混淆，方便归因。最终做到了路由准确率 97%、参数提取准确率 96.6%。

除了这三层，我还会补两类横向指标：一类是**规模成本指标**，比如日均 30w 对话、单次输入 Token 从 70k 降到 1.5k、人机一致率从 40% 提到 90%；另一类是**稳定性指标**，用 Google 黄金四指标（延迟、流量、错误、饱和度）做大盘，配 P0/P1 分级告警，故障响应压到 5 分钟以内。

一句话总结：北极星指标牵引方向，算法层和业务环节层用来归因定位，稳定性和成本指标兜底。

### Q2：四象限为什么分"动态/静态"，懒加载和隔离压缩有什么区别？

四象限是用两个维度切上下文：**时效性（静态/动态）× Token 长度（长/短）**。先讲清这两个维度的原因，再讲清懒加载和隔离压缩的本质区别——你刚才说的"都沉淀成工具、自相矛盾"，其实是我之前没讲清"工具在这两种策略里的角色不一样"。

**为什么用时效性分？** 静态信息是"不随请求变化的固定内容"，加载时机可以提前定；动态信息是"随用户和请求实时变化的"，必须运行时注入。两类信息的失效风险和注入时机完全不同，治理动作也不同，所以要分开。

**为什么用 Token 长度分？** 长信息（几千上万 token）的主要矛盾是"占窗口、撑爆上下文"；短信息（几百 token）的主要矛盾是"被长文本淹没、注意力被稀释"。矛盾不同，解法就不同。

这里我要先纠正一个归类：**静态信息内部还要再分长短**，不能混为一谈。准确的四类是：

| | 静态 | 动态 |
|---|---|---|
| **长** | 大块固定规范：SOP、卡片总结规范（6000 token） | 历史沉淀资产：用户行为序列、历史订单、行业知识库 |
| **短** | 即时交互规约：人设、需求澄清话术 | 即时信息：实时位置、入口环境、用户画像 |

**关键澄清一：不是所有"提前定好的静态内容"都下沉工具层。** 短静态（人设、需求澄清话术）的处理是**固化**——直接写进 System Prompt 常驻，零延迟、强确定性，绝不下沉工具层。系统提示词的骨架（角色、能力、工具调用规范）也始终常驻。**只有"长静态"里那些体积大、又跟特定工具强绑定的大块规范**，才需要懒加载下沉。所以"系统提示词、SOP、卡片规范、人设话术"不是一锅端都去当工具，人设是固化、SOP 和卡片规范才是懒加载对象。

**关键澄清二：懒加载和隔离压缩虽然都"经过工具"，但工具的角色完全不同。**

- **懒加载（长静态）**：对象是**死规则**，内容固定不变。矛盾只是"默认全量注入太浪费"。做法是把规范拆解后**预先绑定到对应业务工具上**，模型调用该工具时，架构层把规范作为伴生注入。这里的工具是"**规则的载体/触发器**"，规则是预先挂载的、内容原封不动。核心是"内容不变，只解决何时注入"。

- **隔离压缩（长动态）**：对象是**活数据**，内容随用户实时变、噪声多。矛盾是"量大 + 每次要实时查 + 噪声多"。做法三招：压缩（只留关键节点）、隔离（不默认注入）、检索（RAG 召回）。这里的工具是"**数据源**"，工具调用是为了实时捞数据，捞回来还要裁剪降噪。核心是"内容要裁 + 要实时取"。

一句话区分：**懒加载是"把死的规则贴在工具上、调工具时跟着进来"，隔离压缩是"用工具实时捞活数据、捞完再裁"**。一个是"规则挂载工具"，一个是"工具查数据"，角色不一样，不矛盾。

### Q3：评测平台的价值、意义和难点分别是什么？

**价值我讲三层。**

第一层是**整合**。做平台之前，评测资产是散的——数据集、指标、测评诉求散落在产品和研发各自维护的文档和脚本里，每次跑评测要手工跑脚本、没法调度、也没法可视化。平台把数据集、评测 Agent、指标、任务统一管起来，大家能看清评测全貌。

第二层是**提效**。我把"数据回放→数据清洗→自动化评估→报告生成"这条固定流程标准化，做成一键式评估，研发不用每次自建一遍流程。结果是评测效率提升 70%，人工成本降低 50% 以上。

第三层是**质量兜底**。把自动化评测嵌入到日常数据回流里定时调度，让机评结果成为产品 UAT 的围栏，新需求和模型变更都能快速评测，避免上线后才发现问题。

**意义**在于把评测从"上线后补救"变成"评测驱动开发"，形成"上线→评估→归因→优化→再上线"的闭环飞轮。

**难点我总结四个。** 一是指标难定义，C 端意图开放、PMF 不清晰，主观体验没法用单一指标衡量；二是评测集难建，冷启动没真实数据，人工构造的 benchmark 分布容易和线上脱节，导致离线结论和线上表现对不上；三是 LLM-as-Judge 的准确率难保证，一开始人机一致率只有 40%，后面靠"主观评价优先 + 案例驱动校准"才拉到 90%；四是编排工程本身的复杂度。前三个是"评得准不准"，第四点是"能不能规模跑起来、跑得稳、跑得便宜"，我单独展开讲。

#### 难点四展开：编排工程的复杂度与解决方案

所谓编排复杂度，本质是**把评估从"一次性脚本"升级成"可规模化、可复现、可观测的生产系统"**。我先把选型逻辑讲清楚，再落到每个子问题的具体实现。

**先讲选型：核心是把"调度编排"和"执行编排"拆成两层，分别选型。**

这是最容易想当然、也最体现判断力的地方。评测平台其实是两种负载：

- **任务级调度**：什么时候跑、跑哪批、怎么定时——这是典型的**批处理调度**，DAG 建模，秒级短任务。
- **样本级执行**：单条数据"回放 → 清洗 → 评估 → 报告"——这是**长任务**，因为一次 LLM 评估要几十秒甚至分钟级，还带重试、动态分支。

如果拿一个引擎同时干两件事，一定别扭：Airflow 的 task 是短时批处理，把"一次 LLM 调用"建模成 task 会很重、调度开销盖过计算；Temporal 强在长时动态工作流，但纯拿它做定时批量又杀鸡用牛刀、运维成本高。

所以我的选型是：**调度层用轻量 DAG 调度（内部偏批量定时，Airflow/Celery Beat 这类就够），执行层用异步任务队列（Celery + Redis/RabbitMQ），单条样本跑成一个异步 task，靠状态机驱动**。判断依据就一条——评测 Agent 的调用是"几十秒的长 IO 任务"，异步队列天然匹配，而批量编排用 DAG 表达依赖最清晰。这层拆对了，后面四个子问题才有干净的落点。

**1. 执行模型：用状态机 + DAG 表达评估流水线。**

评估不是一条直线，而是一张有依赖、有分支的 DAG：数据加载 → 回放 → 清洗 → 评估（按指标类型分叉）→ 报告。具体实现上，每个环节是一个**幂等节点**：节点的输出落库、输入来自上游节点的产物，节点之间只靠产物 ID 传递，不靠内存。这样任意一个节点能单点重跑、能并行、能独立观测，改一个环节不用全量重来。

**2. 失败隔离与可恢复性，这是大规模最容易翻车的地方。**

每天上万条数据回放，单条失败绝对不能拖垮整个任务。三个具体实现：

- **失败隔离**：每条样本是队列里一个独立 task，失败就进**死信队列（DLQ）**，标记失败原因后单独重试，主干不受影响；
- **断点续跑**：样本级状态落库（pending / running / success / failed），挂了重启只捞 pending 和 failed，不从头再来、不重复计费；
- **幂等**：评估结果表用 `(dataset_version, agent_version, sample_id, metric_id)` 做唯一键，写入用 upsert 语义，重复触发直接覆盖，天然去重。

这三点合起来，才保证大规模评估"跑不死、不白烧钱"。

**3. 可观测性与血缘追踪（lineage）：给每个结果打上 provenance。**

每条评估结果必须能回溯到"它是用什么算出来的"：数据集版本、Agent 版本、prompt 版本、judge 模型、温度。实现上两种做法：轻量做法是结果表冗余存这些版本列，每次评估写一条带 `eval_run_id` 的记录；更彻底的做法是像 Dagster 那样把版本做成一等公民的 asset，自动追踪上游血缘。核心目的是一句话——**指标突然波动时，能立刻定位是数据变了、模型变了、还是评测逻辑变了**。没有血缘，评测结果就是一堆不可信的裸数字。

**4. 成本与吞吐：分层模型 + 缓存 + 采样。**

大规模机评的核心矛盾是成本，三个手段：

- **分层模型（cascade）**：便宜模型先跑粗筛并输出置信度，只有低置信度的边界 case 才上 SOTA judge 复核，避免所有样本都烧贵的模型；
- **缓存**：以 `hash(prompt + agent_version + sample)` 为 key 做 Redis 缓存，相同输入相同版本命中即返回，不重复评估；
- **采样**：先按意图类型分层抽样跑小样本判断趋势，趋势明确才全量，避免每次都全量烧钱。

收尾一句话：**编排复杂度的解法不是堆更多脚本，而是把评估当成生产系统来做——调度与执行分层选型、DAG + 状态机、幂等可重试、血缘可追溯、成本可控制。** 前三个难点决定"评得准不准"，第四个难点决定"这个平台能不能真正被团队依赖、长期跑下去"。
