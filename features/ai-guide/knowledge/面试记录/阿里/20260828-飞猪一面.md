### 话题1：Agent架构选型（简历事实 + 通识）

**简历事实**：基于ReAct模式，构建协调者+子智能体架构——协调者负责意图识别与任务规划，子智能体分管供给搜索、预约预订、交易履约。

**口述**：
我们的业务是服务零售C端导购，覆盖200+行业，从选店到履约是长链路。选 Multi-Agent（协调者+子智能体）主要基于三点：

1. **链路长、上下文杂**：全链路如果塞进单 Agent，system prompt 和工具列表会非常臃肿，模型容易在长对话里遗忘早期约束。
2. **各段工具集不同**：供给搜索、预约预订、交易履约各自需要不同的工具和上下文，拆成子智能体后每个 Agent 的职责单一、prompt 精简。
3. **团队边界匹配**：各子链路可由不同小组独立迭代和灰度。

通识上，方案对比可这样讲：
- 单 Agent + 工具调用：实现简单，但工具多了之后选择准确率下降、prompt 难维护。
- ReAct：思考-行动-观察循环，灵活但步骤不可控、token 消耗高（每步都带完整历史）。
- Plan-and-Execute：先规划再执行，步骤可控但不够灵活，中途变需求要重新规划。
- 我们的取舍：C端对话不可预测，主链路用 ReAct 的灵活性；而预订这类确定性流程，在子 Agent 内部用"先收集要素（商品/时间/人数）再执行预订"的类 Plan-and-Execute 思路。

（如果面试官问"协调者路由错了怎么办"，诚实回答：这是 Multi-Agent 的固有风险，我们靠评测集回归 + badcase 驱动来收敛路由准确率——简历里工具路由准确率 97% 就是这个指标。）

### 话题2：评测体系搭建（简历事实 + 通识）

**简历事实**：分层评估指标体系；自动化评测平台（数据集管理、任务编排、大模型自动化评估、报告生成）；LLM-as-Judge，结合主观评价优先与案例驱动校准；人机一致率 40%→90%。

**口述**：
评测体系我按"指标分层 + 平台自动化 + Judge 校准"三块讲：

1. **指标分层**：从业务目标到原子指标逐层拆。业务指标（转化率/满意度）反馈慢，能力指标（意图识别、工具路由、参数提取）和工程指标（成功率、延迟、token）可自动化。分层的好处是：任务完成率下降时，能逐层下钻定位到具体能力或工程问题。

2. **平台自动化**：数据集管理 → 任务编排 → 批量执行 → 自动评估 → 报告生成一条流水线。支持对比评测（同数据集跑两个版本出 diff）和回归门禁（发版前跑回归集，指标下降则阻断）。

3. **LLM-as-Judge 校准**：这是人机一致率能从 40% 提到 90% 的关键。
   - **评分维度细化**（通识）：不搞"整体打分 1-5"，而是拆成多个二元/三元判断（如"是否理解意图：是/部分/否"），二元判断的一致率远高于主观打分。
   - **案例驱动校准**（简历有）：用人工标注的标杆 case 做 few-shot 示例，让 Judge 模仿标注标准。
   - **主观评价优先**（简历有）：人工复核不一致 case，把结论沉淀回评分规则，持续迭代。

（如果追问"Judge 本身会不会偏"：诚实回答——会，所以用标杆样本做锚定、多模型交叉、人工抽检兜底。这一块属于通识补充，简历里没有具体落地，可直接说"这是我们正在持续优化的方向"。）

### 话题3：技师库存设计（简历事实，备用）

> 一面已答且反馈良好，此条仅作2面万一追问的兜底，不复述，只列简历关键事实点：
> - 5min 粒度时间片，单技师日 288 时间片
> - 64 进制压缩编码，将排班状态打入 ES 索引，TP99 < 100ms
> - 库存一致性四级保障：自动重试 + 延迟双写 + 每日全量同步 + 异常告警，一致率 100%
> - 领域模型：技师信息、排班计划、时间片库存、人货关系、订单归因；标准化 API（技师/排班/库存同步、下单/取消/改派），接入耗时 40PD→5PD
