# 第一部分：问题与标准答案

## 一、数据库

### Q1. MySQL 索引为什么用 B+ 树而不是 B 树？

**B+ 树相比 B 树的核心区别**：B+ 树所有数据都存在叶子节点，非叶子节点只存索引键；叶子节点之间用双向链表连接。

**为什么 MySQL 选 B+ 树**：

1. **范围查询效率高**：B+ 树叶子节点有链表连接，范围扫描只需找到起点然后顺序遍历链表即可。B 树数据分散在各层节点，范围查询需要中序遍历整棵树，会产生大量随机 IO。

2. **IO 次数更少**：B+ 树非叶子节点不存数据，单个节点能存更多索引键，树更矮。同样查一行数据，B+ 树可能 3 层就能覆盖，B 树可能要 4 层。

3. **查询稳定性**：B+ 树所有数据都在叶子节点，每次查询的路径长度完全一致。B 树的数据可能出现在任意层，最坏情况要到叶子节点，最好情况在根节点就能命中。

4. **磁盘预读友好**：B+ 树叶子节点连续存储，范围查询时磁盘顺序读取效率远高于随机读取。

**额外补充**：MySQL InnoDB 的主键索引（聚簇索引）叶子节点直接存整行数据，二级索引叶子节点存主键值。这也是为什么建议用自增 ID 做主键——可以避免页分裂，保证插入性能。

### Q2. MySQL 和 Redis 数据一致性怎么保证？

这是一个经典的缓存一致性难题，核心矛盾是：**缓存和数据库是两个独立存储，任何写入时序都无法绝对保证一致性**。

**标准方案：Cache Aside 模式（旁路缓存）**

- **读**：先读缓存，命中则返回；未命中则读数据库，写入缓存后返回
- **写**：先更新数据库，再删除缓存（为什么是删除而不是更新？因为更新缓存在并发下容易产生脏数据）

**延迟双删策略**：

```
1. 先删除缓存
2. 更新数据库
3. 延迟几百毫秒（比如 500ms）后再次删除缓存
```

延迟的目的是：防止在步骤 1 和 2 之间，有读请求把旧数据写回了缓存。

**最终一致性兜底方案**：

1. **Canal + MQ 异步同步**：监听 MySQL binlog，数据变更后通过 MQ 异步更新/删除 Redis 缓存。缺点是有一段时间窗口存在不一致。

2. **设置合理过期时间**：即使前面方案都出问题，缓存过期后也会重新加载最新数据，作为最后兜底。

3. **分布式读写锁**：对一致性要求极高的场景（如库存），写操作加排他锁，读操作检查版本号。

**实际回答要点**：先说明业界没有完美方案，再介绍 Cache Aside + 延迟双删 + binlog 同步 + 过期兜底的组合拳。面试官通常认可这个分层兜底的思路。

### Q3. 数据库分区分表怎么设计？分表键怎么选？

**分表 vs 分区**：
- **分区（Partition）**：单库单表，按规则拆成多个物理文件，对应用透明。适合数据生命周期管理（按时间清理历史数据）。
- **分表（Sharding）**：数据拆分到多个独立的物理表甚至多个数据库实例，应用层感知路由规则。适合海量数据水平扩展。

**分表键选择原则**：

1. **尽量让大多数查询带上分表键**：比如订单系统选 `user_id` 做分表键，那按用户查订单就走单表；但如果要按订单号查，就需要全表扫描或建映射表。
2. **避免跨分片事务**：同一个用户的数据落到同一个分片，下单、退款等事务就不会跨库。
3. **数据分布均匀**：避免热点分片。比如用 `user_id` 哈希取模通常比用时间范围要均匀。

**常见策略**：

| 策略 | 适用场景 | 示例 |
|---|---|---|
| 哈希取模 | 用户维度的均匀分布 | `user_id % 64` |
| 一致性哈希 | 动态扩缩容 | 减少扩容时的数据迁移量 |
| 范围分片 | 按时间归档 | 按月分表，历史数据归档 |
| 基因法 | 需要同时按多维度查询 | 订单号里嵌入 user_id 的哈希值 |

**扩容问题**：如果从 32 库扩到 64 库，取模规则变了，需要数据迁移。解决思路：
- 一致性哈希减少迁移量
- 停服迁移 + 双写切流
- 提前预留足够多的分片（比如一开始就分 512 个逻辑分片，物理上逐渐扩展）

## 二、缓存

### Q4. 缓存雪崩、缓存穿透、缓存击穿分别是什么？怎么解决？

**缓存雪崩**：大量缓存在同一时间点集中过期，或者 Redis 宕机，所有请求直接打到数据库。

**解决方案**：
- 过期时间加随机值：`TTL = 基准时间 + random(0, 300)秒`，避免集中过期
- 多级缓存（本地缓存 + Redis）
- Redis 集群 / 哨兵模式保证高可用
- 限流降级：数据库前加熔断器，被打垮前直接返回降级数据

**缓存穿透**：查询一个数据库中根本不存在的 key，缓存没有命中，每次请求都穿透到数据库。通常是恶意攻击（用不存在的 ID 刷接口）。

**解决方案**：
- **布隆过滤器**：把所有存在的 key 提前写入布隆过滤器，请求先过过滤器，不存在的直接拦截（有误判率，但不会漏判不存在的 key）
- 缓存空值：把"不存在"也缓存，值设为 null，TTL 设短一些（比如 1 分钟）
- 参数校验：ID 做合法性校验（比如负数、超长直接拒绝）

**缓存击穿**：某个热点 key 过期瞬间，大量并发请求同时打到数据库。

**解决方案**：
- 热点数据永不过期（或"逻辑过期"——key 不设 TTL，value 里带过期时间戳，读的时候判断）
- 互斥锁：第一个请求去查 DB，其他请求等待。用 Redis `SETNX` 实现分布式锁
- 异步刷新：后台线程提前刷新即将过期的热点 key

### Q4-补充. 热点 Key 如何设计？（Agent / 商品交易场景）

热点 Key 是指被大量并发请求频繁访问的某个缓存 key，常见于电商大促（爆款商品详情）、秒杀（库存 key）、Agent 系统（热门会话上下文）。设计核心在于**避免单点瓶颈，分散读写压力**。

**方案一：多级缓存 + 本地缓存**

```
请求 → 本地缓存(Caffeine/Guava) → Redis → DB
```

- 热点数据缓存在应用实例的本地内存中，比如商品详情、Agent 配置。读取延迟从毫秒级降到微秒级
- 本地缓存设置极短 TTL（如 1-3 秒），通过 Redis Pub/Sub 或配置中心推送变更通知刷新
- 适用场景：**读多写极少**的配置类数据

**方案二：Key 分片（Sharding）—— 拆热点**

将单一热点 key 拆成多个子 key，分散到 Redis 集群的不同分片：

```
stock:123 → stock:123:0, stock:123:1, stock:123:2, stock:123:3
```

- 写入时：均匀或按比例分配到各个子 key，总数为各子 key 之和
- 读取时：汇总各子 key 的值返回
- 拆分数量根据热点程度定，一般 4-16 个分片即可

**场景举例——秒杀库存扣减**（商品交易）：

```java
// 初始化：总库存 1000，均分到 4 个槽位
for (int i = 0; i < 4; i++) {
    redis.set("sku:123:stock:" + i, 250);
}

// 扣减库存：随机选一个槽位扣减
int slot = ThreadLocalRandom.current().nextInt(4);
Long remain = redis.decr("sku:123:stock:" + slot);
if (remain < 0) {
    redis.incr("sku:123:stock:" + slot); // 此槽位已空，回滚
    // 尝试其他槽位
}
```

**方案三：请求合并（Request Coalescing）**

对同一个 key 的大量并发请求，只让一个请求穿透到后端，其余等待结果：

```java
// 伪代码：用 CompletableFuture 做请求合并
ConcurrentHashMap<String, CompletableFuture<Object>> pending = new ...;

public Object get(String key) {
    CompletableFuture<Object> future = pending.get(key);
    if (future != null) return future.get(); // 等待已有请求的结果
    
    CompletableFuture<Object> newFuture = new CompletableFuture<>();
    pending.put(key, newFuture);
    try {
        Object result = loadFromDB(key); // 只有一个请求真正执行
        newFuture.complete(result);
        return result;
    } finally {
        pending.remove(key);
    }
}
```

**方案四：读写分离**

- 热点 key 写操作走主节点，读操作走从节点（Redis Cluster 副本）
- 有短暂的数据不一致窗口（主从复制延迟），需要业务可容忍

**Agent 场景的特殊考量**：

Agent 系统中 Session Context（对话上下文）是天然的热点——用户连续对话时同一个 sessionId 频繁读写：

- **按用户维度本地缓存**：用户级别的上下文缓存在 WebSocket 连接所在的服务器实例本地内存中，配合 Redis 异步双写做持久化和故障恢复
- **上下文分层**：高频访问的短期上下文用本地缓存，长期记忆走 Redis，历史归档走对象存储
- **降级策略**：缓存不可用时，降级为空上下文回复（告知用户"重新开始对话"）

**实践建议**：
1. 先通过监控识别热点 key（Redis `--hotkeys` 命令或 monitor 分析）
2. 优先用**本地缓存 + 短 TTL**，成本最低
3. 库存类热点 key 用**分片方案**
4. Agent 会话用**用户维度的本地缓存 + Redis 双写**

## 三、消息队列

### Q5. Kafka 的核心架构是什么？怎么保证消息不丢？

**核心概念**：
- **Topic**：消息的逻辑分类，可以理解为"消息的分类主题"
- **Partition**：Topic 的物理分区，每个 Partition 是一个有序、不可变的消息序列
- **Producer**：消息生产者，把消息写入指定 Topic 的指定 Partition
- **Consumer Group**：消费者组，组内每个消费者负责一个或多个 Partition，同一条消息只被组内一个消费者消费
- **Broker**：Kafka 服务节点

**为什么 Kafka 吞吐量高**：
- 顺序写磁盘（比随机写快几个数量级）
- 零拷贝（sendfile 系统调用，数据直接从磁盘到网卡，不经过用户态）
- 批量发送和压缩
- Page Cache 加速读取

**消息不丢的三端保障**：

| 端 | 配置/机制 | 说明 |
|---|---|---|
| Producer | `acks=all` | 等待所有 ISR（同步副本）确认才返回成功 |
| Producer | `retries=3` | 发送失败自动重试 |
| Broker | `min.insync.replicas=2` | 最少要有 2 个同步副本，保证冗余 |
| Broker | `unclean.leader.election.enable=false` | 不允许落后副本竞选 leader |
| Consumer | 手动提交 offset | 消息处理完再 commit，不自动提交 |

### Q6. 流量削峰怎么做？

电商大促场景下，瞬时流量可能是平时的几十倍，直接打崩系统。
验证码/答题 → CDN静态化 → Nginx令牌桶限流 → 前端排队页 → MQ削峰 → 后端消费 → Redis缓存 → DB + 熔断降级兜底

1. 验证码/答题

精髓是「把机器请求挡掉，把人的请求拉慢」。纯人机识别时，用户手动输入消耗 2-3 秒，天然就把瞬时并发脉冲打散了 —— 原本 1 秒内涌入的 10 万请求被摊平到几秒内分批到达。

2. CDN 静态化

精髓是「请求连服务器都不用到了」。商品详情、活动页等读多写少的内容推送到 CDN 边缘节点，用户就近访问。大促 90%+ 的流量在这一层被消化，后端几乎无感。

3. Nginx 令牌桶限流

精髓是「允许突发，但封顶总量」。令牌匀速生成，桶满则溢出（拒绝超额请求）。前面的验证码已经打散了脉冲，这一层是基于 QPS 的兜底——万一仍有流量尖刺，果断拒绝，保护下游。

4. MQ 削峰

精髓是「生产与消费的速率解耦」。请求快速写入 MQ 即返回受理成功，后端消费者按固定速率（如 1000 QPS）慢慢消化。MQ 起到了蓄水池的作用 —— 瞬时洪水进来，细水长流出去。

5. Redis 缓存

精髓是「数据库之前最后一道保护」。绝大多数商品信息、用户资料、库存数据都在 Redis 中（内存存储），读请求到 Redis 就返回，不碰磁盘。只有写入和极少数缓存 miss 才落到 DB。

8. DB + 熔断降级兜底

精髓是「宁可部分不可用，也不全挂」。如果连 DB 都快撑不住了，熔断器直接开路，拒绝所有新请求，返回降级结果（如「活动火爆，请稍后重试」）。等 DB 恢复后熔断器自动半开试探，逐步恢复全量。 停掉半边业务比全部宕机好。

### Q6-补充. Kafka 如何保证有序消费？如何保证数据一致性？

#### 一、有序消费

Kafka 的有序性是一个**分层保证**的设计：

**核心原理**：

- Kafka 只保证 **单个 Partition 内消息有序**（追加写，offset 递增）
- **多个 Partition 之间不保证顺序**
- 因此，有序消费的关键在于：**将需要有序的消息路由到同一个 Partition**

**实现方式**：

**1. 指定 Partition Key（推荐）**

```java
// 相同 key 的消息会打到同一个 Partition
producer.send(new ProducerRecord<>("order-topic", orderId, message));
//                                       topic      key      value
```

Kafka 默认用 `hash(key) % partitionCount` 决定 Partition。相同 key（如 orderId）的全部事件——创建订单、支付、发货、完成——都会进入同一个 Partition，消费时自然有序。

**2. 单 Partition Topic**

最彻底的方案：整个 Topic 只有一个 Partition，绝对有序。代价是完全丧失并行能力，吞吐量极低，只适合低频场景（如全局配置变更通知）。

**3. 消费端幂等 + 版本号兜底**

当消息可能乱序到达时（如重试、网络抖动），消费端通过业务手段保证最终一致：

```java
// 基于数据库版本号做乐观锁，防止旧状态覆盖新状态
UPDATE order SET status = 'paid', version = version + 1 
WHERE order_id = ? AND version = ?;  -- 版本号不匹配则更新失败，忽略旧消息
```

**4. 顺序消费的代价与权衡**

| 方案 | 吞吐量 | 有序性 | 适用场景 |
|---|---|---|---|
| Partition Key 路由 | 高（多个 key 并行） | 同 key 有序 | 订单事件流（同订单有序） |
| 单 Partition | 极低 | 全局有序 | 配置变更、全局计数 |
| 消费端版本号 | 高 | 最终有序 | 允许短暂乱序的场景 |
| 内存队列排序 | 中 | 窗口有序 | 消费后在内存按序号重排再处理 |

**商品交易场景实践**：订单事件用 `orderId` 做 Partition Key，保证同一笔订单的创建→支付→发货→完成严格有序。不同订单之间可以并行消费，整体吞吐量不受影响。

#### 二、数据一致性

Kafka 场景下的"数据一致性"主要有两个层面：

**层面 1：Producer → Broker 的一致性（不丢消息）**

已在 Q5 中覆盖：`acks=all` + `min.insync.replicas=2` + 禁止 unclean 选举。

**层面 2：Broker → Consumer 的一致性（消费幂等 + 事务）**

这是更常见的难点——消息不丢但可能重复消费。

**2.1 幂等消费（At-Least-Once → 业务幂等）**

Kafka 默认语义是 **At-Least-Once**（至少一次），即消息可能被重复投递（如 rebalance、手动提交 offset 失败后重试）。需要消费端实现幂等：

```java
// 方案一：数据库唯一键去重
// 把 msgId 作为唯一键写入去重表，插入成功才执行业务逻辑
INSERT INTO msg_consumed (msg_id) VALUES (?);  // 重复消息插入失败，跳过

// 方案二：Redis 去重
// 消费前 SETNX msg_id，设置成功才处理
Boolean firstTime = redis.setnx("msg:" + msgId, "1");
redis.expire("msg:" + msgId, 3600);  // 过期自动清理
if (!firstTime) return;  // 已处理过，忽略

// 方案三：业务天然幂等
// 比如「订单状态更新为已支付」本身就是幂等的
UPDATE order SET status = 'paid' WHERE order_id = ? AND status != 'paid';
```

**2.2 Kafka 事务（Exactly-Once Semantics）**

Kafka 0.11+ 支持事务，实现"生产-消费-处理-生产"的端到端精确一次：

```java
// 生产者事务：多条消息原子写入
producer.initTransactions();
producer.beginTransaction();
producer.send(new ProducerRecord<>("topic-A", msg1));
producer.send(new ProducerRecord<>("topic-B", msg2));
producer.commitTransaction();  // 要么全部成功，要么全部回滚

// 消费者事务（消费-转换-生产模式）
// 需配置 isolation.level=read_committed，只消费已提交的事务消息
```

**事务的代价**：吞吐量下降约 20-30%（需要额外的协调日志），且跨 Topic 事务增加延迟。大多数业务场景不需要 Kafka 事务，**业务幂等 + 手动提交 offset** 足够覆盖。

**2.3 手动提交 Offset 的坑**

```java
// 错误做法：自动提交（可能丢消息）
props.put("enable.auto.commit", "true");  // 拉取后立即提交，处理失败也无法回退

// 正确做法：手动提交 + 先处理后提交
props.put("enable.auto.commit", "false");
while (true) {
    ConsumerRecords records = consumer.poll(Duration.ofMillis(100));
    for (record : records) {
        processBusiness(record);  // 先处理完业务逻辑
    }
    consumer.commitSync();  // 处理成功后再提交 offset
}
```

注意：先提交后处理会丢消息（提交成功但处理失败），先处理后提交可能导致重复消费（处理成功但提交失败）。需要幂等来兜底。

**一致性全景总结**：

```
Producer 端          Broker 端              Consumer 端
  acks=all    →    ISR 多副本    →    手动提交 offset
  retries           unclean=false        业务幂等（唯一键/状态机）
  idempotent                               Kafka 事务（按需）
```

三者缺一不可：Producer 保证消息不丢地到达 Broker，Broker 保证多副本持久化，Consumer 保证准确不重复地处理。

## 四、并发编程

### Q7. 线程池的核心参数有哪些？怎么合理配置？

**ThreadPoolExecutor 七个参数**：

```
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 空闲线程存活时间
    unit,              // 时间单位
    workQueue,         // 等待队列
    threadFactory,     // 线程工厂
    rejectedHandler    // 拒绝策略
)
```

**工作流程**：新任务来 → 核心线程满没满？没满就新建线程 → 满了就放入等待队列 → 队列满了就创建非核心线程（直到 maximumPoolSize）→ 全满了就走拒绝策略。

**四种拒绝策略**：

| 策略 | 行为 | 适用场景 |
|---|---|---|
| AbortPolicy（默认） | 抛 RejectedExecutionException | 需要感知拒绝的场景 |
| CallerRunsPolicy | 由提交任务的线程自己执行 | 减缓提交速率 |
| DiscardPolicy | 静默丢弃 | 可有可无的任务 |
| DiscardOldestPolicy | 丢弃队列中最旧的任务 | 优先处理最新任务 |

**参数配置经验**：

- **CPU 密集型**：`corePoolSize = CPU 核数 + 1`，线程多了频繁上下文切换反而慢
- **IO 密集型**：`corePoolSize = CPU 核数 * 2` 或更多，因为线程大部分时间在等 IO
- **混合型**：拆成两个线程池分别处理

**实际经验**：不要迷信公式，根据压测和监控调。关注指标：活跃线程数、队列积压数、拒绝次数、任务平均等待时间。

### Q8. ThreadLocal 的使用场景和内存泄漏问题？

**原理**：每个线程内部有一个 `ThreadLocalMap`，key 是 ThreadLocal 的弱引用，value 是存的值。同一个 ThreadLocal 对象在不同线程中取到的是各自的值。

**使用场景**：
- **链路追踪**：在拦截器里把 traceId 放入 ThreadLocal，后续所有日志都自动带上，无需显式传参
- **数据库事务**：Spring 的事务管理器用 ThreadLocal 存当前线程的数据库连接，保证同一个事务内用同一个连接
- **日期格式化**：SimpleDateFormat 线程不安全，用 ThreadLocal 给每个线程持有一个实例，避免加锁
- **用户上下文传递**：拦截器解析 token 后把用户信息放入 ThreadLocal，controller 和 service 直接取用

**内存泄漏原因**：

ThreadLocalMap 里的 Entry 的 key（ThreadLocal 对象）是**弱引用**，但 value 是**强引用**。当 ThreadLocal 对象被 GC 回收后，key 变成 null，但 value 依然被 Entry 强引用着，只要线程还活着（比如线程池的线程），value 永远不会被回收。

**解决方案**：
1. **用完手动 remove()**：在 finally 块中调用 `ThreadLocal.remove()`。最佳实践：在拦截器的 afterCompletion 里清理
2. **try-finally 保证清理**：
   ```java
   try {
       threadLocal.set(value);
       // 业务逻辑
   } finally {
       threadLocal.remove();
   }
   ```

**面试加分点**：提到线程池场景下尤其容易出现内存泄漏，因为线程池线程复用，不会销毁，ThreadLocal 值一直存着。

## 五、RPC 框架

### Q9. Dubbo 的通信协议是什么？RPC 和 HTTP 什么区别？

**Dubbo 支持的协议**：
- **dubbo://**（默认）：基于 Netty + TCP 长连接 + 自定义二进制序列化（Hessian2）。适合小数据量高并发的服务间调用
- **tri://**（Triple，Dubbo 3.0+）：基于 HTTP/2 + Protobuf，兼容 gRPC 协议，支持流式调用
- **rest://**：基于 HTTP + JSON，面向浏览器/移动端
- 还支持 Hessian、Redis、Thrift 等

**Dubbo 协议特点**：
- 单一长连接：消费者和提供者之间只建一条 TCP 长连接，适合小数据量高频调用
- NIO 异步通信：Netty 实现，线程利用率高
- 自定义协议头：只有 16 字节 header，比 HTTP 协议头小很多

**RPC vs HTTP**：

| 维度 | RPC（Dubbo） | HTTP（REST） |
|---|---|---|
| 协议 | TCP 长连接 + 二进制序列化 | HTTP(S) + JSON/XML |
| 性能 | 高（二进制、长连接、少序列化开销） | 较低（文本协议、每次建连开销） |
| 契约 | 通过接口定义 + 注册中心强类型约束 | 松散，靠文档约定 |
| 适用场景 | 内部微服务间高频调用 | 对外 API、浏览器、跨语言互调 |
| 服务治理 | 内置负载均衡、熔断、限流、注册发现 | 需要外部网关（Kong/Nginx）补充 |
| 通信模型 | 同步/异步/future/callback 多种模型 | 主要是请求-响应 |

**选型建议**：内部微服务间用 RPC（Dubbo/gRPC），对外 API 用 HTTP（RESTful）。

---

### Q10. 为什么 Dubbo 默认用单一长连接？

1. **服务提供者数量少**：一个服务通常只有几个到几十个实例，长连接不够成瓶颈
2. **消费者数量可能很多**：如果每个消费者和维护多个连接，提供者端的连接数爆炸
3. **请求量分散**：Dubbo 默认每个请求都小，用连接池反而不划算
4. **连接是有成本的**：每个连接占用文件描述符、内存和心跳维护开销

**何时用多连接**：如果单个服务实例之间需要传输大量数据（比如文件传输），可以配置 `connections` 参数增加连接数。
