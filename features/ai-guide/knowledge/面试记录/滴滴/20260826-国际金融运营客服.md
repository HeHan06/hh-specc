### 1. Agent 一次对话 API 调用完整流程：表达不够清晰

**复盘分析**

你简历里写的是"Multi-Agent 架构 + ReAct 模式"，但被要求"完整讲一遍一次对话经过哪些 API 调用"时，你讲得零散。根因是：平时只关注"某一块的实现"，没有把**端到端的数据流**串成一条线。面试官要的是"从用户输入到最终回复，中间每一跳发生了什么、调用了几次 LLM、消耗了多少 token、哪些环节可控"，这是 Agent 岗的送分题，必须能一口气讲清楚。

**标准口述答案（结合简历里的美团 C 端导购 Agent）**

> 我以美团服务零售 C 端导购 Agent 为例，讲一次完整对话的端到端流程。核心是 ReAct 模式下的「协调者 + 子智能体」架构，一次对话通常包含多个"思考→行动→观察"的循环：
>
> **第一跳：请求接入与上下文组装。** 用户 query 进来后，先做上下文治理——这是我最熟的一块。我主导了三阶段演进：全量堆砌 → 隔离精简 → 动态增补，把单次 Token 从 70k 降到 1.5k。这一步是"喂给模型什么"的问题，直接决定后续每一跳的成本和效果。
>
> **第二跳：query 改写（或叫 query 规范化）。** 把用户口语化、多轮指代、错别字的原始输入，改写成一个下游意图识别和检索更好处理的标准 query。（必要性见第 2 点）
>
> **第三跳：意图识别 + 任务规划（协调者）。** 协调者（主 Agent）根据改写后的 query，识别用户意图（选店 / 选品 / 预约 / 交易），并拆解成子任务。这里调用一次 LLM 做规划。
>
> **第四跳：工具路由 + 参数提取。** 根据规划出的子任务，把请求路由到对应的子智能体（供给搜索、预约预订、交易履约），同时完成工具参数的提取。简历里工具路由准确率 97%、参数提取准确率 96.6% 就是这个环节的指标。
>
> **第五跳：子智能体执行（调用工具）。** 子智能体调用实际工具（商品召回、库存查询、下单接口），拿到结构化结果。这里是真实业务接口调用，不是 LLM 调用。
>
> **第六跳：结果聚合与回复生成。** 协调者汇总各子智能体的返回，再做一次 LLM 调用，生成面向用户的自然语言回复。
>
> 所以一次对话，LLM 调用通常是「规划 1 次 + 各子任务若干次 + 汇总 1 次」，中间穿插真实工具调用。优化点在于：通过上下文精简降低每跳 Token，通过并行化子智能体调用降低总耗时，通过工具路由和参数提取的高准确率减少无效 LLM 重试。

### 2. 引入 query 改写的必要性：没想清原因

**复盘分析**

你只知道"要做 query 改写"，但说不出"为什么必须做"。这是典型的"记住了结论、没建立因果"。答这类题的正确姿势是**反证法**：先问"如果不改写，直接用原始 query 会怎样？"——把后果列出来，必要性自然就成立了。

**标准口述答案**

> 引入 query 改写，本质是把"用户非结构化的原始输入"转成"下游模型/检索能精准处理的规范输入"。我从"不改写会怎样"三个后果反推必要性：
>
> **第一，口语化、错别字会拖垮意图识别。** 用户说"帮我找个周末能唱歌的地儿"，不是"KTV 门店检索"。原始口语直接喂给意图识别，容易误判。改写把它规范成标准表达，意图识别准确率才上得去。
>
> **第二，多轮对话的指代消解。** 用户第一轮问"有没有足疗店"，第二轮只说"那家近不近"，"那家"指的是谁？不把前文上下文补进来做指代消解，第二轮就完全没法处理。query 改写要负责把"那家"还原成具体门店。
>
> **第三，提升检索/工具调用的召回率。** 原始 query 词面杂、噪声多，直接做检索召回率低；改写后做归一化、同义词扩展，能让供给搜索、商品召回更准。
>
> 所以必要性一句话：**query 改写是连接"用户自然语言"和"下游结构化处理"的桥，不写这条桥，后面的意图识别、工具路由、参数提取全都建立在噪声输入上，准确率上不去。** 这在美团导购场景里尤其关键，因为服务零售覆盖 200+ 行业，用户表达高度口语化、长尾化。

### 3. 分库分表：键选 user_id 答错，且没答出"按订单号查用户订单"的解法

**复盘分析**

这是本次最典型的基本功失分。订单场景分库分表，你第一反应选了 `user_id` 作分片键，说明没有先分析**订单业务的读写模型**。订单系统的核心是：下单、按订单号查单、按用户查订单列表、商家侧查订单。选键的本质是"把最高频的查询路由到单库，避免跨库扫表"。这个题还有一个必考的追问——"用订单号分片，那查某用户所有订单怎么办"，标准解法是**基因法（订单号里嵌入 user_id 基因）**，你完全没接上。

**标准口述答案**

> 订单场景我推荐用 **`order_id`（订单号）作为分片键**，而不是 user_id。原因是订单系统最高频的读写是"按订单号定位单笔订单"（下单、支付回调、查单、退款），用 order_id 分片能让这些请求只路由到一个库，不用扫全库。user_id 分片的问题在于：支付回调、退款、第三方对账往往只有订单号、没有用户 id，按 user_id 分片会导致这些请求不知道去哪个库，被迫广播查询所有分片，性能灾难。
>
> 那"按用户查他所有订单"怎么办？这恰恰是 order_id 分片的代价，有三种解法：
>
> **第一，基因法（最推荐）**：下单生成 order_id 时，把 user_id 的"基因"（比如 user_id 取模分片数的后几位）编码进 order_id。这样 order_id 和 user_id 落在同一个分片，按 user_id 查订单时，从 user_id 推算出分片号，直接去那一个库查，不用扫全库。这是大厂订单系统的经典做法。
>
> **第二，建"用户→订单"映射表**：单独一张 `user_order` 表按 user_id 分片，存 user_id → order_id 列表，查订单时先查映射表拿 order_id，再去对应库取详情。
>
> **第三，用 ES 建用户维度索引**：订单详情按 order_id 存 MySQL，同时冗余一份到 ES 按 user_id 维度建索引，用户订单列表走 ES 查询。
>
> 核心认知：**分片键要选"最频繁、最需要单库路由"的那个维度，其他维度的查询用基因法或冗余索引来补**，没有完美只靠一个键就覆盖所有查询的方案。

### 4. 分布式事务：解决方案和替代方法不清楚

**复盘分析**

分布式事务是一个成体系的知识点，你答得零散，说明没有按"强一致 → 最终一致"的谱系梳理过。面试官问"如何解决和替代"，其实是在考察两层：一是知道有哪些方案，二是知道**工程上通常不用强一致方案，而用"最终一致 + 消息"来替代**。

**标准口述答案**

> 分布式事务方案我按"强一致到最终一致"的谱系梳理：
>
> **强一致类：**
> - **2PC / XA**：数据库层两阶段提交，强一致但性能差、有阻塞和单点问题，互联网高并发场景基本不用。
> - **TCC（Try-Confirm-Cancel）**：业务层两阶段，Try 预留资源、Confirm 确认、Cancel 回滚。一致性强但业务侵入大，每个操作都要写三个接口。
> - **SAGA**：长事务拆成多个本地事务，靠补偿操作回滚。适合跨多个服务的长时间流程。
>
> **最终一致类（工程主流）：**
> - **本地消息表 + MQ**：本地业务和"写消息表"放在同一个本地事务里提交，后台任务扫描消息表投递 MQ，消费方幂等消费。可靠、简单，是美团/大厂订单场景最常用的方案。
> - **事务消息（RocketMQ 半消息）**：消息先发半消息、等本地事务提交后再确认投递，省去自己扫表的麻烦。
> - **最大努力通知 / 对账补偿**：实在保证不了的，用对账兜底，定期比对两边的数据做补偿。
>
> **替代思路（面试官问"替代"时重点答这个）**：分布式事务能不碰就不碰。第一优先是**通过设计规避**——能合并到单个服务/单库操作的就不拆；其次是**最终一致性**：用「本地消息表 + MQ + 幂等 + 对账」这套组合替代强一致的 2PC，用"最终一致"换"高可用和高吞吐"。强一致只留给真正不能容忍中间态的金融核心（转账、扣款），而且即使金融也优先用 TCC 而非 2PC。

### 5. CI 到上线前（大促场景）的稳定性保障：没有系统讲清

**复盘分析**

你答得零散（压测、告警各说一点），是因为没有用一个**时间轴框架**把稳定性工作串起来。面试官要的是"从 CI 到上线前，大促场景，完整的稳定性保障"，标准答法就是按"**上线前准备 → 上线中保障 → 应急兜底**"三个阶段系统铺开，每个阶段落到可执行的动作，而不是报菜名。简历里"上线 0 P0 事故、灰度开关、一键回滚、P0/P1 分级告警、监控大盘"这些素材你都有，就是没组织成体系。

**标准口述答案（结合简历）**

> 大促稳定性保障，我按"上线前 → 上线中 → 应急"三个阶段来讲：
>
> **一、上线前（准备期）**
> 1. **容量评估与扩容**：根据预估峰值 QPS，对下游依赖（Redis、MySQL、Kafka、三方接口）做容量评估，提前扩容。
> 2. **全链路压测**：模拟大促峰值流量做压测，找出瓶颈，验证限流阈值和降级开关是否有效。
> 3. **缓存预热**：把热点商品、榜单、配置提前加载进 Redis/Caffeine，避免大促瞬间冷启动击穿（呼应 Redis 那套缓存体系）。
> 4. **限流、降级、熔断、隔离**：核心链路配限流，非核心链路配降级，依赖方故障配熔断，资源配隔离（线程池、连接池隔离）。
>
> **二、上线中（发布与观察期）**
> 1. **灰度发布**：我在美团就是通过灰度开关控制功能启用，先小流量、再逐步放量，有问题能一键回滚——这是我"上线 0 P0 事故"的关键手段。
> 2. **监控告警大盘**：上线前就把核心指标（QPS、TP99、错误率、上下游依赖）接入监控大盘，配好 P0/P1 分级告警，确保故障能被第一时间发现。
>
> **三、应急兜底**
> 1. **应急预案 + 一键降级/回滚**：提前定义好每个故障场景的应对动作（哪个开关降级、怎么回滚），保证出事时不用现想。
> 2. **故障演练**：大促前做一次真实演练，验证告警能触发、预案能执行。
>
> 一句话总结：**大促稳定性 = 上线前的容量/压测/预热 + 上线中的灰度/监控 + 应急的预案/回滚**，三阶段缺一不可。核心是用"灰度 + 监控 + 一键回滚"兜住不确定风险。
