### 二、Agent 相关深度问题

#### Q1：Excel 为什么使用向量库不好？

> 这个问题要从 Excel 的数据特征和向量检索的匹配逻辑来讲。
>
> Excel 数据有几个特点：第一，它是高度结构化的表格数据，每一列有明确的字段含义，比如"销售额"、"日期"、"地区"，这些字段之间的关联关系是精确的，不是语义层面的模糊匹配。第二，Excel 里大量的查询是聚合类的，比如"去年 Q3 华东区的总销售额是多少"，这类问题需要的是精确的列名匹配加 SQL 聚合计算，而不是语义相似度。
>
> 而向量库的核心能力是语义相似度检索，它把文本 embedding 成向量后，用余弦相似度或欧氏距离来找最相似的片段。这个思路在 Excel 场景下有三个问题：
>
> 一是**语义漂移**：比如用户问"销售额"，向量检索可能把"利润"、"毛利"也召回，因为它们语义相近，但实际上在 Excel 里这是三个不同的列，不能混淆。
>
> 二是**数值精度丢失**：向量 embedding 对数值不敏感，比如"100万"和"101万"在向量空间里可能非常接近，但对查询来说就是两个不同的结果。
>
> 三是**聚合逻辑无法覆盖**：向量检索只能返回相似的文本片段，做不到 sum、count、group by 这些结构化操作。
>
> 所以 Excel 场景更合适的方案是 **Text-to-SQL** 或者 **Table QA** 路线，比如用大模型把自然语言转成 SQL 或 Pandas 操作，直接对结构化数据做精确查询。向量库更适合非结构化文档比如 PDF、Word 这些场景。

#### Q2：语义检索实现原理，除了余弦相似度还有什么？

> 余弦相似度是文本语义检索里最常用的，但它只是其中一种相似度度量方式。整个语义检索从原理上分几个层面：
>
> **相似度度量层面**，除了余弦相似度，还有：
> - **欧氏距离（L2）**：在 FAISS 里配合 IndexFlatL2 使用，对向量绝对位置敏感，适合 embedding 已经做过归一化的场景。
> - **内积（IP）**：向量点积，适合 embedding 没有归一化但希望计算方向一致性的场景，比如某些对比学习产出的 embedding。
> - **曼哈顿距离（L1）**：在高维稀疏向量中偶尔使用，但语义检索场景不常见。
>
> **检索策略层面**，不止是简单的 ANN 近似最近邻：
> - **倒排索引 + 量化**：比如 FAISS 的 IVF（Inverted File）加 PQ（Product Quantization），先把向量空间聚类分桶，检索时只搜最近的几个桶，再用乘积量化压缩向量，大幅减少内存和计算量。
> - **HNSW（Hierarchical Navigable Small World）**：分层图索引，构建多层跳表结构的图，上层做粗粒度导航，下层做精细搜索，是当前召回率和速度平衡最好的算法之一，Milvus 默认就是用这个。
> - **LSH（局部敏感哈希）**：用哈希函数把相似向量映射到同一个桶，适合超高维稀疏场景，但精度不如 HNSW。
>
> **更上层的检索优化**：
> - **混合检索（Hybrid Search）**：把语义检索和关键词检索（BM25）的结果做融合，比如用 RRF（Reciprocal Rank Fusion）加权合并，兼顾语义和精确匹配。
> - **重排序（Rerank）**：ANN 粗召回后，用 Cross-Encoder 模型对候选集做精排，提升 top-k 的准确率。
>
> 实际工程中，选什么方案取决于数据规模和延迟要求。百万级数据用 HNSW 就够了，千万级以上就要考虑 IVF+PQ 做压缩。

#### Q3：不同业务的 RAG 选型怎么考虑？

> 我会从四个维度来评估一个业务场景适合什么 RAG 方案：**数据类型、查询模式、准确率要求、延迟要求**。
>
> **第一类：非结构化文档问答（比如 PDF、Word 知识库）**
> 这是最经典的 RAG 场景。数据是非结构化的长文本，查询是开放式问题。方案选型：文档解析（Unstructured / PyPDF）→ 文本分块（固定大小或用语义分块）→ Embedding（BGE / text2vec 等中文模型）→ 向量库（Milvus / FAISS）→ 召回 + 大模型生成。这个链路成熟，效果稳定。
>
> **第二类：结构化数据问答（比如 Excel、数据库表）**
> 就是我刚才说的 Excel 场景。核心矛盾是语义检索解决不了精确匹配和聚合计算。方案选型：Text-to-SQL 或者用 Pandas Agent，让大模型生成可执行代码去操作数据，而不是用向量去搜。可以用少量的 few-shot 示例来提升 SQL 生成准确率。
>
> **第三类：多模态检索（比如图片、图表）**
> 如果文档里有大量图片和图表，纯文本 embedding 就不够用了。要考虑多模态 embedding 模型（比如 CLIP），把图片和文本映射到同一个向量空间，支持以文搜图。同时文档解析环节要保留图片位置信息，方便生成答案时引用。
>
> **第四类：实时性要求高的场景（比如客服、金融风控）**
> 查询延迟要控制在毫秒级。方案上要做几层优化：向量索引选 HNSW 而不是暴力搜索；embedding 模型选轻量级的（比如 BGE-small）；加一层缓存，热点问题直接返回缓存结果；必要时用小型微调模型做本地部署，减少网络调用延迟。
>
> **第五类：高精度要求场景（比如医疗、法律）**
> 召回率优先于速度。要用混合检索（BM25 + 向量），加 Rerank 精排，甚至做多路召回（不同分块策略 + 不同 embedding 模型）然后合并去重，确保不会漏掉关键信息。同时要做引用溯源，每条答案都能追溯到原文片段。
>
> 总结来说，选型没有银弹，一定是根据业务的数据特征和查询需求来组合方案。

#### Q4：BM25 算法实现原理，与类似算法的区别？

> BM25 是经典的基于词频的概率检索模型，它是 TF-IDF 的改进版。我先讲核心公式，再对比类似算法。
>
> **核心公式**：BM25 的得分由三部分组成：
>
> 第一部分是 **IDF 逆文档频率**：`IDF(qi) = log((N - n(qi) + 0.5) / (n(qi) + 0.5) + 1)`，这和 TF-IDF 的 IDF 类似，衡量一个词在整个文档集里的稀缺程度。词越稀有，IDF 越高。
>
> 第二部分是 **TF 词频饱和度**：`TF(qi, d) = (f(qi, d) * (k1 + 1)) / (f(qi, d) + k1 * (1 - b + b * (|d| / avgdl)))`。这里有两个关键参数——k1 控制词频的饱和度，一般来说 k1 在 1.2 到 2 之间，意思是词频到了一定程度后，再多次出现也不加分了，这点和 TF-IDF 里词频线性增长完全不同。b 控制文档长度归一化的程度，b 在 0 到 1 之间，通常取 0.75，b 越大，长文档越吃亏。
>
> 第三部分是**查询词权重**，如果查询本身有多个词，可以给每个词加权。
>
> **和 TF-IDF 的区别**：TF-IDF 是最简单的向量空间模型，TF 是线性增长的，也没有文档长度惩罚。BM25 在此基础上做了两个关键改进：一是 TF 饱和，避免了长文档里某个词重复几十次导致分数虚高的问题；二是文档长度归一化，让短文档和长文档在同一水平线上比较。在实际检索效果上，BM25 显著优于 TF-IDF。
>
> **和 BM25F 的区别**：BM25F 是 BM25 的多字段扩展，适用于文档有多个字段（比如标题、正文、摘要）且每个字段权重不同的场景。公式上它会分别计算每个字段的 BM25 分然后加权求和，而不是把整个文档当一个字段。
>
> **和向量语义检索的区别**：这是本质区别。BM25 是基于词频统计的**稀疏检索**，它只能匹配精确的词，理解不了"汽车"和"轿车"是同义词。向量检索是基于 embedding 的**稠密检索**，可以捕捉语义相似性。所以实际工程中通常把两者结合做混合检索：BM25 保证精确匹配（比如产品型号、编号），向量检索补上语义泛化能力。

#### Q5：如何从大模型层面提高模型速度？

> 从大模型层面提速度，核心思路是**减少计算量**和**优化计算过程**，我分几个方向来谈：
>
> **第一，模型量化（Quantization）**：把模型参数从 FP16 降到 INT8 甚至 INT4，计算量直接砍半甚至降到四分之一。比如用 GPTQ 或 AWQ 做训练后量化，GGUF 格式配合 llama.cpp 做 CPU 推理。量化会有精度损失，但 INT8 的损失基本可以忽略，INT4 在大多数场景下也够用。
>
> **第二，KV Cache 优化**：这是推理阶段最大的瓶颈之一。随着对话变长，KV Cache 的显存和计算量线性增长。优化方案包括：**GQA（Grouped Query Attention）**，多个 query head 共享一组 KV head，减少 KV Cache 大小；**PagedAttention**，把 KV Cache 分页管理，类似操作系统的虚拟内存，vLLM 就是基于这个实现的，吞吐量能提升几十倍；**FlashAttention**，通过算子融合和分块计算减少显存读写，把 attention 计算从 O(n²) 的显存占用降到 O(n)。
>
> **第三，投机推理（Speculative Decoding）**：用一个小的 draft 模型（比如 1B）快速生成多个候选 token，然后用大模型做一次并行验证，如果 draft 对了就一次性接受多个 token，相当于一次生成多个 token，显著降低延迟。这个在低延迟场景下效果很好。
>
> **第四，算子融合和编译优化**：用 TensorRT-LLM 或者 vLLM 做推理引擎，把多个算子融合成一个 kernel，减少 kernel launch 开销。配合 CUDA Graph 消除 CPU-GPU 同步等待。
>
> **第五，模型架构层面**：选 MoE（Mixture of Experts）架构的模型，比如 Mixtral，每次推理只激活部分专家，参数总量大但计算量小。或者用更小的模型配合长上下文窗口，减少模型本身的计算量。
>
> 实际落地时，我一般优先用量化加 vLLM 部署，这两步就能把速度提上来一大截，然后再根据延迟要求决定要不要上投机推理。

#### Q6：了解模型微调吗？

> 了解的，微调是让通用大模型适配特定业务场景的核心手段。我主要从三种主流微调方式来谈：
>
> **第一，全量微调（Full Fine-tuning）**：更新模型所有参数，效果最好但成本最高，需要大量的显存和高质量标注数据。一般只有在大规模业务场景下才值得做，比如要训练一个特定领域的代码模型或者医疗模型。
>
> **第二，LoRA（Low-Rank Adaptation）**：这是目前最主流的高效微调方式。核心思想是不动原始模型参数，而是在每一层的权重矩阵旁边加一个低秩矩阵（A×B），只训练这个低秩矩阵。参数量通常是原始模型的 0.1% 到 1%，显存需求大幅降低，单张消费级显卡就可以做。训练完成后可以把 LoRA 权重合并回原模型，推理时没有额外开销。我实际项目中用 QLoRA 比较多，它在 LoRA 基础上加了 4-bit 量化，进一步降低了显存门槛。
>
> **第三，其他高效微调方法**：比如 **Adapter**，在 Transformer 层之间插入小型网络层，只训练这些插入层；**Prefix Tuning** 和 **P-Tuning**，在输入层前面加可训练的虚拟 token，适合指令微调场景。这些方法参数量更少，但效果一般不如 LoRA。
>
> **微调的数据准备**也很关键，需要构造高质量的指令数据集，格式是 instruction-input-output 三元组。数据量方面，LoRA 用几千到几万条高质量样本就够了，全量微调可能需要十万级别。
>
> **实际经验**：如果要做垂直领域的知识注入，微调不是首选，RAG 更灵活且成本更低。微调更适合做**行为对齐**——比如让模型学会特定风格的输出格式、遵循特定的指令规范、或者学会某种分类/抽取任务。

### 三、Coding 题

**题目**：一个主字符串，一个子字符串列表，找到最长匹配主串的子字符串。

**题目理解**：给定一个主字符串 `S` 和一个字符串列表 `words`，找出 `words` 中能作为 `S` 的子串出现的、长度最长的那个字符串。

**最优解思路**：这道题最优解是 AC 自动机（Aho-Corasick）。AC 自动机是 Trie 树 + KMP 失败指针的结合，可以在 O(n + m) 的时间内完成多模式串匹配，其中 n 是主串长度，m 是所有模式串长度之和。

**标准口述**：

> 这道题我给一下最优解思路，用 AC 自动机来做。
>
> 首先分析问题：给定一个主串 S 和一个模式串列表 words，需要找到 words 中在 S 里出现过的、长度最长的那个字符串。如果多个长度相同，返回任意一个。
>
> 暴力解法是对每个 word 做一次 KMP，时间复杂度 O(n * k + sum(len))，其中 k 是 words 的数量。在模式串很多的情况下效率不高。
>
> 最优解是用 AC 自动机，它本质上是 Trie 树加 KMP 失败指针的结合。具体步骤：
>
> 第一步，把所有 words 构建成一棵 Trie 树，每个节点记录从根到该节点的路径形成的字符串，以及该字符串的长度。
>
> 第二步，构建失败指针。失败指针的含义是：当当前节点匹配失败时，应该跳转到哪个节点继续匹配。这个和 KMP 的 next 数组思想一致，但是针对多模式串的。构建方式是 BFS 层序遍历，每个节点的失败指针指向父节点的失败指针的对应子节点。
>
> 第三步，遍历主串 S，在 AC 自动机上进行状态转移。每走到一个节点，就沿着失败指针链向上检查，看是否有完整的单词匹配。如果匹配到单词，记录下它的长度。
>
> 第四步，遍历结束后，从所有匹配到的单词中选长度最长的返回。
>
> 时间复杂度 O(n + m)，其中 n 是主串长度，m 是所有模式串长度之和。空间复杂度 O(m * 26)，即 Trie 树的节点数。
>
> 如果没有接触过 AC 自动机，退一步的解法是：对于每个 word，用 KMP 或者 Python 的 `in` 操作符在主串中查找，同时记录最长匹配。但面试中显然面试官期待的是 AC 自动机。

**代码实现**：

```python
from collections import deque

class ACNode:
    def __init__(self):
        self.children = {}          # 子节点
        self.fail = None            # 失败指针
        self.word = None            # 完整单词
        self.length = 0             # 单词长度

class AhoCorasick:
    def __init__(self):
        self.root = ACNode()
    
    def insert(self, word: str):
        """将单词插入 Trie 树"""
        node = self.root
        for ch in word:
            if ch not in node.children:
                node.children[ch] = ACNode()
            node = node.children[ch]
        node.word = word
        node.length = len(word)
    
    def build_fail(self):
        """BFS 构建失败指针"""
        queue = deque()
        # 根节点的所有子节点的失败指针指向根
        for ch, child in self.root.children.items():
            child.fail = self.root
            queue.append(child)
        
        while queue:
            node = queue.popleft()
            for ch, child in node.children.items():
                # 递归找失败指针
                fail = node.fail
                while fail and ch not in fail.children:
                    fail = fail.fail
                child.fail = fail.children[ch] if fail else self.root
                queue.append(child)
    
    def search(self, text: str) -> str:
        """在主串中搜索所有模式串，返回最长匹配"""
        node = self.root
        longest = ""
        
        for ch in text:
            # 匹配失败时沿着失败指针跳转
            while node and ch not in node.children:
                node = node.fail
            if node is None:
                node = self.root
                continue
            
            node = node.children[ch]
            
            # 检查当前节点及失败指针链上是否有完整单词
            temp = node
            while temp and temp != self.root:
                if temp.word and temp.length > len(longest):
                    longest = temp.word
                temp = temp.fail
        
        return longest if longest else None


def find_longest_match(s: str, words: list[str]) -> str:
    """主函数：找到 words 中最长的、在 s 中出现过的子串"""
    ac = AhoCorasick()
    for w in words:
        ac.insert(w)
    ac.build_fail()
    return ac.search(s)
```

### 四、后端基础：如何保证项目可维护性？举一个真实例子

> 项目可维护性不是一个点，而是一个系统工程，我从架构、代码、流程三个层面来谈，然后举一个真实例子。
>
> **架构层面**：模块化设计和接口隔离。每个模块职责单一，模块之间通过接口通信，而不是直接依赖实现。这样改动一个模块不会影响其他模块。
>
> **代码层面**：统一的代码规范和风格，通过 lint 工具（比如 eslint、pylint）自动检查；关键逻辑必须有单元测试，覆盖率在 80% 以上；写代码的同时写好关键注释，但不写废话注释。
>
> **流程层面**：Code Review 是底线，所有代码必须经过至少一人 review 才能合入；CI/CD 流水线自动跑测试、lint 和构建；技术文档沉淀在 wiki 或代码仓库中，保证新人能快速上手。
>
> **真实例子**：我在做 RAG 平台的时候，最开始检索模块和生成模块是耦合在一起的——检索逻辑直接写在生成接口里，数据库查询、embedding 调用、LLM 调用全在一个函数里。后来业务扩展，不同的场景需要不同的检索策略，原来的代码就变得很难维护，改一个策略可能影响另一个场景。
>
> 我做的重构是这样的：把检索流程拆成三个独立的子模块——**文档检索器**（负责从向量库召回文档）、**重排序器**（对召回结果精排）、**生成器**（拼接上下文调用 LLM 生成答案）。每个子模块定义统一的接口，比如检索器接口就叫 `retrieve(query, top_k) -> List[Document]`。不同的业务场景通过组合不同的实现来满足需求，比如 Excel 场景用 Text-to-SQL 检索器，文档场景用向量检索器。
>
> 重构之后，加一个新场景只需要实现一个新的检索器，其他模块完全不用动。单元测试也从原来的一个巨大测试文件拆成了每个模块独立的测试，出问题能快速定位。这就是通过模块化设计来保证可维护性的一个实践。

### 五、问题解决能力：给你一个难任务，你的解决思路是什么？

> 面对一个难任务，我的解决思路分五步走：
>
> **第一步，拆解和定义**：先不要急着动手，而是把模糊的大任务拆成可执行的小问题。比如"做一个智能客服系统"，拆成"意图识别怎么做"、"知识库怎么构建"、"多轮对话怎么管理"、"效果怎么评估"这几个子问题。每个子问题再进一步细化，直到每个子问题都有一个明确的验收标准。
>
> **第二步，调研和选型**：针对每个子问题，调研业界已有的方案。比如意图识别，是用规则匹配、传统分类模型、还是大模型直接做；知识库是用向量检索还是知识图谱。调研时关注三个点：方案的成熟度、团队的熟悉度、和业务场景的匹配度。有现成的轮子就不重复造。
>
> **第三步，MVP 快速验证**：选方案后不要一上来就做完整版，先做一个最小可行版本，用最小的成本验证核心链路是否能跑通。比如智能客服，先做一个单轮问答的原型，验证检索和生成的效果，再考虑多轮对话的上下文管理。
>
> **第四步，迭代优化**：MVP 跑通后，根据反馈数据迭代。这里的关键是建立评估体系——用定量指标衡量效果，比如准确率、召回率、延迟，而不是凭感觉说"好像好了一点"。每次迭代只改一个变量，看指标变化，避免同时改多个东西导致无法归因。
>
> **第五步，复盘和沉淀**：任务完成后做复盘，总结踩过的坑和有效的方案，沉淀到团队知识库。这样下次遇到类似问题，自己和团队都能快速复用。
>
> 举个例子，之前做 RAG 平台的技术选型时，我按照这个思路：先明确了核心需求是"多租户、低延迟、支持中文"，然后调研了 LangChain 和 LlamaIndex 两个框架，用一周时间各做了一个原型来对比，最终选了 LangChain，因为它的生态更成熟、社区支持更好。上线后通过监控召回率和用户反馈持续优化 embedding 模型和分块策略。这个方法论让我在不确定的任务中也能有节奏地推进。

## 面试改进要点

1. **Coding 准备不足**：AC 自动机、Trie 树、KMP 这些字符串算法是高频考点，需要系统刷一遍。之后每周至少刷 3-5 道中等难度算法题，重点覆盖字符串、动态规划、树和图。
2. **Agent 知识体系化**：日常工作中做了很多 Agent 相关的事，但没有形成体系化的知识结构。后续需要把 RAG、模型推理优化、微调这些知识点整理成文档，做到能随时口述出原理、对比和选型依据。
3. **开放性问题的回答框架**：像"如何保证可维护性"、"如何解决难任务"这类问题，面试官考察的是结构化思维。回答时要用"总-分-总"加"举例子"的方式，先给框架再给实例，让回答有层次感。
