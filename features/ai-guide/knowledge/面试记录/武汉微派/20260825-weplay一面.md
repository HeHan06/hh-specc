### 1. 括号字符串匹配：漏掉"栈为空取 top"的边界

**复盘分析**

这道题是经典的栈应用题，思路本身没问题（左括号入栈、右括号出栈匹配），失分点是**边界条件没先想全**——栈为空时遇到右括号，直接 `top()` 会越界/抛异常。这正是自己《避免粗心习惯流程》里第 0 步"读题三问"要解决的问题：写代码前先列边界（空串、单括号、全左/全右括号、交叉不匹配），而不是写完再去想。

**标准口述答案**

> 这道题我用栈来做。遍历字符串，遇到左括号就压栈；遇到右括号时，**先判断栈是否为空**——如果栈空了，说明这个右括号前面没有可匹配的左括号，直接返回 false；否则弹出栈顶，比较是否匹配，不匹配也返回 false。遍历结束后再判断栈是否为空，为空说明所有左括号都被正确闭合，返回 true。
>
> 核心边界有三个：一是栈为空时遇到右括号（不能越界取 top）；二是遍历结束栈非空（左括号多出来）；三是多种括号需要映射判断。
>
> 时间复杂度 O(n)，空间复杂度 O(n)。参考实现：

```java
public boolean isValid(String s) {
    Deque<Character> stack = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        if (c == '(' || c == '[' || c == '{') {
            stack.push(c);
        } else {
            if (stack.isEmpty()) return false; // 关键边界：栈为空不能取 top
            char top = stack.pop();
            if ((c == ')' && top != '(') || (c == ']' && top != '[') || (c == '}' && top != '{')) {
                return false;
            }
        }
    }
    return stack.isEmpty();
}
```

> 如果一开始就按"读题三问"把空串、单括号、全右括号这些 case 先跑一遍，就不会漏掉"栈为空"这一处。

### 2. AI 在实际业务中的应用：只答了"人机一致率对齐"，视野太窄

**复盘分析**

这个问题考察的是"AI 在工程/业务里能落哪些场景、有哪些坑"。你只答了评测维度（人机一致率对齐），这其实对应简历里"评测体系 + LLM-as-Judge"最熟的一块，但题目是开放式的，面试官明显还想听到 **Code Review、稳定性、研发提效**等其他方向，并且点出了"AI 做 CodeReview 会漏性能问题"这个反面案例。失分在于**没有先搭一个"AI 应用全景"的框架再往里填**。

**标准口述答案（结合简历）**

> 结合我在美团的 Agent 建设经验，AI 在业务里的应用我分四类来看：
>
> **第一，质量评测**：这是我最熟的。用 LLM-as-Judge 做自动化评估，核心难点是"机器分"和"人评"对齐，我们靠主观评价优先 + 案例驱动校准，把人机一致率从 40% 提到 90%。
>
> **第二，代码研发提效**：AI 做 Code Review、单测生成、Bug 定位、文档生成。这里有个关键认知——**AI 擅长找语法错误、代码规范、常见安全漏洞（SQL 注入、XSS）和明显逻辑 bug，但容易漏性能问题**。因为性能问题往往要结合业务场景、数据规模、并发模型才能判断，比如高并发下的锁竞争、缓存穿透、N+1 查询、慢 SQL、内存泄漏、深分页，AI 没有足够上下文时容易放过。所以 Code Review 要"人机结合"：AI 做第一道筛查，人做性能、架构、业务正确性的兜底。
>
> **第三，线上稳定性**：用 AI 做日志分析、告警归因、故障定位，缩短 OnCall 排查时间。
>
> **第四，需求与知识管理**：需求澄清、知识库问答、跨团队对齐。
>
> 这样四类一展开，既能体现广度，又能落到 CodeReview 漏性能问题这个具体坑上。

### 3. Redis 排行榜找代码问题：没抓住"高并发"关键词，钻了编译错误的牛角尖

**复盘分析**

这道题是典型的"给代码找 bug + 高并发场景"综合题。你一开始盯着编译错误、运行时错误找，方向就跑偏了——**题干里"高并发"这个关键词才是题眼**，它暗示问题一定出在**并发安全（原子性/竞态）和性能（热 key、深分页、大 key）**上，而不是语法。同时 zset API 不熟，导致连"该用 ZINCRBY 还是读改写"这类关键判断都做不出来。

**标准口述答案（先补 API，再讲高并发问题）**

> Redis zset（有序集合）常用 API 我分四组：
> - 基础：`ZADD`、`ZREM`、`ZSCORE`、`ZCARD`、`ZCOUNT`
> - 排名：`ZRANK`（正序名次）、`ZREVRANK`（倒序名次）
> - 范围：`ZRANGE` / `ZREVRANGE`（按名次）、`ZRANGEBYSCORE` / `ZREVRANGEBYSCORE`（按分数）
> - 聚合与删除：`ZINCRBY`（原子增减分数）、`ZUNIONSTORE` / `ZINTERSTORE`、`ZREMRANGEBYRANK` / `ZREMRANGEBYSCORE`
>
> 排行榜这种**高并发**场景，找代码问题我重点看四点：
>
> **第一，原子性/竞态（最核心）**：更新分数必须用 `ZINCRBY` 原子自增，**不能"先 GET 分数 → 本地计算 → 再 ZADD/SET 写回"**。这种读改写在高并发下会互相覆盖、丢更新、排名不准。这是排行榜代码里最常见的 bug。
>
> **第二，热 key 问题**：榜单头部成员访问高度集中，单 key 压力大，容易把 Redis 打爆。做法是本地缓存（Caffeine）挡一层 + 定期刷 TopN，或按榜单分片。
>
> **第三，深分页性能**：`ZREVRANGE key 0 9` 取 Top10 没问题，但 `ZREVRANGE key 100000 100009` 这种深翻页，offset 越大越慢（复杂度随 offset 线性增长），要改成按分数游标 `ZRANGEBYSCORE` 翻页。
>
> **第四，大 key 与持久化**：成员数过多会拖慢操作，用 `ZREMRANGEBYRANK` 定期裁剪；同时确认 RDB/AOF 配置合理，避免宕机丢数据。
>
> 所以拿到题我会先抓"高并发"关键词，往"原子性 + 热 key + 深分页"这三个方向查，而不是先找语法/编译错误。

### 4. MySQL 基础薄弱（面试官新增信号，此前未覆盖）

**复盘分析**

面试官把 MySQL 单独拎出来点名，说明在存储组件的考察上，MySQL 是和我 Redis 并列暴露的第二块短板。此前复盘完全没覆盖这块。MySQL 面试题集中在几个高频方向：**范式与表设计、索引（B+ 树 / 联合索引最左前缀 / 覆盖索引 / 回表）、事务与隔离级别、锁与 MVCC、慢查询与 EXPLAIN、主从复制**。

**标准口述答案（MySQL 高频基础速记）**

> **索引为什么快 / 为什么用 B+ 树**：InnoDB 用 B+ 树做索引，非叶子节点只存 key、叶子节点存完整数据且用链表串联。好处有三：树矮（磁盘 IO 次数少）、范围查询友好（叶子有序 + 链表）、查询稳定。聚集索引的叶子存整行数据，二级索引的叶子存主键，所以非主键查询要"回表"。
>
> **联合索引最左前缀**：`(a, b, c)` 联合索引，能命中 `a`、`a,b`、`a,b,c`，但 `b`、`b,c`、`c` 单独查不走。所以建索引要按查询条件的区分度和出现频率排序。
>
> **事务四大特性 ACID**：原子性（undo log）、一致性、隔离性（锁 + MVCC）、持久性（redo log）。
>
> **隔离级别与并发问题**：读未提交 / 读已提交 / 可重复读（InnoDB 默认，靠 MVCC 解决幻读）/ 串行化；对应脏读、不可重复读、幻读三个并发问题。
>
> **慢查询排查**：`EXPLAIN` 看 type（const > ref > range > index > ALL）、key、rows、Extra（是否 Using filesort / Using temporary），再针对性加索引或改写 SQL。

### 三、专业建议（重点）

**先说结论**：你的反思方向是对的，但有两个地方需要精确纠偏——**① 根因是"岗位错位"而不是"能力全面崩盘"；② 策略不是"停止 Agent"，而是"重新分配精力配比"**。

#### 1. 先承认一个事实：根因是"岗位错位"

你的简历求职意向是「AI Agent 技术专家」，但最近大量面试的其实是**传统后端岗**（PDD 电商交易、淘天价格保障、字节本地生活、武汉微派等），这些岗位的考察权重天然落在 **coding + 高并发 + 中间件** 上，而不是 Agent。

面试官说"岗位对传统后端高并发要求未达标"，翻译过来是：**你以一个 AI 专家的定位，去面了一个后端专家的场子**。这解释了为什么 Agent 强项没帮上忙——不是它没用，是这些岗位本来就不怎么考它。

所以第一优先级不是"猛补后端"，而是**把投递策略和能力策略分开想清楚**：

- **投递侧**：把岗位分两类——
  - **真·AI Agent 岗**（Agent 应用开发 / 大模型应用 / AIGC 后端，如得物数据应用、涂鸦 AI Agent）：这是你的主战场，Agent 是加分项，后端只要求到"能答场景题"。
  - **传统后端岗**（电商交易、价格保障、本地生活）：这类岗你目前是"陪跑"，除非把后端基本功补齐到及格线，否则投了也大概率挂。
- **能力侧**：无论投哪类，coding + Redis/MySQL + Java 并发都已经是硬门槛，**躲不掉**，必须补。

#### 2. 不要"停止 Agent 补强"，要"重新配比"

Agent 是你唯一能和其他后端候选人拉开差距的差异化优势。完全放下很可惜，而且真 AI 岗会用上。建议精力配比从"Agent 主攻"调整为：

| 优先级 | 模块 | 精力占比 | 目标 |
|--------|------|---------|------|
| P0 | 后端基本功（Redis/MySQL/Java 并发 + 中间件 API） | 60% | 从"八股"补到"能写、能用、能讲坑" |
| P0 | coding（算法 + CR 找 bug） | 25% | 简单题快速+不漏边界，CR 题按清单排查 |
| P1 | Agent 保温 | 15% | 维持已熟的定调语/架构/评测，不再扩新 |

> 关键纠偏：你不是"已经 Agent 很强了所以该转向"，而是"Agent 已到可复用水平，应该转为维持，把增量时间投给短板"。

#### 3. 中间件短板怎么补：从"背八股"升级到"API + 场景"

你之前《应急学习与优化计划》里做了"战略性放弃中间件八股"的决定，这在当时"只投 AI 岗"的前提下是对的；但面试官现在点的是 **"未实际使用过 API"**，这说明你要补的不是概念，而是**真的用过**。

每个组件用"**1 个 demo + 1 个高频坑**"的方式过，比刷十页八股管用：

- **Redis**：亲手写一个排行榜 demo（`ZADD`/`ZINCRBY`/`ZREVRANGE`），再写一个 `Redisson` 分布式锁 demo，跑通并复现"读改写丢更新"的 bug。
- **MySQL**：建一张含联合索引的表，用 `EXPLAIN` 实测最左前缀、回表、覆盖索引、慢 SQL 的 `type` 变化。
- **Kafka**：写一个 producer/consumer，跑通"消费失败重试 + 顺序性"的场景，理解为什么单分区有序、多分区无序。

> 目标不是"背熟 API"，而是面试被问到"排行榜怎么设计""缓存一致性怎么保证"时，你能说"我写过，当时踩过 XX 坑"。

#### 4. coding 短板：用流程卡边界，不靠"更小心"

你在《避免粗心习惯流程》里已经有答案了——漏边界不是粗心，是没按流程先列 case。落到行动上就两条：

1. **简单题**：写代码前先口头报 3 个边界（空、单个、全相同/极值），再动笔。目标是"一次写对 + 讲清复杂度"，不是"写完再补"。
2. **CR 题（找 bug）**：固定按清单排查——**并发安全 → 性能 → 正确性 → 资源**，坚决不从语法/编译错误找起（这是你两次都栽的地方）。

#### 5. 一句话行动结论

> **别再往 Agent 里加东西了；把 85% 的时间砸到 coding + Redis/MySQL/Java 并发 + 中间件 API 上，Agent 只做保温。同时把投递重心往真 AI Agent 岗倾斜，避免拿自己的短板去撞传统后端的硬门槛。**
