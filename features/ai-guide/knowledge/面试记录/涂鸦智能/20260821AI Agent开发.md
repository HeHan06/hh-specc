## 复盘

本场「AI Agent 开发」岗位面试，面试官明显是懂 Agent 的，问题都打在实际架构和工程细节上。四个失分点可以归成两类：

- **没准备 / 概念不熟**：skill 渐进式加载完全没准备，这是最伤的；它本质上就是自己"上下文工程四象限 + 小团 Skill 协议"里做过的东西，但没提前串成一条可讲的线。
- **表达不够收敛**：Agent 架构选型和评测平台编排，项目本身是扎实的，但没按"为什么这么选 → 代价 → 收益"的收敛结构讲，显得啰嗦、抓不住重点。
- **react 流程处理**：只讲了 happy path，没有把"遇到问题时如何自纠"这条线（反思校验、工具路由归因、场景回放）讲出来。

核心提升点：把这些"会做但讲不好"的点，都落到一个"一句话结论 + 分层展开"的口述模板上。

## 标准回复答案（口述版）

### Q1：skill 渐进式加载流程是怎么做的？

skill 渐进式加载的本质，是把"一次把所有技能和知识全量塞进上下文"改成"按需分步注入"。核心机制是 **Reference 模式 + 主模型通过 load_skill 意图触发架构层展开**，不靠额外的小模型。

我先把 Skill 分三层管理：
- **L0 主 Agent Prompt**：ReAct 首轮默认加载，包含角色、能力、常规流程规范和"Skill 激活方法"，兜住大部分请求。
- **L1 专家技能**（酒旅、医药等长尾专家）：默认走 **Reference 模式**，只在上下文里放 name + description（几十 token），不展开全文。
- **L2 原子技能**（Coupon、Price 等）：被 Expert 或 Agent 引用，实现分层复用。

具体加载流程三步：

**第一步，Reference 模式下只注入元信息。** 请求进来后，System Prompt 只挂"当前可用业务专家"的 name + description 列表和默认激活的 Skill，上下文里没有 skill 全文，token 很轻。

**第二步，主模型通过 ReAct 决策触发激活。** 主模型（Planner）在 Thought 阶段判断"综合专家兜不住、需要特化专家"时，会表达一个 `load_skill` 意图——本质就是一个 Function Call 式的激活信号。

**第三步，架构层拦截并展开全文。** 架构层收到 load_skill 信号后做 SHR 激活/展开，把对应 skill 的 markdown 全文注入上下文，同时挂载它内置的工具，模型再继续执行。

另外还有 **Built-in 模式**：超高频 skill（内容搜、供给搜）直接常驻，模型直接调工具，连 load_skill 意图都不用表达。

需要澄清一点：架构里确实有个"意图小模型（<8B SLM）"，但它不是做 skill 识别的，而是**统一网关层**的流量分流——把"查订单、历史查询、活动重定向"这类约 40% 的确定性请求拦截下来绕过 Planner，走缓存/模板链路，跟 skill 加载是两套东西。

做完这套，单次推理 Token 从万级压到 ~3K，TTFT 不随业务复杂度线性劣化。

### Q2：ReAct 流程中遇到问题一般怎么处理？

ReAct 就是让模型在一个循环里交替做"思考（Thought）→ 行动（Action）→ 观察（Observation）"，直到完成任务再输出最终答案。我们服务零售 Agent 就是用 ReAct 做核心推理循环的，一个典型闭环是：用户说"帮我下个 30 以内的洗剪吹团购"，模型先 Thought 判断需要先找供给再交易，然后 Action 调用搜索工具拿到门店和价格，Observation 拿到商品 ID 和价格，再 Action 调用交易工具下单，最后总结输出订单卡片。

遇到问题我分三类处理：

**第一类，工具选错或调用错了。** 早期预约和交易工具容易混淆、幻觉频发。我的处理是：把高频工具合并、把非业务工具移除，指令固化到 System Prompt 减少干扰；用工具路由的混淆矩阵做归因，看哪些工具容易混，针对性优化；架构上从多 Agent 串行演进到 ReAct 融合，减少链路过长带来的意图损耗。

**第二类，参数提错或缺参数。** 比如预约要收集时间、项目、门店这些要素，缺了就让模型发起澄清追问，多轮补齐再执行，而不是直接报错。

**第三类，循环不收敛或者返回异常。** 我做了反思校验机制，主 Agent 对子 Agent 返回的结果做合理性判断，不合理就重试或降级兜底；同时对无结果、空结果、异常回复这类情况设围栏指标，靠监控和场景回放把问题定位到具体轮次和决策点。

### Q3：Agent 架构选型的原因？（收敛版）

我们架构经历了三个阶段，每个阶段的选择都是被当时的核心矛盾逼出来的。

**第一阶段是中心化 Multi-Agent。** 选它的原因是职责高内聚、低耦合：主 Agent 管意图识别和任务规划，子 Agent 分工管供给搜索、预约预订，方便模块化测试和独立迭代。这个阶段用 SOTA 模型（GPT-4.1）快速验证 MVP。

但 Multi-Agent 暴露出三个问题：工具调用准确率只有 80% 左右、单次 query 要串行调用 4-5 次模型导致首 Token 延迟到 26 秒、强依赖境外模型有合规风险。所以**第二阶段改成单 Agent**，把所有能力内化为主 Agent 的工具池，减少模型调用次数。

**第三阶段又演进成 ReAct 驱动的融合 Agent。** 原因是单 Agent 阶段出现了"上下文割裂"和"工具互斥"——搜完就结束，没法"搜→选→约→付"一条链走完。ReAct 能把多步推理串起来，让模型在同一 query 里按需多步调度工具。

至于开发框架，我们选的是自研框架 + 图灵 AIGC 平台双轨并行：工具调用密集的流程用自研，因为图灵平台当时环境不互通、工作流不支持循环和完整工具链路；简单的 LLM 调用和 workflow 用图灵搭，降低算法同学负担。核心原则是避免重复造轮子、渐进式迁移。

### Q4：评测平台的编排流程、意义和难点分别是什么？

**编排流程我分两个层面讲。**

先讲一个评估任务的执行编排，整体是"场景 + 任务"两层模型：先创建一个评估场景，关联三样东西——评测数据集、待测 Agent、评估指标，然后一键执行。执行阶段用组合模式把多个评估功能模块（数据回放、数据清洗、自动化评估、报告生成）编排成一条流水线，模块内部再用策略模式应对不同评估类型。具体链路是：

数据回放（调评测 API 在待测 Agent 上批量回放、收集结果）→ 数据清洗（把回放结果、数据集、指标整合对齐，生成标准评估输入）→ 大模型自动化评估（按 SOTA 流程，用"便宜模型 + 明确指标 + 分类而非打分"来保证成本和准确率）→ 结果统计（解析模型返回，生成 Excel 报告）。

再讲平台层面的编排能力：它支持任务调度，能把自动化评测嵌入到日常数据回流里定时跑，而不是靠人手动触发。

**意义就是三层：** 整合散落的评测资产、标准化一键式提效（效率 +70%）、让机评成为产品 UAT 的围栏，实现评测驱动开发。

**难点四个：** 指标难定义（C 端意图开放、PMF 不清晰）；评测集难建（冷启动缺数据、benchmark 分布易和线上脱节）；LLM-as-Judge 准确率难保证（人机一致率从 40% 拉到 90%）；以及大规模机评的成本控制。
