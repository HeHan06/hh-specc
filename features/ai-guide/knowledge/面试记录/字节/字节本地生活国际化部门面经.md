## 四、最佳答案模板（下轮面试直接用）

### 4.1 Agent系统设计 — 最佳回答框架

当面试官问"讲讲你们的Agent系统是怎么设计的"，按下述结构回答：

---

#### 第一层：全局定位（30秒，一句话定调）

> "我们做的是一个覆盖选店、选品、交易、履约全链路的C端导购Agent，日均30万对话，采用**ReAct模式 + 协调者-子智能体**的Multi-Agent架构。整个系统经历了单Agent试错、Multi-Agent拆分、到现在的上下文精细化治理三个阶段。下面我展开讲几个关键点。"

---

#### 第二层：架构展开（3分钟，核心）

**2.1 Multi-Agent 架构**

```
协调者Agent（Coordinator）
  ├── 子Agent1：供给搜索 Agent
  ├── 子Agent2：预约预订 Agent
  ├── 子Agent3：交易履约 Agent
  └── 子Agent4：名词解释 Agent
```

- 协调者：意图识别 + 任务拆解 + 工具路由（准确率 97%）
- 子Agent：各自独立上下文 + 独立工具集，通过 ReAct 循环决策

**2.2 上下文工程（四象限治理模型）**

我设计了一个四象限分类：

|  | 稳定 | 动态 |
|------|------|------|
| **全局** | System Prompt、工具定义 | 用户画像、Session状态 |
| **当前任务** | 当前-历史对话摘要 | 工具调用结果、实时数据 |

操作策略：

- **预加载**：System Prompt + 工具定义，启动时注入，占约 30%
- **按需注入**：动态上下文（用户画像、商品信息）只在触发对应意图时加载
- **压缩替换**：超过 5 轮的工具调用结果自动摘要压缩，丢弃原始 JSON

**2.3 窗口占比与预算管理（面试官追问的就是这块）**

```
单次请求 Token 预算分配（总额 64K）：
  System Prompt     → 12K  (18%)   固定，启动注入
  工具定义           →  8K  (12%)   固定，启动注入
  历史对话摘要       →  6K  ( 9%)   动态，滚动窗口
  当前轮工具结果     → 20K  (31%)   动态，按需注入
  模型思考余量       → 18K  (28%)   预留给模型推理

超预算策略：
  - 工具结果 > 20K → 优先保留字段级摘要，丢弃原始 JSON
  - 对话历史 >  6K → 用滑动摘要窗口替代原文，保留最近 3 轮完整内容
  - 总 Token > 54K → 触发上下文截断告警，记入监控大盘
```

**窗口占比为什么这样设计？**

- 工具调用结果占 31% 是 C 端导购 Agent 的特点——需要返回大量商品/门店信息，这部分最需要精细化压缩
- 思考余量 28% 是通过 A/B 测试确定的：低于 20% 时工具调用准确率下降 3 个百分点

**监控指标**：
- `context_usage_ratio`：单次请求 Token 实际使用比例
- `window_truncate_rate`：触发了多少次截断
- `tool_result_compress_rate`：工具结果压缩比例
- 告警阈值：连续 5 分钟截断率 > 10% → P1 告警
- 工具路由准确率从 93% → 97%，核心是这个窗口占比调优

---

#### 第三层：架构演进思考（1分钟，展现抽象能力）

> "从 Agent 架构的宏观视角看，我们的演进路径是：
>
> **阶段一**（单Agent）：把所有能力堆在一个Prompt里 → 70K Token，幻觉严重
> **阶段二**（Multi-Agent）：拆成协调者+子智能体 → 总Token从70K降到6K，引入工具路由
> **阶段三**（当前）：上下文精细化治理 → Token降到1.5K/单次输入，工具路由90→97%
>
> 这个演进方向本质上在解一个问题：**Agent规模化的开销**。往上看，未来的方向是 Agent as OS——把每个子Agent抽象成可插拔的服务，统一调度、统一评估、统一计费。我在做评测体系时已经开始朝向这个方向设计。"

### 4.2 Java多线程 — 高频题最佳答案

#### Q1：线程池的创建参数和拒绝策略？

**最佳回答**：

> 线程池七个参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
>
> 执行流程：新任务来了 → 先看核心线程满了没 → 没满直接创建核心线程 → 满了放队列 → 队列满了创建非核心线程（最多到 maximumPoolSize → corePoolSize 个）→ 非核心也满了就触发拒绝策略。
>
> 四个拒绝策略：
> - **AbortPolicy**（默认）：抛 RejectedExecutionException，适合关键任务，必须感知拒绝
> - **CallerRunsPolicy**：由调用线程自己执行，适合可降级场景，吞吐量下降但不丢任务
> - **DiscardPolicy**：静默丢弃，适合允许丢失的非关键任务（如埋点上报）
> - **DiscardOldestPolicy**：丢弃队列最老的任务，适合追求最新数据的场景
>
> **美团实际场景**：Agent 的工具调用用的是 CallerRunsPolicy。因为工具调用是核心链路，丢了任务用户就得重试，用 CallerRuns 让主线程自己执行虽然慢一点，但保证不丢。

#### Q2：实际业务中线程池有哪些坑？

> 三个最关键的坑：
>
> 1. **线程池不要用 Executors 创建**。FixedThreadPool 用的是无界 LinkedBlockingQueue，队列能撑爆内存；CachedThreadPool 的 maximumPoolSize 是 Integer.MAX_VALUE，能创建无限线程。必须用 `new ThreadPoolExecutor(...)` 显式指定参数。
>
> 2. **线程池隔离**。不同业务类型用不同线程池。Agent 系统里，工具调用和 LLM 请求用的是两组池子——工具调用短平快（core=10, max=20, 队列=100），LLM 请求耗时长（core=4, max=8, 队列=50）。混在一起慢请求会堵死快请求。
>
> 3. **ThreadLocal 内存泄漏**。线程池里的线程是复用的，ThreadLocal 用完后不 remove，下次这个线程被复用时会读到上次的脏数据。我们在链路追踪时踩过这个坑——traceId 串了，排查了半天。

#### Q3：实际项目中怎么监控线程池？

```java
// 我封装了线程池监控埋点

    @Override
    protected void beforeExecute(Thread t, Runnable r) {
```

### 4.3 算法 — 翻转二叉树（迭代，禁止递归）

```java
/**
 * LeetCode 226 - 翻转二叉树
 * 要求：不能使用递归
 * 思路：使用栈做 DFS 前序遍历（或用队列做 BFS 层序），
 *       遍历到每个节点时交换左右子树
 *
 * 时间复杂度：O(n)，空间复杂度：O(n)（最坏情况为链状树）
 */
public TreeNode invertTree(TreeNode root) {
    if (root == null) return null;

    // 用栈做迭代前序遍历
    Stack<TreeNode> stack = new Stack<>();
    stack.push(root);

    while (!stack.isEmpty()) {
        TreeNode node = stack.pop();

        // 交换左右子树
        TreeNode temp = node.left;
        node.left = node.right;
        node.right = temp;

        // 先压左再压右（因为栈是后进先出）
        if (node.left != null) stack.push(node.left);
        if (node.right != null) stack.push(node.right);
    }
    return root;
}
```

## 七、总结

这次面试暴露的核心问题是：**在美团做了4年深度项目，但没有把经验"翻译"成面试官能快速理解的语言**。

两条改进主线：
1. **Agent回答改结构化**：先抽象定调 → 细节展开 → 延伸思考，每个环节准备5分钟以内的逐字稿
2. **Java基础补八股**：多线程/线程池/集合源码，按速查表一天内过完

字节面试风格是"追问式+抽象提炼"，策略调整 → **每个回答先给结论和数据，再展开，结尾抛延伸思考**。
