## 一、通用必问（开场与全局）

### Q1. 请做个自我介绍（1-2 分钟）
**考察要点**：① 表达是否结构化、抓重点、有数据；② 是否能把 4 年经历串成一条清晰的成长主线；③ 是否主动贴合「AI Agent 应用开发」岗位而非泛泛而谈；④ 时间把控能力。

**记忆与讲解**：
- 用「四段式」记忆骨架：**我是谁 → 前两年打底 → 近两年进阶 → 为什么投这个岗**。四段层层递进，结尾落点必须是「岗位匹配」，不要停在「我很厉害」。
- 主线一句话：**「从确定性交易系统 → 不确定性智能决策」**。这条线能把 4 年串起来，也天然呼应 AI Agent 应用开发岗。
- 只记 3 个数字锚点：**30w 对话、70k→1.5k Token、人机一致率 40%→90%**。数字多了像背简历，少了没说服力，3 个刚好。
- 主动埋钩子：把「评测体系 40%→90%」放在最后，这是你最硬的差异点，面试官大概率会顺着追问，把节奏带进你的强项区。
- 避坑：① 不要念流水账、不要报公司内部黑话（Beam/小团/到综直接说人话）；② 不要说「我精通 Java」这种空话，用「4 年 Java 后端」带过；③ 控制在 90 秒内，宁可短而利落，不要长而啰嗦。

**口述标准答案**：

> 面试官好，我叫何涵，杭州电子科技大学计算机硕士，2022 年校招进美团，做了 4 年 Java 后端开发。我的经历可以分两段。
>
> 前两年我做到综预订方向，做三方能力接入和导购展示层标准化，这段经历把供给聚合、导购展示、库存和领域建模这些后端基本功打扎实了，也让我对「业务」有了比较深的理解。
>
> 这两年我主动转到了 Agent 方向，深度参与服务零售 C 端导购 Agent 从 0 到 1 的建设。这个 Agent 现在支撑日均 30 万以上的对话，覆盖找店、找品、预约预订、交易下单全链路。我主要做三块：一是 Agent 工程开发，基于 ReAct 搭了协调者加子智能体的分层架构；二是性能优化，把单次输入 Token 从 70k 降到 1.5k；三是评测保障，从 0 搭评测体系，内容质量分的人机一致率从 40% 提到 90%。
>
> 我理解这个岗位是 AI Agent 应用开发，正好能和我的工作经历匹配上，这也是我来投的原因。谢谢。

### Q2. 为什么从预订/货架业务转向 Agent 方向？是主动选择还是组织调整？
**考察要点**：① 转型动机是否真实、有思考深度；② 是否体现技术判断力（看懂趋势）而非被动随大流；③ 能否说明「后端功底对 Agent 开发的价值」，打消面试官对「半路转 AI」的顾虑。

**记忆与讲解**：
- 记忆骨架四步：**先定性 → 再认同 → 讲主动 → 落点延伸**。定性（组织调整还是主动）要诚实，重心放在「我为什么认同并主动投入」。
- 关键策略：如实承认是「两者结合」，但把「组织调整」讲成「被看中的契机」，把「主动选择」讲成「我早有的判断」。既不撒谎（背调有转岗记录），也不显得被动。
- 一个金句：**「这不是转行，是我能力的自然延伸」**。这句话一举三得——① 打消「半路转 AI 是否靠谱」的顾虑；② 把前两年后端经验变成资产而非弯路；③ 暗示自己不是跟风追热点。
- 核心论证链：我在货架/导购做的事，本质是「把复杂供给信息结构化、帮用户做决策」；Agent 的供给推荐是同一件事，只是从「确定性规则」升级成「模型智能决策」。这条链能证明转型是有逻辑的，不是脑热。
- 避坑：① 不要贬低预订/货架业务「没前途」；② 不要说「我早想转 AI 但前两年没机会」（显得前两年在混）；③ 不要回答成「组织让我转我就转了」的纯被动。

**口述标准答案**：

> 这个问题我如实说，是「组织调整」和「主动选择」各占一半。2024 年下半年公司要组建 C 端 Agent 团队，我在预订方向积累的导购展示、供给聚合经验被团队看中，就转了过去。
>
> 但对我来说，这不是被动接受。一方面我早就在关注大模型，判断 Agent 会是本地生活交互的新形态；另一方面，我发现自己在货架、导购上做的事，本质就是「把复杂的供给信息结构化，帮用户做决策」——这和 Agent 要解决的核心问题是同一件事，只不过以前靠确定的规则和流程，现在靠模型做智能决策。
>
> 所以转岗之后，我主动申请去做最核心的 Agent 工程和评测体系建设，而不是等分配。对我来说，这不是转行，是我后端能力和业务理解的自然延伸。

### Q3. 你在简历里写求职意向是「AI Agent 技术专家」，你怎么定义这个角色？
**考察要点**：① 对岗位认知是否清晰（工程 vs 算法 vs 产品的边界）；② 是否知道自己「能做」和「不做」什么；③ 与目标岗位「应用开发工程师」是否对齐。

**记忆与讲解**：
- 记忆骨架：**先给定义 → 再画边界 → 最后对齐岗位**。一句话定义要落地，别背「专家 = 很厉害的人」这种空话。
- 核心定义（记这句）：**「AI Agent 技术专家，是能把大模型能力变成稳定、可评测、可落地的产品系统的人」**。三个关键词「稳定、可评测、可落地」就是你的能力画像，也精准踩中应用开发岗的要求。
- 主动画边界，显示「我知道自己不做啥」：不训练基座大模型（那是算法）、不定产品方向（那是产品），我负责的是中间的工程层——架构设计、上下文工程、工具编排、评测保障、稳定性。
- 对齐策略：你要投的是「应用开发工程师」，所以明说「我不对标算法专家，我对标的是工程侧的专家」，既不自贬，也不让面试官误以为你要抢算法的活。
- 避坑：① 不要说「专家就是什么都懂」；② 不要过度谦虚「我还算不上专家」（自我否定）；③ 不要只罗列技术名词，要落到「解决什么问题」上。

**口述标准答案**：

> 我理解的「AI Agent 技术专家」，核心是「能把大模型的能力，变成稳定、可评测、可落地的产品系统」的人。它和算法专家、产品专家不一样，算法负责把模型训得更好，产品负责定义方向和需求，而 Agent 技术专家负责中间这层工程：怎么设计架构、怎么做上下文和 Prompt、怎么编排工具、怎么保证效果可评测、系统可稳定运行。
>
> 我自己对这个角色的定位，恰恰是工程侧——我在美团做的事也印证了这一点：搭 Multi-Agent 架构、把 Token 从 70k 压到 1.5k、从 0 建评测体系，这些都是「让模型能力真正变成可用产品」的工程活。我不训练基座大模型，也不定义业务方向，但我能把这两端串起来，让 Agent 从 Demo 变成能扛住日均 30 万对话的生产系统。
>
> 所以如果按这个定义，我觉得我过去两年做的事，就是在往这个方向积累，这也是我投「AI Agent 应用开发」这个岗位的原因。

### Q4. 你为什么想离开美团？上一份工作为什么离职？
**考察要点**：① 是否客观、不抱怨前东家；② 离职动机是否正向（成长/平台/方向）而非逃避；③ 与应聘岗位的匹配逻辑是否自洽。

**记忆与讲解**：
- 记忆骨架：**主因（客观）→ 契机（体面）→ 善后（责任心）→ 落点（正向）**。四步层层递进，全程不出现负面情绪。
- 核心原则：**「裁员」两个字永远不要从你嘴里说出来**。改成「赶上公司组织调整，我主动和 leader 沟通申请了离职指标」——既诚实（背调能查到离职类型），又把「被裁」讲成了「主动协商、双向满意」。这个措辞的差异，直接决定面试官把你归为「被优化的」还是「体面离场的」。
- 主因放「结束异地、回杭州」：这是最硬、最不可辩驳的客观理由，且和你简历「期望城市：杭州、上海」完全自洽。面试官几乎不会追问，也不会觉得你在找借口。
- 善后一句带过：强调「离职前把项目交接清楚」，体现责任心，也暗示「我不是甩手走人」。
- 落点正向：把离职和「我想继续深耕 Agent 工程与评测」绑定，顺势转回岗位匹配。
- 避坑：① 不抱怨公司、不吐槽裁员、不流露怨气；② 不说「公司不行了/业务没前途」；③ 不要撒谎说「纯主动辞职」——组织调整记录背调可能露馅，用「组织调整 + 我主动申请」这个平衡点最稳。

**口述标准答案**：

> 核心原因是家庭原因，我想结束异地，从上海回杭州发展。诚实说，正好赶上公司那段时间在组织调整，我 leader 私交不从， 坦诚沟通了这个想法，他也比较理解，主动申请了一个指标。离职前请了leader和同事吃了份便饭，算是体面结束了4年的工作生涯
>
> 走的时候我还是挺感谢美团的，这 4 年让我从校招生成长起来，尤其这两年做 Agent，积累了丰富的工程经验。
>

### Q5. 为什么选择我们部门/这个岗位？
**考察要点**：① 是否做过功课（了解「行业运营技术/供给行业运营方向」在做什么）；② 动机是否真诚、与自身经历有具体连接；③ 是否有长期留任意愿。

**记忆与讲解**：
- 记忆骨架：**业务匹配 → 技术方向匹配 → 长期价值**。三段式，每段都落到「我能给什么」，而不是「我想要什么」。
- 核心策略：这是「你为什么选我 + 我为什么选你」的双向题，别只拍马屁说「贵公司很好」。要把「公司要做的」和「我已经做过的」做**一一对应**，让面试官觉得「这人不只是海投，是真的对口」。
- 通用化处理：把具体公司/部门名留成【占位】，你面试现场替换。但替换不能只换名字，要换「业务关键词」——如果是供给方向就说「复杂供给的结构化与决策」，如果是其他 Agent 方向就换成对应的业务痛点。
- 必杀技：主动补一句「我做过功课」的证据，比如「我了解到你们在做 XXX 方向的 Agent 落地」。哪怕信息不多，也要显得你提前研究过，而不是「进来再说」。
- 落点长期价值：表达「我想在这个方向深耕，而不是镀金跳板」，消解面试官对你「可能干不久」的顾虑（你刚经历离职，这点尤其要安抚）。
- 避坑：① 不要泛泛夸「大厂/平台好/技术强」；② 不要只说「我对 AI 感兴趣」（人人都感兴趣）；③ 不要说「想来学东西」（公司花钱是让你产出，不是让你进修）。

**口述标准答案**：

> 我选这个岗位，主要是三个层面的匹配。
>
> 第一是业务匹配。我之前在美团做的就是复杂供给场景下的导购和 Agent 建设，核心是「把非结构化、多维度的业务信息，结构化之后帮用户做决策」。我了解到咱们这边也是在做类似的事情【占位：替换成你了解到的具体业务，如「供给行业运营的 Agent 应用」】，这块我算是踩过很多坑、也沉淀了不少方法。
>
> 第二是技术方向匹配。这个岗位要的不是纯算法，而是「能落地、能评测、能扛量」的 Agent 应用开发，这正好是我过去两年在干的事——架构、上下文工程、评测体系、稳定性，都是我的主战场。
>
> 第三是长期价值。我这次换工作不是随便看看，是明确想沿着「AI Agent 工程化」这条线深耕下去。我希望找个能让我把这几年的经验继续做深、做透的地方，而不是换个地方重新开始。所以我对这个岗位是认真评估过匹配度的。

### Q6. 你的职业规划是什么？未来 2-3 年想往哪走？（纯 IC 还是带团队？）
**考察要点**：① 是否有清晰但不浮躁的规划；② 规划是否与岗位成长路径吻合；③ 是否暴露「只想来镀金」或「过渡跳板」信号。

**记忆与讲解**：
- 记忆骨架：**短期（扎根）→ 中期（成为骨干）→ 长期（深耕方向）→ 带团队表态**。四段层层递进，节奏是「稳」，不是「冲」。
- ⚠️ 两道红线（你的真实想法，但绝不能说出来）：① 「35 岁危机 / 年龄焦虑」——一说就暴露不安全感，面试官会怀疑你的稳定性和心态；② 「国企 / 银行稳定备选」——这是最致命的，等于告诉面试官「这岗位只是我的过渡，过几年我就去养老了」，基本直接出局。你的真实规划里「深耕前沿 AI」是能讲的，「求稳」是必须咽下去的。
- 定位明确「偏 IC / 技术专家路线」：这与你简历「AI Agent 技术专家」的求职意向一致，也匹配「应用开发工程师」这个 IC 岗。别答成「我想尽快转管理」，会显得不安分、和岗位错位。
- 带团队的表述要「开放但不急切」：说「我优先做深技术，带人是顺其自然的延伸，不排斥」——既显得有上进心，又不让人觉得你「一进来就想当官」。
- 具体化短期目标（加分项）：别只说「好好学习」，给一个可落地的 1 年目标，比如「把 Agent 评测体系做到团队里可复用、可信赖的基建」，和你的强项挂钩。
- 避坑：① 不说「几年后我想创业 / 转产品 / 考公」；② 不说「我还没想好」；③ 不要过分谦虚「我能力有限，能学就行」；④ 不要吹「我要做行业最牛的专家」这种空话。

**口述标准答案**：

> 我的规划比较清晰，就是想沿着 AI Agent 的工程化这条路一直深耕下去。
>
> 短期看，入职第一年我会先把手头的业务吃透，把自己最有把握的「Agent 评测和稳定性保障」这块快速做出价值，成为团队里能独当一面的骨干，而不是一进来就想着转型或跳槽。
>
> 中期两到三年，我希望能在 Agent 架构设计和评测体系上形成自己的方法论，做到「既能带项目、又能把复杂问题拆解清楚」，成为这个方向里别人愿意来问我的人。
>
> 至于纯 IC 还是带团队，我个人的倾向是先走技术专家路线，把技术深度做扎实。带团队对我来说是能力到位之后顺其自然的延伸，我完全不排斥，但不会为了 title 去抢。我更看重的是能不能在 Agent 应用这个方向持续做出可量化、可复用的成果。

### Q7. 期望薪资多少？怎么评估的？
**考察要点**：① 是否有市场认知与合理锚点；② 是否给区间而非死咬一个数；③ 谈判姿态是否成熟、不卑不亢。

**记忆与讲解**：
- 记忆骨架：**先反问/要信息 → 给区间 → 给依据 → 留弹性**。核心是「给区间，不死咬」，且要显得「我有市场认知，不是乱开价」。
- 黄金原则：**先别急着报数**。尽量先反问一句「想了解一下这个岗位的薪资范围和结构」，把球踢回去。如果面试官坚持让你先说，再给区间。
- 区间怎么定：以你当前年包为锚，上浮 15%-30% 作为区间。你目前税前约 27k/月（年包按 16 薪估约 40w+），可以给「月薪 30-35k」或「年包 X-Y」的区间，但具体数字你根据对方职级和城市自己定。**不要报一个精确死数**。
- 给依据（显得专业）：说「我参考了杭州/上海同方向 Agent 应用开发的行情 + 我现在的 package + 我带来的评测体系差异化经验」，三要素支撑，而不是「我觉得我值这么多」。
- 留弹性：补一句「薪资不是我唯一的考量，我更看重方向和成长空间」，把姿态放稳，避免显得只认钱。
- 避坑：① 不要一上来就报最高价；② 不要说「最低 XX，少了不来」（太硬）；③ 不要虚报现薪资（背调/流水会露馅）；④ 不要因为刚离职就自降身价。

**口述标准答案**：

> （如果可以先反问）在聊具体数字之前，方便先了解一下咱们这个岗位的薪资范围和结构吗？这样我也好判断整体匹配度。
>
> （如果对方坚持让你先报）那我先说个大致的区间：我期望月薪在【X】到【Y】之间，对应年包大概【Z】左右。这个区间我是综合三方面定的：一是杭州/上海这边 AI Agent 应用开发岗的市场行情；二是我目前的 package；三是我能带来的差异化价值——比如 Agent 评测体系这块，是比较稀缺的经验。
>
> 当然，薪资不是我唯一的考量，我更看重的是岗位方向、团队和成长空间。如果整体匹配度高，具体数字我们可以再谈。

### Q8. 你目前在职，多久能到岗？

## 二、求职动机与岗位匹配

### Q9. 你觉得自己和我们岗位的匹配度在哪？核心竞争力是什么？
**考察要点**：① 能否提炼出 1-2 个不可替代的差异点（如「Agent 评测 + 供给行业」双重背景）；② 是否围绕 JD 关键词（AI Agent 应用开发、供给行业运营）展开；③ 是否自信但不浮夸。

**记忆与讲解**：
- 记忆骨架：**一个定位句 → 两个差异化能力 → 一个证据收尾**。核心是「提炼 1-2 个别人难以复制的组合优势」，而不是罗列技能清单。
- 核心定位（记这句）：**「我是少数既懂复杂业务、又懂 Agent 工程，还做过评测体系闭环的人」**。这三个词「业务 / 工程 / 评测」是你相对纯算法、纯后端的差异化组合拳。
- 差异化能力一：**「懂业务」**——你做过 4 年复杂业务的后端和领域建模，不是只会调 API 的「Prompt 工程师」。Agent 应用开发最缺的就是「既懂模型、又懂业务规则」的人。
- 差异化能力二：**「会评测」**——这是你最硬的杀手锏。多数 Agent 团队会写 Demo，但很少有从 0 搭评测体系、把人机一致率做到 90% 的经验。这恰恰是「应用从 Demo 到生产」的分水岭。
- 证据收尾：不要停在「我觉得」，落到「30w 对话 + 人机一致率 90% + Token 70k→1.5k」这些可验证的成果上。
- 避坑：① 不要说「我什么都能干」；② 不要贬低别人「很多 Agent 团队都不行」；③ 不要照搬简历逐条念，要「提炼组合优势」。

**口述标准答案**：

> 我觉得我最大的匹配点，是「懂业务 + 会做 Agent + 能建评测体系」这三件事的叠加，这个组合在 Agent 应用开发这个方向上不算多。
>
> 具体说两点。第一，我懂业务。我做了 4 年复杂业务的后端和领域建模，知道真实业务里的供给、交易、库存这些规则有多复杂，所以在做 Agent 的时候，我不是只会写 Prompt 或调 API，而是能理解业务背后的约束，把模型的自由发挥收敛到可控范围里。
>
> 第二，我会建评测体系。这是我最拿得出手的一块。很多团队能把 Agent 做成 Demo，但从 Demo 到能扛住日均 30 万对话的生产系统，中间缺的就是评测和稳定性保障。我从 0 搭过这套体系，把人机一致率从 40% 做到 90%，这也是我觉得自己相对稀缺的地方。
>
> 所以我的核心竞争力，不是某一项技能，而是「能把复杂的 Agent 应用，从想法一路做到可评测、可落地、可扛量」的完整能力。

### Q10. 你目前做的是「服务零售」Agent，我们是「供给行业运营」方向，你觉得经验能迁移吗？差异在哪？
**考察要点**：① 迁移能力与抽象能力；② 是否理解供给/运营侧 Agent 与 C 端导购 Agent 的差异；③ 是否提前思考过业务差异，而非「进来再说」。

**记忆与讲解**：
- 记忆骨架：**先答「能迁移」→ 讲「迁移的是底层能力」→ 坦诚「差异在哪」→ 补「我已经想过怎么补」**。核心姿态是「自信但不傲慢」，既不说「一模一样」，也不说「完全不懂」。
- 关键认知：**业务会变，但 Agent 的底层工程能力不变**。你要迁移的是「架构设计、上下文工程、工具编排、评测体系」这套骨架，而不是「服务零售」这个具体行业知识。把这点讲清楚，就证明你有抽象能力。
- 差异要主动说、说得准（这题面试官就是考你有没有提前想）：服务零售 Agent 是「C 端导购」，用户是消费者，重点是推荐和交易；供给/运营侧 Agent 的「用户」是商家或内部运营，重点是「供给的结构化、运营决策、效率提升」。你能主动点出这个差异，比「我进来再学」高一个段位。
- 落点补一句「补课路径」：说「行业知识我可以快速补，但底层工程和评测能力是通用的、可以直接复用」，既坦诚又不露怯。
- 通用化：把【服务零售】和【供给行业运营】都当占位符，实际面试替换成你当前行业 vs 目标行业即可，逻辑骨架不变。
- 避坑：① 不要说「差异不大，很快上手」（显得不懂）；② 不要说「差别很大，我可能要很久适应」（露怯）；③ 不要只谈「都是 Agent」而说不出差异。

**口述标准答案**：

> 我觉得能迁移，而且迁移的主要是底层能力，不是行业知识。
>
> 我做服务零售 Agent 这两年，沉淀的核心是「怎么设计 Multi-Agent 架构、怎么治理上下文、怎么编排工具、怎么建评测体系」——这套工程骨架是通用的，不管换个什么行业，这些能力都能直接复用。
>
> 差异我也有想过。服务零售 Agent 是面向 C 端消费者的导购，核心是推荐和交易，用户诉求开放、长尾；而供给行业运营方向的 Agent，更多是面向商家或者内部运营，核心是供给的结构化、运营决策和效率提升，任务相对更收敛、更强调可复用和可量化。
>
> 所以行业知识我会快速去补，但底层工程和评测这套能力，我觉得是可以直接迁移过来的，这也是我敢投这个方向的原因。

### Q11. 你怎么看「业务技术」这个定位？技术人要不要懂业务？
**考察要点**：① 对「技术为业务服务」的理解是否到位；② 是否愿意沉下心做业务侧的脏活累活；③ 与纯算法/纯平台岗的自我认知差异。

**记忆与讲解**：
- 记忆骨架：**亮观点 → 讲自己的实践证明 → 说清业务技术 vs 纯技术的差异**。核心立场必须是「技术要为业务服务」，绝不能流露「业务是脏活、我想做纯技术」的倾向。
- 一句话立场（记牢）：**「技术本身不产生价值，技术解决业务问题才产生价值」**。这句既显格局，又精准贴合「业务技术」岗的定位。
- 用自身经历佐证（别空谈）：你前两年做「导购展示层标准化」，就是因为「不同行业的展示逻辑不同」，必须懂业务才能抽象出「通用链路 + 行业差异化」——这就是「业务技术」的活案例。用这个例子证明你不是嘴上说说。
- 主动亮出「业务技术岗的独特价值」：业务技术岗是最懂业务的技术人，能把「业务语言」翻译成「技术方案」，这是纯平台/纯算法岗做不到的，也是业务技术岗的护城河。
- 表达愿意「沉下去」：补一句「我不排斥在业务细节里打磨，因为好架构往往是从业务里长出来的」，直接打消「你只想做高大上技术」的顾虑。
- 避坑：① 不要说「业务是脏活累活」（哪怕心里这么想）；② 不要过度拔高「技术至上」；③ 不要说自己「以后想做纯平台/纯算法」。

**口述标准答案**：

> 我的观点很明确：技术本身不产生价值，技术解决了业务问题才产生价值。所以技术人一定要懂业务，尤其是做 Agent 应用的，因为 Agent 的核心就是把业务规则和用户需求翻译成模型能执行的指令。
>
> 我自己是有切身体会的。前两年我做到综导购展示层标准化，表面看是技术活，但本质是「不同行业的展示逻辑完全不同」——KTV 强调包房和时段，足疗强调技师和项目。我要是不懂业务，根本抽不出「通用链路 + 行业差异化」这套东西，做出来的接口一定复用不了。
>
> 所以我觉得「业务技术」这个定位反而是有独特价值的：它是最懂业务的技术人，能当业务和工程之间的翻译官。这也和我的定位一致——我不是纯算法，也不是纯平台，我是那种愿意在业务细节里打磨、把业务规则变成稳定系统的人。好架构往往就是从业务里长出来的，我不排斥这个过程。

## 三、项目深挖 —— 服务零售 C 端 Agent（简历核心项目一）

### Q12（总纲）. 请完整介绍一下这个 Agent 项目——背景、价值、方案、架构选型、演进与困难
**考察要点**：① 能否有条理地讲清「背景→难点→方案→演进→结果」完整闭环；② 是否体现全局理解而非碎片记忆；③ 是否主动点出「架构选型原因」和「困难与解决」；④ 是否想到哪说到哪。

**记忆与讲解**：
- 叙事主线（这是「整体思路」的骨架，务必记牢）：**是什么 → 为什么做 → 难在哪 → 怎么一步步解（三阶段）→ 结果**。顺着这条线讲，回答就不会散。
- 用「三个核心矛盾」统领全局，让面试官看到你抓得住本质，而不是只记得细节：
  1. **模型能力 vs 时延**——模型单次推理扛不住「高难度意图识别 + 超长上下文 + 十几把工具调度」，拆多步又拖慢 C 端响应；
  2. **业务快速迭代 vs 系统扩展性**——半年新增 14 个垂类场景，上下文窗口和工具容量很快被撑爆；
  3. **冷启动 vs 科学评测**——PMF 不清晰，评测指标和评测集都无从下手。
- 三阶段演进 = 三个矛盾的依次化解，这就是「整体思路」：
  - **阶段一（SOTA + Multi-Agent）**：先拿到能力基线，接受时延损失，同步搭评测体系；
  - **阶段二（国产化 + 扁平化）**：换国产模型，靠架构扁平化 + 上下文工程守住时延和效果；
  - **阶段三（CA + SA 融合）**：打通「搜索」和「执行」，实现「搜→选→约→付」端到端闭环。
- 架构选型原因要主动讲（面试官必追问）：① 为什么先 Multi-Agent——单模型扛不住，拆子 Agent 降复杂度；② 为什么又扁平化——Multi-Agent 串行 4~5 次调用、首 Token 26s、工具准确率仅 80%，且要国产化；③ 为什么融合——解决「要么搜、要么做」的上下文割裂。
- 困难与解决要一一对应（体现「遇到问题能解决」）：工具调不准→工具合并+场景隔离+上下文重构；时延高→架构扁平化+减少调用+AI 搜透传；国产模型能力下降→上下文重构补偿+后训练；冷启动评测模糊→专家知识+数据合成+线上回流。
- 收尾落在「数字」+「我负责的三块」，呼应简历。全程用「深度参与/主导其中几块」而非「我一人搞定」。

**口述标准答案**：

> 我用一条主线来介绍这个项目：它是什么、为什么难、我怎么一步步解决、最后结果如何。
>
> 先说背景。服务零售覆盖 200 多个行业，是场地、设备、人等多元服务实体，供给非常非标。过去的做法是把信息通过层级抽象打到 POI 实体上，但当用户需要基于多个、个性化的决策要素做跨实体组合比较时，GUI 就有三个局限：信息过载、操作层级太深、没法动态适配个体需求。更关键的是，有些场景要结合用户个体情况、用专业引导把需求澄清和收敛，而 GUI 没有互动性，根本做不到。结果就是用户先跑到内容平台、或者到店去问，平台慢慢丧失了决策价值、沦为交易工具。所以我们启动了这个 C 端 Agent，目标是把「选店、选品、交易、履约」全链路做成一个智能助手。
>
> 这个项目难，难在三个核心矛盾。第一，模型能力 vs 时延：模型单次推理扛不住「高难度意图识别 + 超长上下文 + 十几把工具的调度」，但拆多步又拖慢 C 端响应。第二，业务快速迭代 vs 系统扩展性：半年加了 14 个垂类场景，上下文窗口和工具容量很快被撑爆。第三，冷启动 vs 科学评测：PMF 不清晰，评测指标和评测集都无从下手。
>
> 我的解题思路是三阶段演进，本质就是这三个矛盾的依次化解。
>
> 阶段一，先用 SOTA 模型加 Multi-Agent 架构，把复杂任务拆成「协调者 + 找供给子 Agent + 预约预订子 Agent」，降低单 Agent 的复杂度，同时同步搭评测体系，先把能力基线拿到。这个阶段验证了可行性，但也暴露三个问题：工具调用准确率只有约 80%、串行调用 4 到 5 次导致首 Token 要 26 秒、境外模型有合规风险。
>
> 阶段二，做国产化替换和架构扁平化。把子 Agent 内化成主 Agent 的工具，去掉调度环节，减少 1 到 2 次调用；同时合并细粒度工具、把 AI 搜索结果直接透传，把端到端时延从 21.8 秒降到 4.7 秒。国产模型能力下降的部分，靠上下文工程重构来补偿。
>
> 阶段三，做 CA 和 SA 的融合。因为阶段二有个遗留问题：AI 搜索完流程就终止了，中间结果留不住，模型「要么搜、要么做」，做不到「先搜再下单」的连续动作。我们把本身就是 ReAct 架构的 SA 升级为推理主体，把业务能力融进同一个推理循环，工具池打平，这样一次 Query 就能完成「搜、选、约、付」的端到端闭环。
>
> 我在里面主要做三块：Agent 工程开发、上下文和性能优化、还有从 0 搭评测体系。结果上，工具路由准确率从 90.2% 提到 97%，参数准确率从 79.6% 提到 96.6%，时延从 21.8 秒降到 4.7 秒，单次输入 Token 从 70k 降到 1.5k，现在支撑日均 30 万以上的对话。

### Q13. 你简历写「协调者+子智能体」Multi-Agent 架构，能画一下架构图、讲清各 Agent 职责边界吗？
**考察要点**：① 架构表达是否清晰、能落图；② 各 Agent 职责是否边界清晰、无重叠/遗漏；③ 是否真正主导设计而非照抄；④ 是否了解 Handoff 与 Tool Call 的区别。

**记忆与讲解**：
- 记忆骨架（边画边讲，从中心到外围）：**顶层结构 → 主 Agent（CA）职责+工具 → 子 Agent 职责+工具 → 关键约束（不直接通信）→ 交互方式（Handoff vs Tool Call）→ 为什么这样分**。
- 顶层一句话定位：**中心化多 Agent 架构，主 Agent 是中枢，下游挂子 Agent 和工具**。
- 主 Agent（CA）职责，四词：**全局上下文管理、意图识别、任务规划、总结回复**。它的工具清单（记 6 个）：沟通指令查询、门店收藏、子 Agent 调度、供给查询、商品下单、订单退款。⚠️ 关键设计点：短链路任务（店内咨询/交易/收藏）主 Agent **直接闭环，不下发**。
- 子 Agent 两类（按工具边界分）：
  - **找供给子 Agent**：负责「找店/找品/找人/找款」四类意图，挂门店搜索、作品搜索、手艺人搜索工具；
  - **预约预订子 Agent**：负责预约要素搜集、创建预约单、取消预约单。
- 关键约束必讲：**子 Agent 之间禁止直接通信，必须经主 Agent**（避免互相等待→时延放大，保证可控）。
- 深度加分点（来自架构建议）：交互方式分 **Handoff vs Tool Call**——单业务意图+多轮复杂交互用 Handoff（主 Agent 完全移交控制权，子 Agent 直面用户，完成后交还）；多业务意图或简单需求用 Tool Call（主 Agent 只调子 Agent 拿结果，不移交控制权，自己汇总输出）。
- 为什么这样分（认知层 vs 交易层）：导购同时含「闲聊推荐」和「交易支付」两种性质完全不同的任务，塞一个 Agent 会上下文爆炸、模型在资金环节「自由发挥」，所以切开。
- ⚠️ 高频追问辨析（务必吃透）：「Agent vs 工具」的区别**不在「有没有模型」**，而在三点：**① 有没有自己的上下文；② 有没有多轮交互能力；③ 能不能直接面对用户**。子 Agent 是完整自治体（有自己的上下文、能多轮交互、能直面用户），工具只是「一次调用内的判断或执行」，用完就返回、不保留状态。判断标准记牢：「有独立上下文 + 能直面用户」才是 Agent，否则只是工具。阶段二把子 Agent 内化成工具，本质是「砍掉了它独立持有上下文、多轮决策的能力」，即便工具内部仍有 LLM，整体也从 Multi-Agent 降级成单 Agent + 多工具。
- 避坑：① 别画太细绕晕面试官（点到「主 Agent + 2 子 Agent + 工具」即可）；② 别说「子 Agent 互相调用」；③ 别说「全程我一人设计」。

**口述标准答案**：

> 我边画边说。顶层是一个中心化的 Multi-Agent 结构：主 Agent 是中枢，下面挂多个子 Agent 和工具。
>
> 主 Agent，也就是协调者，职责是全局上下文管理、意图识别、任务规划、最后的总结回复。它自己的工具有六个：沟通指令查询、门店收藏、子 Agent 调度、供给查询、商品下单、订单退款。这里有个设计点——像店内咨询、交易、收藏这些短链路任务，主 Agent 会直接闭环，不下发到子 Agent，减少调用开销。
>
> 下游子 Agent 按任务复杂度和工具边界划分，核心是两类。第一类是「找供给子 Agent」，负责找店、找品、找人、找款这四类意图，挂的是门店搜索、作品搜索、手艺人搜索这些工具；第二类是「预约预订子 Agent」，负责预约要素收集、创建预约单、取消预约单。

> 关键约束是：子 Agent 之间禁止直接通信，所有协作必须经过主 Agent，这样避免它们互相等待导致时延放大，也让整个流程更可控。
>
> 交互方式上我们区分了两种。单业务意图、多轮复杂交互的场景，用 Handoff——主 Agent 把控制权完全移交给子 Agent，由子 Agent 直面用户，完成后交还控制权；多业务意图或者简单需求，用 Tool Call——主 Agent 只调用子 Agent 拿结果，不移交控制权，自己汇总输出。

### Q14. 为什么选 Multi-Agent 而不是单 Agent + 多工具？当时的技术选型逻辑是什么？
**考察要点**：① 是否有真实权衡（上下文长度、职责隔离、模型能力限制）；② 是否知道 Multi-Agent 的代价（延迟、协调成本、错误累积）；③ 是否了解业界共识（Anthropic「能 workflow 就不上 Agent」）。

**记忆与讲解**：
- 记忆骨架：**当时为什么选（三个真实原因）→ 后来为什么改（三个真实代价）→ 现在的认知（业界共识）**。核心是「我做过权衡，不是拍脑袋」，且「我知道 Multi-Agent 的代价」。
- 当时选 Multi-Agent 的三个真实原因（来自架构建议文档）：
  1. **单模型能力不足**：All-in-One 模式下 Prompt 上下文长度、工具数量激增，且不同业务逻辑/工具间可能互斥，对 CA 模型能力要求极高，当时通用大模型扛不住；
  2. **职责隔离**：导购同时含「闲聊推荐」和「交易支付」两种性质不同的任务，塞一个 Agent 里上下文爆炸、模型在资金环节「自由发挥」，切开更安全；
  3. **业务敏捷迭代**：WA（业务 Agent）还在 PMF 探索期，需要独立快速试错，和 CA 保持松耦合才能各自迭代。
- 后来为什么改（Multi-Agent 的三个代价，体现你知道代价）：
  1. **时延**：子 Agent 串行调用，一次 Query 触发 4~5 次模型调用，首 Token 达 26s；
  2. **错误累积**：意图每经过一层 Agent 的「重新理解」就失真一次，工具准确率仅约 80%；
  3. **上下文割裂**：子 Agent 有自己的上下文，中间结果留不住，搜完无法接着执行。
- ⚠️ 加分点：主动说「业界共识」——**Anthropic 的原则是「能用 workflow 就不上 Agent」，我们最终也是往「扁平化、端到端」收敛**。这句话证明你不是只会背书，而是有业界视野 + 亲历过「先上 Agent 再收敛」的完整闭环。
- 一句话总结选型逻辑（记牢）：**「先用 Multi-Agent 换『能力基线』和『职责清晰』，代价是时延和错误累积；拿到基线、摸清问题后，再用扁平化换回『时延和确定性』」**——这是「先复杂后简化」的务实路径，不是「一开始就选错」。
- 避坑：① 别说「Multi-Agent 就是更高级」；② 别把「后来改成单 Agent」讲成「前期选错了」（要讲成「阶段性最优」）；③ 别说「我一开始就主张单 Agent」——那和简历的演进史矛盾。

**口述标准答案**：

> 当时选 Multi-Agent，是三个现实原因逼的。
>

>

### Q15. 子 Agent 之间的通信协议怎么设计的？同步还是异步？有没有遇到过互相等待导致时延放大的问题？
**考察要点**：① 工程落地细节；② 是否关注过时延与可靠性；③ 是否有真实踩坑与解法。

**记忆与讲解**：
- 记忆骨架：**先纠偏（子 Agent 不直接通信）→ 说同步/异步 → 说踩过的时延坑 → 说解法 → 深度补充（缓存交互）**。
- 第一句先纠偏（关键，别顺着「子 Agent 之间」这个假设答）：**子 Agent 之间不直接通信，都经主 Agent 中转**。这是中心化架构的刻意设计，避免「多对多」通信的时延和状态混乱。
- 通信方式：阶段一是**同步串行**——主 Agent 发起子 Agent 调度后，阻塞等待子 Agent 返回结果，再继续下一步。这正是「一次 Query 触发 4~5 次模型调用、首 Token 26s」的根因：每层同步等待都会把时延叠加。
- 踩坑与解法（体现「我遇到过并解决了」）：串行同步导致时延放大，所以阶段二做了三件事——① **砍掉调度层**（子 Agent 内化成工具，减少 1~2 次调用）；② **AI 搜索结果透传**（不再二次总结）；③ **异步化**（架构建议文档明确写了「流程异步化、非阻塞等待」是短期时延手段之一）。
- ⚠️ 深度加分点（预约场景的「缓存如何与 Agent 交互」，面试官常追问）：
  - 预约的槽位中间状态存 **Redis**（`用户ID + 商户ID` 为 key），**不是存在任何 Agent 的上下文里**——这就是「把状态从上下文搬出来」的关键，解决了阶段一「子 Agent 上下文割裂、中间结果留不住」的问题。
  - 读缓存不是主 Agent 直接读，而是**「要素追问工具」内部完成**：这个工具**内部有模型调用**，负责「读 Redis → 对比该行业必填要素（海马平台配置）→ 判断缺啥 → 生成追问话术」，再把「追问话术」或「要素齐全信号」回填给主 Agent。
  - 这印证了「Agent vs 工具」的判断：要素追问工具内部虽有 LLM，但它不保留自己的上下文、不直接面对用户、不跨轮记忆，所以它还是「工具」，不是「Agent」。
- 避坑：① 别把「子 Agent 通信」答成「它们互相 RPC」；② 别只说「同步」不说为什么、怎么改；③ 别把缓存交互讲成「主 Agent 直接查 Redis」。

**口述标准答案**：

> 这里先纠正一个前提：子 Agent 之间其实不直接通信，都经过主 Agent 中转。这是中心化架构刻意做的，避免「多对多」通信带来的时延叠加和状态混乱。
>
> 通信方式是同步串行的：主 Agent 发起子 Agent 调度后，阻塞等待子 Agent 返回结果，再继续下一步。这个设计确实踩过时延的坑——一次 Query 会触发 4 到 5 次模型调用，每层同步等待都叠加时延，最后首 Token 要到 26 秒，这在 C 端是不可接受的。
>
> 所以阶段二我们做了三件事来解决：第一，砍掉调度层，把子 Agent 内化成主 Agent 的工具，直接减少 1 到 2 次模型调用；第二，AI 搜索结果直接透传，不再二次总结；第三，部分流程做异步化、非阻塞等待。
>
> 这里我可以展开讲一个预约场景的细节，它体现了「状态」和「上下文」是怎么解耦的。预约要填的槽位中间状态，我们存在 Redis 里，用「用户 ID + 商户 ID」做 key，而不是存在任何 Agent 的上下文里。具体读缓存，是「要素追问工具」内部做的——这个工具内部有模型调用，负责读 Redis、对比这个行业必填的要素、判断缺什么、生成追问话术，然后把话术或「要素齐全」的信号回填给主 Agent。这样主 Agent 的上下文随时可以裁剪，但槽位状态一直安全地躺在缓存里。这正好解决了阶段一「子 Agent 上下文割裂、中间结果留不住」的问题。

### Q68. 简历写「日均 30w 对话」，这个数字是峰值还是均值？统计口径是什么？
**考察要点**：① 数字是否真实可验证；② 是否夸大；③ 对业务规模的真实认知。

### Q69. 「工具路由准确率 97%」「参数提取准确率 96.6%」这两个数字在什么评测集上？业界什么水平？
**考察要点**：① 数字背后的评测集是否可信；② 是否了解业界对标（避免自嗨）；③ 数据诚实度。

### Q70. 「人机一致率 40%→90%」提升的 50 个点，是优化了评测提示词还是优化了 Agent 本身？会不会有「评测作弊」嫌疑？
**考察要点**：① 是否诚实区分「评测体系变准」和「Agent 变好」；② 是否理解「用 LLM 评 LLM」的循环论证风险；③ 是否有独立校验。

### Q71. 你简历写「单次 Token 消耗从 70k 降至 1.5k」，是极端 case 还是均值？中间有没有回退过？
**考察要点**：① 数字口径严谨度；② 是否诚实说明「压缩有代价、可能回退」；③ 是否被深挖时露怯。

### Q72. 你有 SCI 三区论文和一篇专利，是什么方向的？和现在的工作有关吗？
**考察要点**：① 学术背景的真实性；② 研究能力与工程岗位的关联；③ 是否只是「简历装饰」。

### Q73. 你是硕士，为什么本科电子信息类、硕士计算机技术？转专业原因？
**考察要点**：① 成长路径的合理性；② 学习能力与自驱力；③ 是否有清晰的技术追求。

### Q74. 你在美团 4 年，从 L5 到 L6，职级晋升路径正常吗？为什么觉得自己值 L6？
**考察要点**：① 职业成长的真实含金量；② 是否理解职级与能力的关系；③ 自信程度。

### Q75. 你期望城市写「杭州、上海」，这个岗位在哪个城市？你对工作地点有硬性要求吗？
**考察要点**：① 地点灵活性；② 是否与岗位实际所在地冲突；③ 稳定性顾虑。

## 九、候选人反问环节（准备 2-3 个高质量问题）

### Q76. （反问）这个岗位目前团队规模、分工是怎样的？新人前 3 个月的核心目标是什么？
**考察要点**：① 体现你对「落地」而非「title」的关心；② 显得务实、目标感强。

### Q77. （反问）当前供给行业运营 Agent 最大的技术挑战/瓶颈是什么？团队希望这个人优先解决什么？
**考察要点**：① 体现你「以解决问题为导向」而非「以学习为导向」；② 展现主动性与责任感。

### Q78. （反问）这个岗位的成长路径和晋升机制是怎样的？团队对技术沉淀/分享的重视程度？
**考察要点**：① 体现长期主义与上进心；② 不卑不亢，把「我要成长」和「我能贡献」绑定。
