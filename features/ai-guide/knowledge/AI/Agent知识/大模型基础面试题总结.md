1. 面试官真正想考什么?

答：
大模型基础题表面上问概念，实际考的是工程判断。你可以按下面这张表来理解。

| 考察方向 | 面试官想确认什么 | 常见扣分点 |
| --- | --- | --- |
| Token 和上下文 | 你是否理解成本、延迟、窗口限制和信息取舍 | 只说 Token 是"词元"，讲不出工程影响 |
| 采样参数 | 你是否知道如何在创造性和稳定性之间取舍 | 把 Temperature 说成越高越聪明 |
| API 调用链路 | 你是否具备把模型接入生产系统的经验 | 只说调用 HTTP 接口，忽略重试、限流、幂等 |
| 结构化输出 | 你是否知道自然语言约束不等于工程契约 | 认为"请返回 JSON"就足够可靠 |
| 评测闭环 | 你是否能验证效果，而不是凭感觉调 Prompt | 只看公开 benchmark，不做业务 Golden Set |

一个不错的回答通常不是定义式的，而是“概念 + 问题 + 工程解法”。例如问 Token，你可以先解释 Token 是模型处理文本的基本单位，再补一句：Token 直接影响上下文容量、推理成本、响应延迟和截断风险，所以生产系统里要做预算估算、历史消息压缩、RAG 证据筛选和最大输出限制。

2. Token 是什么？为什么中文、英文、代码消耗的 Token 不一样？

答：
Token 不是字，也不是单词，它是 BPE 这类分词算法对文本切分后的最小子词单元。举个例子，英文词 "playing" 可能被切成 play 和 ing 两个 token，高频词像 the 就是单独一个 token。模型本质上只认识数字，所以文本进模型前必须先 tokenize 成一个 token ID 序列。

为什么不同语言消耗不一样？根因在 BPE 分词器的训练数据分布。训练语料里英文占绝大多数，高频英文词和常见字母组合很早就被合并成了独立 token；而中文在语料里占比小，汉字编码长，BPE 没有足够的统计信号把它们合并成大单元，所以中文通常被切成更碎的 token。同一个意思的中文输入，token 数往往是英文的 1.5 到 3 倍。

代码就更特殊了。代码里缩进空格、换行、大括号、分号这些符号密度非常高，分词器又是为自然语言优化的，不会把这些符号合并，导致每个符号都独立占 token。所以一段代码的 token 数通常比等量文字的英文还高。

工程层面，这意味着三件事：第一，API 按 token 计费，中文和代码场景的成本天然更高，要做 token 预算估算；第二，上下文窗口是 token 维度计量的，中文和代码在同样窗口下有效信息量更少，长文档或长代码文件更容易触发截断；第三，token 越多自回归解码步数越多，首 token 延迟和总延迟都会线性增长。所以在生产系统中，针对中文业务我会做 prompt 压缩、历史消息摘要，针对代码场景会做文件切片和窗口预留。

3. 上下文窗口是什么？上下文窗口越大，效果一定越好吗？

答：
上下文窗口指的是模型单次推理时，能处理的token总数上限，包括输入和输出。比如，一个128K窗口的大模型，如果输入战略100k，那输出最多输出28K。

第二个问题，窗口越大效果不一定越好，甚至可能更差。我从四个角度解释：

第一，“迷失中间”效应。这是很多论文都验证过的线下：模型对上下文开头和结尾的信息注意力最强，中间部分显著衰减。你把关键指令放在长文的中间位置，模型经常忽略。这不是bug，是Transformer注意力机制的固有偏置。

第二，计算成本的平方增长。Transformer自注意力的复杂度是O(N^2)，窗口从8K扩展到128K，计算量不是16被，是256倍，API调用时延和成本都会暴涨，生成环境里这是实打实的钱。

第三，“大海捞针”随窗口增大退化。各大模型在大海捞针问题测试中的表现曲线显示，窗口越大，模型从长上下文中定位关键信息的准确率越低，尤其在窗口中间位置。128K的长窗口能力不等于128K的精准检索能力。

第四，噪音问题。如果把不相关的上下文一股塞进去，无关信息会稀释注意力全在，模型反而容易被带偏，回答质量还不如给精炼过的关键信息。

所以工程实践中，我不会盲目追求长窗口。我的判断逻辑是：如果任务需要跨文档的全局理解和推理，比如全文摘要或多跳推理，那长窗口是必要的；如果知识从知识库中检索相关片段来回答问题，那动态嵌入上下文的方案，效果更好，成本更低、延迟也更可控。

4. 什么是 Lost in the Middle 问题？长上下文场景下怎么缓解？

答：
Lost in the Middle 是一个多篇论文反复验证的现象：当上下文边长，模型对中间位置信息的理解和提取能力会显著下降，但对开头和结尾保持高准确率，整体呈现U型曲线。

他的根因主要有两个层面。一个是注意力机制层面----因果自注意力让序列前面的token被大量后续token关注，积累了更强的表示；结尾token因为自回归解码的recency bias，也有天然优势。中间的token被前后夹击，注意力信号被稀释。另一个是训练数据分布层面----真实文档中重要信息往往在开头和结尾（类似总分总结构），模型在预训练中强化了这种收尾偏好，

怎么缓解？我分两类说：不改变模型的做法和需要微调的做法。

先说不改变模型的做法，这也是工程中最常用的：

第一，信息重排。比如RAG场景，我不用直接把相关度最高的文档全排最前面，而是把最重要的放到开头和结尾。有实践经验表明，把关键证据放到prompt末尾，召回率往往比放开头更好。

第二，分段处理加汇总。长文档场景下，我切成多块分别让模型做局部摘要或信息提取，再把各块的结论汇总后做最终推理，这样每次都保证模型在较短的、可控的窗口内工作。

第三，多轮递进。第一轮当模型扫描全文定位关键段落，第二轮只把定位到的关键段落输入做精读推理，相当于用模型的“第一遍浏览”代替人工检查。

第四，关键信息前置或重复。重要的系统指令、约束条件、放在prompt前面，如果上下文很长，在末尾再重复一遍，两端夹击保证模型不忽略。

如果需要微调，可以坐位置编码的干预（比如让RoPE频率更分散），或者对长上下文中段做专门的训练数据增强。

实践中我常用的组合是：RAG场景中把Top文档按重要度首尾分布；长对话场景对历史做滑动窗口+摘要压缩，保证最新的对话上下文始终在窗口末尾。这样基本能覆盖大部分生产场景的Lost in the Middle。

5. Temperature、Top-P、Top-K 分别控制什么？生产环境怎么设置更稳？

答：
这三个参数控制的是模型在生成每个token时，如何从词表概率分布中采样。它们是递进关系，我按推理流程来讲。

模型每步输出的是一个对数概率向量，覆盖整个词表。

第一步，temperature对这个向量做温度缩放：T=1保持原样，T > 1把分布压扁让低概率次也有机会被选中、输出更多样，T<1拉尖分布让高概率词更加突出、输出更稳定。T=0就是argmax，永远选概率最大的那个token，更确定。

第二步，Top-K做硬截断，只保留概率最高的K个候选，其余的置0。K越小越保守，但问题在于分布是动态的--有时候前50个词占了99%的概率，有时候才占10%，一刀切不合理。

第三步，Top-P做自适应截断，只保留概率从高到低累加刚好超过阈值P的最小子集。P=0.9意思是“只保留那些概率足够高、加起来刚好超过90%的token”。它的优势是根据每步的实际分布动态调整候选集大小，不会像Tok-K那样再分布集中时浪费多样性、分布平坦是保留太多噪音。

现在主流工程实践是Temperature + Top-P组合，Top-K在大部分API中已经被边缘化，甚至不暴露出去了。

**生产环境怎么设置？我按场景来：**

第一类，需要确定性的场景--代码生产、数学推理、结构化数据提取。我会设Temperature=0，Top-P无所谓因为temperature=0已经是argmax。这时候模型输出是确定性的，但要注意，不同硬件上的浮点运算可能产微小差异，如果业务要求严格幂等，需要在应用层做缓存校验。

第二类，客服问答、事实查询类场景。Temperature设0.1到0.3，Top-P设0.9.这个区间能保证回答的准确性，同时措辞有少量自然变化，不会每次回复完全一样，显得像机器人。

第三类，通用聊天对话。Temperature0.5到0.7，Top-P 0.9到0.95。这是自然度和稳定性的平衡点。

第四类，创意类任务比如写诗、起名。Temperature可以设0.8到1.0，但注意不要超过1.5，超过之后概率分布趋于均匀，输出会变得随机拼凑、语义断裂。

另外有一个容易忽视的点：即使temperature设的比较低，如果prompt本省给了模型很大的发挥空间，输出仍然会不稳定。所以参数调优要和prompt设计放在一起看，不能只调参数。稳定定是一个系统工程，不是单个参数的锅。

6. 为什么 Temperature 设置为 0，模型输出仍然可能不完全一致？

答：
这个问题问到了推理栈的底层。Temperature=0在数学上等价于greedy decoding--每一步都选概率最大的token，逻辑上是确定的，但工程上“确定”是个相对概念。

根因是GPU浮点运算的非确定性。

具体来说有三个环节在推理链路里注入不确定性：

第一，并行矩阵乘法的浮点规约不满足结合律。Transformer推理的核心运算是大矩阵乘法。GPU上几千个线程并行计算，每个线程负责一部分乘积再累加。由于浮点数假发不满足结合律，不同线程的调度顺序会产生不同的舍入误差累积。两次推理即使输入一样，如果GPU的线程wrap调度有差异，中间结果就可能差几个最小精度单元。

第二，softMax的误差放大效应。这几个最小精度单位的差异传到softmax层，经过指数运算后被放大。假设两个token的logit分别是5.000000和5.0000001，差异是1e-7--经过指数运算后变成e5和e5（1+1e-7），这个差异虽然仍很小，但在极少数情况下，刚好能翻转概率排名的第一和第二。这时候greedy decoding就选到了不同的token，后续整个序列都岔开了。

第三，不同推理框架的实现差异。同一个开源模型，用vLLM跑和用Transformer跑，中间结果也可能不同。因为不同框架的算子融合策略、KV cache的数值精度、FlashAttention的版本都不同。不是模型变量，是计算意图变了。

那工程商怎么办？两个策略：
一：如果业务不要求绝对确定性（大部分场景），接受他，在评测时做统计回归而非单次对比；
二：如果要求绝对幂等--比如线上判决、合规审查--那应用层要对相同prompt的输出做缓存去重，不做缓存就要固定整个推理环境：同一张卡、同一个batch size、同一个框架版本、同一个seed。

最后补充一点：在同一个进程、同一个GPU上，相同参数连续调用两次，结果基本是确定的。差异主要体现在跨硬件和跨运行时。所以排查此类问题，先确认是否换过部署环境。


7. 大模型为什么会产生幻觉？常见缓解方案有哪些？

答：
先说根因。大模型的本质是一个条件概率模型，它在做的是给定前文预测下一个toke的最大概率。这个过程中没有任何的“真值校验”机制。

具体来说有四个层面的原因：

第一，架构层面。自回归解码是单向的、逐token的。模型生成第100个token时，不会回头检查第5个token是真是假。即使前面内容已经虚构了，后面也继续沿着虚构的方向走。

第二，数据层面。预训练预料从互联网爬取，本身就包含大量错误、过时和虚构信息。比如模型学到了“某个明星的出生日期”，但那个日期的来源可能是论坛上的谣言。

第三，泛化层面。当用户问一个模型训练数据中覆盖不足的领域时，模型不会输出“我不知道”，而是从参数化的临近只是域做插值生产，这会产生看似合理但实际不正确的答案。LLM没有被训练成会说“不知道”。

第四，采样层面。Temperature不为0时，采样随机性可能选中次有token，而一旦开头选错，后续token会沿着这条错误路径持续自回归--这就是暴露偏差，幻觉会自强化。

缓解方案我按工程成本从低到高说：

第一层--prompt设计，零成本，立刻见效。我会在系统提示词中明确要求“如果信息不充分，请直接声明不确定”;对关键事实要求“引用原文回答，不要推断”；再用few-shot示例展示不确定是的正确行为。这是最快见效的一层。

第二层--RAG外挂知识库，这是目前业界最主流的方案。把模型的角色从“记忆库”变成“阅读理解器”--检索相关文档塞入上下文，让模型基于给定材料回答而不是凭记忆。这样可以大幅降低事实性幻觉，但不能解决逻辑推理类幻觉。

第三层--解码策略控制。事实类任务设Temperature = 0做贪心解码；或者对同一问题多次采样，取出现频率最高的答案做一致性投票。

第四层--后处理校验。输出后做一层“安检”：用NER抽取实体、检查是否在输入文档中出现；用规则引擎校验日期、数字是否合法；甚至用另一个模型做事实检查。成本高一些，但对高风险场景有必要。

第五层--模型训练层面。通过RLHF或DPO做偏好对齐，让模型学习在不确定时表达不确定性；在SFT阶段加入我不知道的训练样本。但这是需要训练资源的方案。

实际生产系统我不会只用一种，通常是多层组合。比如客服场景：RAG检索文档+Temperature=0.1+prompt约束“基于材料回答”+后处理检查输出中的产品型号是否在知识库中。这套组合下来，幻觉率能压倒很低，但说实话，目前做不到零幻觉。

8. Token 预算怎么估算？输入、输出、历史消息、RAG 证据如何取舍？

答：
Token预算的本质上是在固定的窗口下，对输入输出做配额管理。我先说预算公式，再说各部分的取舍策略。

预算公式很简单：
```
可用输入token = 上下文窗口 - max_tokens(输出上限) - 5%到10%的安全余量。
```
安全余量一定要保留，因为tokenizer的计数和模型实际消费可能有微小偏差，卡在窗口上限调用容易被截断。

取舍策略上，我按优先级排了5个角色：

第一优先级，系统提示词。它定义了模型的行为边界和输出规范，不能被压缩和截断，但必须设计的精炼。我会定期审查系统提示词，去掉冗余的修饰语和重复指令。

第二优先级，用户当前输入。这是本轮任务的核心，必须完整保留。但如果用户输入本身就很长（比如粘贴了一整篇论文），我会先估算token数，超过输入预算的50%就直接截断末尾部分，同时在prompt里告知模型“输入因长度限制，已被阶段”。

第三优先级，RAG检索证据。证据是约束幻觉的关键，但不需要无限堆砌。我的做法是：按检索相关度排序，从高到低逐条填充，每加一条用tiktoken算累计值，知道剩余预算用完或证据好近。通常Top3到Top-5就够了，更多证件在Lost in Middle效应下反而被忽略。另外，我会把最相关的证据放到prompt末尾，利用位置优势提升召回。

第四优先级，历史消息。长对话场景下最占空间的就是历史消息。我的策略是“滑动窗口+摘要压缩”：保留最近N论的完整对话，超过N论的用LLM对早期历史生成摘要、替代原文。如果摘要也超预算，就按“最久远优先淘汰”原则直接丢弃。关键点是--摘要必须保留“用户核心诉求”和“模型已经确认的结论”，避免因压缩而丢失关键上下文。

第五优先级，模型输出。它不是输入预算的一部分，但会反向挤占输入。我会根据业务需求设定max_tokens：客服场景512-1024，文章生成2048-4096，代码生成可能到8192。原则是宁可截断输出，也不能让输出挤掉输入中的系统提示词或关键证据

执行流程上，我会在每次API调用前做三件事：
1）用tiktoken精确计算各部分token数；
2）按优先级填充直到预算耗尽；
3）断言总token数不超过预算上限，超出就触发阶段或降级逻辑。不要让API服务帮我截断

最后，如果窗口实在不够用，走降级路径：要么降低max_tokens，要么减少RAG证据条数、要么对历史消息做深度的压缩。实在不行就用支持更大窗口的模型，但成本会相应增加。


9. 长上下文窗口会不会取代 RAG？二者分别适合什么场景？

答：
我的判断是不会取代，二者是互补工具，各有不可替代的场景。

先说明一下各自的本质。长上下文本质上是一种“全量加载”的策略--把相关文档一股脑塞进prompt，让模型自己做信息筛选和关联。RAG则是“检索优先”策略--先通过向量检索或关键词检索从知识库取到最相关的片段，只把这些片段注入prompt。

为什么长上下文不能取代RAG？三个根本原因：

第一，成本差异是指数级的。Transformer的注意力复杂度是N2，128K和8K窗口的成本差距远超16被，而对大多数知识问答场景，真正相关的可能知识三五段话，把整本手册塞进去纯属浪费。

第二，精度反而下降。Lost in Middle效应告诉我们，上下文越长，中间部分信息被模型忽略的概率越高。RAG把Top-3相关片段放在prompt末尾，正好落在模型注意力最强的位置，事实性回答的准确率往往比长窗口全量塞入更高。

第三，RAG提供了知识热更新能力。知识库新增一篇文档，RAG只需更新向量索引，毫秒级生效。长上下文方案要么在每次prompt构建是重新拼装全文，要么就是用过时的静态文本。

各自适用场景：
1）长上下文适合需要“全局视野”的任务。比如全文摘要，只看片段无法概括整体；合同审阅，需要理解条款之间的交叉引用；多跳推理，A文档引用B文档的结论，RAG对这种跨文档关联天然弱势。
2）RAG适合需要“精准定位”的任务。比如企业内部的知识库问答。文档可能几千分，每次质检所最相关的3-5端就够了；代码库问答：找函数定义或调用链；需要时效性的场景，比如查询最新的政策法规。

实际生产架构中，我通常会做混合设计。举个例子：用户问“对比我们2023年和2024年的销售策略”，RAG先检索出这两年相关的文档段落，然后把这些段落和用户问题一起放进一个中等长度的上下文窗口，让模型做段落的对比推理。这叫“RAG初筛，上下文精度”。

路由层面也可以做自动化：先对用户问题做意图分类，如果是“总结”“对比”“审阅”类任务就走长上下文链路，如果是“查找”“检索“”什么是“类任务就走RAG链路。这样既保证了各自的优势场景，也控制了整体成本。


====API调用工程====


10. 大模型 API 调用的完整链路是什么？

答：
我把API调用拆分成5个阶段来讲，每个阶段都有生产环境需要考虑的关键点。

第一阶段，请求构建。首先做prompt拼装，系统提示词、用户当前输入、对话历史、RAG检索结果按优先级组装好。然后最关键的一部--用tiktoken做token计数校验，确保总token数不超过模型窗口减去max_tokens再减去5%安全余量。这个校验不做，上线后会出现随机截断。参数上根据任务类型设置Temperature和max_tokens，事实类任务Temperature=0保证确定性，创意类适当调高，

第二阶段，发送请求。HTTP POST 到 API endpoint，带上认证信息和合理的超时配置。这要要分开设置连接超时和读取超时----连接超时通常5-10s就够了，读取超时要根据max_tokens估算，一般设60-120s，流式输出场景要更宽容。请求体里我会带上idempotency_key，做幂等保证。

第三阶段，错误处理和重试。这是生产环境最容易出问题的地方。我按错误类型分类处理：
1）4xx客户端错误不重试，因为重试也不会成功，直接记录日志并告警；
2）429限流错误读取响应头的的Retry-After字段，等够时间重试，同时触发客户端限流保护；
3）5xx服务端错误和网络超时用指数退避重试，策略是1s、2s、4s，最多3次，并且加一个随机jitter避免惊群效应。另外重试时必须带相同的idempotency_key，防止重复消费。

第四阶段，响应处理。拿到响应后先检查HTTP状态码，然后解析JSON体。这里不能假设响应格式一定对，要做try-catch。解析完以后重点看三个东西：
1）content内容本身；
2）finish_reason，这直接决定了回答是否完整--”stop“政策，”length“说明max_tokens不够被截断了，”content_filter“说明触发了安全审查；
3）是usage里的token消耗，用来做成本核算。如果业务要求结构化输出，比如要求返回JSON，我会在拿到内容后先尝试json.loads，解析失败就触发重试或降级。

第五阶段，监控观测。生产系统不是黑盒。我会记录每次调用的关键指标：端到端延迟、首Token延迟、prompt token数和completion token数、finish_reason分布、错误率按类型分类。这些指标做成监控大盘，设置告警规则，比如限流错误率，超过5%就告警、finish_rason为”length“的比例突然升高就要检查max_tokens配置。

补充一个全链路的关键设计--多层降级。如果主模型调用持续失败，降级链路通常是这样：主模型 -》同厂商轻量模型-》备选厂商模型-》静态兜底回复。每一层降级都有独立的超时和重试配置，不影响上一层的正常恢复。


11. Streaming 为什么能改善用户体验？它能减少总耗时和 Token 成本吗？

答：
先说结论：streaming改善的是“体感延迟”，不是“实际耗时”，不能减少token成本，这两个容易混淆，我分开讲。

**为什么改善用户体验？**
核心原因是吧“首token时延”从秒级降到了毫秒级。非流式调用时，模型自回归生成所有token后才一次性返回，用户盯着空白页面等5-10s。流式调用时，第一个token生成出来立刻推给前端，通常200-500ms用户就能看到内容开始出现，虽然全部内容显示完的时间跟非流式一模一样，但用户体感上“响应很快”，因为他立刻得到了反馈。

这种心理效应在UV研究中有明确的结论：人来对等待的感知不是总时长，而是“有没有反馈”。有内容在动，用户就觉得系统在工作。

**能减少总耗时吗？**
模型的token生成速度--也就是每秒生成的token数是由推理引擎的计算能力决定的，跟传输方式无关。不管是用streaming每生成一个送一个，还是非流式攒齐了一起送，最后1个token生成的时刻是相同的。总耗时还包括prefill阶段，就是模型出处理输入prompt的KV cache计算，这部分时间streaming也省不了。

**能减少token成本吗？**正常使用不能。
API按输入和输出的token总数计费，streaming只是改变了传输方式，不改变token生成数量。
但有个特殊场景：如果用户在中途取消，服务端停止生产后续token，这时候确实节省了剩余token成本，但这是用户主动选择的，不是streaming的能力。

**工程上使用straming有什么需要注意的？**
streaming引入了额外的复杂度。首先，错误处理变困难了--非流式一次能拿到完整响应，检查没问题再返回；流式可能在前100个token已经显示给用户后，第101个token才报服务端错误，这时候前端需要处理”半截回复“的状态。

其次，解析方式完全不同。非流式是一次JSON解析，流式要走SSE协议逐行解析delta，需要自己拼接完整内容，涉及状态管理。

最后，如果业务需要对输出做后处理校验--比如检查实体是否正确、是否包含敏感词，流式场景下等全部接收完毕再做，失去了”即时显示”的优势，前端需要做“显示+后台校验”两套逻辑。

实际中我的选型原则很简单：面向用户的产品必须用streaming，机器对机器的调用用非流式。前者关注体验，后者关注可靠性。比如内部数据管线的批量推理，不需要给谁看进度，非流式更简单可靠。


12. SSE、WebSocket、HTTP Chunked 在流式输出场景下怎么选？

答：
大模型流式输出场景，我的选择非常明确：SSE。这是业界的事实标准，OpenAI、Anthropic、国内达产的API全部用的SSE。

为什么？从三个维度对比。
第一，场景匹配度。大模型流式输出是纯粹的单向数据推送--客户端发一个prompt，服务端持续返回token。SSE为单向推送而设计，完美匹配。WebSocket提供的时双向全双工通信，在这个场景下是功能过剩--你不需要客户端随时给服务端发包。HTTP chunked是最底层的传输编码。处理的时无结构的字节流，不是消息帧，解析成本高。

第二，协议成本和工程复杂度。SSE的本质就是HTTP长连接架简单的文本格式--data：{}\n\n就是说一条消息，data:[DONE]结束。前端用浏览器原生的EventSource API，一行代码就搞定，而且自带断线自动重连。WebSocket要做协议升级握手、手动定帧格式、自己处理ping/pong保活、自己实现重连逻辑--代码量差一个数量级、

第三，基础设施兼容性。SSE跑在HTTP上，可以穿透绝大多数代理、负载均衡器和CDN，不需要额外配置。WebSocket在不少企业网络中会被防火墙拦截，部署是要额外打通，这在B端产品中是实实在在的成本。

**那什么时候考虑WebSocket？**
只有1个场景--客户端需要在推理过程中发送控制指令，比如用户点击“停止生成”、实时调整输出风格、或者多模态交互需要同时收发。但即使是要实现“停止生成”，在SSE链接上发FIN包也能做到abort，真正需要WebSocktet的场景很少。

HTTP chunked我不建议直接使用。现在所有后端框架都在HTTP上封装了SSE支持，不需要自己去操作chunked传输层，

**使用SSE有一个工程要点**：浏览器的原生EventSource API不支持自定义请求头，没法传Authorization做认证。在实际生产代码中，我通常用fetch API手动读取响应的readableStream，按SSE格式解析每行，这样既能带认证头，也能完整控制流式处理逻辑。或者如果是APP场景，用原生的URLSession或OKHttp，就没有这个限制。


13. 哪些大模型 API 错误可以重试？哪些错误不能重试？

答：
重试策略的核心原则是：服务端的暂时性故障可以重试，客户端错误和内容审查拦截绝不重试。
我按Http状态码分成三组说。

第一组，绝不重试--4xx客户端错误。
- 400 Bad Request，请求格式本身就是错误的，比如json格式不对，参数值非法，这些重试一万次也不对，这时候应该抓日志看请求体，修bug再发。
- 401或403，认证失败或权限不够。API key过期了、没开对应模型的权限--重试解决不了认证问题，应该去检查key和权限配置。
- 404，请求的资源不存在，比如model name写错了，同样是配置问题不是暂时性故障。
另外还有个特殊的400--finish_reason为content_filter或者直接返回内容审核拦截错误。这说明prompt或输出触发了安全审核规则，重试只会再次触发，应该修改内容。

第二组，可以重试--5xx服务端错误和429限流
500、502、503、504都是服务端问题。500是内部错误，502是网关错误，503是服务暂不可用，504是网关超时。这些都是暂时的，重试大概率成功。
429是大模型API最常见的问题，需要单独讲。大模型API的429通常有两个维度：RPM（请求每分钟）和TPM（每分钟token消耗）。被限流时，一定要读取响应里的retru-after头，它会告诉你要等多少秒。不要拿到429就按固定策略重试，不读retry-after只会继续被限流。

第三组，超时类的要分情况处理。
Read Timeout（读取超时）可能是大模型推理太慢、max_tokens设太大，这时候重试可能有效，但要注意别超过整体超时预算。
Connect timeout（连接超时）通常是网络或DNS问题，重试前应该检查下是不是网络层面的故障。

重试策略怎么写？
我一般用指数退避 + 随机抖动：第一次重试等1s，第2次等2s，第三次4s，每次乘上一个0.9到1.1的随机系数，最多重试3次，超过就告警并将错误抛给上层降级逻辑。

最关键的一点--幂等。网络超时有一个经典陷阱：你的请求可能已经成功到达服务端并执行完了，只是HTTP响应在路上丢了。如果重试不带幂等键，同一段对话被处理两次、扣两次费。所以生产环境必须带“x-idempotency-key”头，防止重复消费。
附带说一下降级策略：3次重试都失败后，不是返回用户一个冷冰冰的error，而是走降级路径：切换到备选模型、或者用轻量模型做简要回复，或者返回“系统繁忙，请稍后重试”的友好提示，最好有个重试按钮，用户可以点击重试。

14. 大模型限流为什么不能只按 QPS 做？

答：
因为大模型API的成本和负载跟请求数不是线性关系，而是跟token数强相关。
举一个极端例子：一个请求输入“你好”只消耗10个token，另一个请求粘贴了一整篇论文消耗80k token。按QPS计数，两者都是1次请求，但后者的计算资源消耗是前者的几千被。如果只用QPS限流，会出现两个问题：大请求被放过去把GPU打满，小请求反而被错杀--这就是限流策略完全失准。

大模型API的消耗是多维度的，至少两个维度：
第一个，TPM--每分钟token消耗数，这是真正反应GPU负载的指标。所有大模型缠上的核心限流策略都是TPM优先，因为token数直接对应FLOPs计算量和现存占用。

第二个，RPM--每分钟请求数，防止连接层面把API网关打垮。一个5000token的请求和一个5token的请求在连接建立、鉴权、kv cache的初始化上的开销是差不多的。如果只限TPM不限RPM，攻击者可以用海量1token的短请求耗尽服务端的连接池和调度资源，

再深一层，单请求也有上限。我不希望某个用户一次发个128k的请求，把整个TPM预算占满。所以客户端还要设档次请求的token上限，比如单请求input token不超过32K。

工程实践上，我的限流方案是三层嵌套：

第一层，每分钟总token预算，用滑动窗口计数器，分了输入token和输出token，因为prefill和decode的资源瓶颈不同----prefill吃算力，decode吃显存带宽。

第二层，每分钟请求数上限（RPM），防止连接洪水和调度资源耗尽。

第三层，单次请求token上限，防止单个请求吃掉大部分配额。

客户端实现上，我会做预检和动态调节。每次请求前先用tiktoken算清这次请求需要的token数，判断是否超过剩余预算，超过就先排队等待或直接拒绝。同时持续读取API响应头里的x-ratelimit-remainning-tokens和x-ratelimit-remaining-requests，动态调整请求频率；收到429后读取retry-after头，按指示时间等待后重试。


15. 模型网关通常要承担哪些能力？

答：
模型网关是业务系统和各自大模型之间的中间层。它的核心价值是把限流、重试、安全、成本管控这些横切关注点从业务代码中剥离出来，让业务方专注于prompt和业务逻辑。

我按照层次来讲：
第一层，路由与编排。这是最基本的功能。根据请求特征做智能路由--简单问题路由到轻量模型节省成本，复杂推理路由到强模型保证质量。同时支持多模型的AB Test和灰度发布，在网关层做流量切分，业务代码不用改。还要有降级链路：主模型不可用是自动切换到备选模型或返回兜底回复。

第二层，限流与配额。不能只按QPS，要按TPM和RPM双维度限流，同时做多租户配额管理，比如租户A每天100万Token额度，用超了就拒绝或排队。还要在接近配额上限时提前预警。

第三层，安全防护。输入侧要检测prompt注入攻击--比如用户说“忽略之前的系统指令”、越狱攻击。输出侧要做敏感词过滤和隐私信息脱敏。这些安全能力统一在网关做，比每个业务方自己去实现更可靠，也更容易保持策略一致。

第四层，可靠性与容错。包括指数退避重试、幂等保证、超时控制和熔断机制。连接失败超过阈值触发熔断，进入半开探测状态，回复后自动切回。还有缓存层，相同或相似的prompt可以直接返回缓存结果，节省Token消耗。

第五层，内容质量管控。对输出做各式校验、finish_reason检查、幻觉初筛--比如用NER抽实体后检查是否在RAG检索材料中出现过，这些校验不要求完美，但可以拦截明显的质量问题。

第六层，可观测性。全量记录每次调用的prompt、response、token消耗、延迟、错误。画出DashBoard、按模型、按租户、按时间段分维度展示。设置告警规则，比如错误率超5%或截断率突然升高就触发通知。

我的实践经验是：不要一开始就做全六层。第一期先做路由+限流+重试+日志，这是MVP，解决“能用”的问题；第二期加安全和内容校验，解决“安全问题”；第三期加缓存和智能路由，解决省钱问题。一层一层加，每层都有独立的评测指标。


16. AI 应用的调用日志里至少要记录哪些字段？

答：
AI应用日志设计目标和传统应用不一样--除了排查故障，还要回答“花了多少钱”和“为什么回答不完整”。我按排查链路吧字段分成5组。

第一组，请求标识。三个字段：request_id贯穿全链路。session_id关联多轮对话，timestap精确到毫秒。这是后续所有分析的基础。

第二组，请求内容。三个字段：model记录使用的模型名称；input_prompt全量存储实际发给模型的完整prompt，包括系统提示词、历史消息和RAG证据；input_tokens记录prompt的token消耗，以及API返回的usage.prompt_tokens为准，用于成本核算。

第三组，响应内容。三个字段：output_content存储模型原始输出的全量文本，不截断；output-tokens记录输出token消耗finish-reason记录结束原因--这是最容易忽略但最有价值的字段。“stop”正常结束，“length”说明输出被max_tokens截断了，“content_filter”触发了安全审查。线上最常见的用户投诉是“回答不完整”，不看finish_reason你永远分不清是模型不会答还是被截断了。

第四组，性能与成本。三个字段：TTFT首token时延E2E latency端到端延迟、cost本次调用的实际费用。cost必须在日志写入时实时计算并固化，不能时候离线算---因为API定价可能调整，事后算的数跟实际扣费对不上，影响财务对账。

第五组，异常与上下文。三个字段：error_type按类型记录错误----超时、限流、服务端错误、内容审查拦截；retry count记录实际重试次数；userid关联到具体用户，用于问题归因和成本分摊。

存储策略上，我分两个通道：全量日志保存7天用于实时故障排查，采样日志保留90天用于成本分析和模型效果回归。文本字段建议存对象存储，数据库只保留元数据和引用路径----prompt和output可能动辄几十KB，存关系数据库成本高且慢查询。


====结构化输出与工具调用====


17. 为什么只写“请返回 JSON”不可靠？

答：
因为”请返回JSON格式“是一句自然语言提示词，它对模型来说只是上下文里的一句建议，不是硬约束。模型本质上是一个token生成器，它逐token最大化概率，不知道什么是”合法的json语法“。

具体来说有5种常见翻车情况：

第一，模型可能先输出一句”好的，下面是json答案“，这不是模型不听话，只不过训练数据里，这种”先回应再输出“的模式太常见了。
第二，模型经常把JSON用markdown包裹起来，前后再加三个反引号。因为它训练时见过的json大多放在代码块里的。
第三，自回归解码没法回头检查语法。比如输出尾部多余逗号，未闭合引号，多个json块并列输出。
第四，Temperature不为0的时候，采样随机性可能选错token，一旦开通选错，后面全错。

工程上的解决方法，我分四层：
第一层，Prompt加固，零成本。不是只写一句”请返回JSON“，而是给出明确的JSON Schema示例，用few-shot展示期望格式，并且加一句赢指令：”只输出JSON，不要加任何解释、前缀或markdown标记“。这层能解决60%-70%的问题。

第二层，后处理兜底，必须做。拿到模型输出后，先用正则提取JSON块，然后json.loads解析，解析失败就触发重试。重试是在Prompt里告诉模型”你上次输出的不是合法的JSON，请严格按照格式重新输出。“这层能把可靠性提到80%。

第三层，API层面的结构化能力，这是生产环境的主力方案。OPENAI的JSON Mode、Function Calling，或者Anthropic的Tool Use，这些本质上是在推理阶段对token采样做了限制--当模型开始输出JSON时，只在合法的JSON token里采样。Function Calling则更进一步，你用JSON Schema定义参数类型和必填字段，模型不仅输出合法JSON，还会做参数层校验。这层的可靠性能达到95-99%。

实际生产中的最佳实践：Function Calling做主路径，后处理修复做兜底，Schema校验做最后方向。即使API返回了合法的JSON，仍要要做校验字段完整性、类型正确性和业务合理性。自然语言不是工程契约，硬校验才是。


18. JSON Mode 和 Structured Outputs（JSON schema） 有什么区别？

答：
JSON Object 和 Structured outputs是OpenAI在两代API中，提供的结构化能力，本质区别在于：JSON Mode只保证语法合法，Structured Outputs保证语法和Schema都严格符合。

先说JSON Mode。它的做法是：设置response_format: {"type": "json_object"}，然后再Prompt里用自然语言描述期望的JSON格式。API登场会强制模型输出以{开头，保证最终输出是一段合法的JSON字符串。但他不会检查输出结果是否按照Prompt的的描述来的

Structured outputs是2024年推出第二代方案。它的做法完全不同：我们直接再请求里传一个完整的JSON schema，定义字段名、类型、必填标识、枚举值和描述。API在推理阶段使用约束解码技术--每生成一个token，都过滤掉哪些不符合schema规范的token。所以它不仅能保证json语法正确，还能保证结构完全匹配。

还有一个关键差异是拒绝机制。JSON mode不会拒绝--你要求它输出JSON，他就一定输出json，哪怕内容不合理。Structured outputs如果判断你的schema在当前上下文无法满足，模型会返回一个refusal而不是硬编一个。

另外，我们之前生产中使用的function calling，现在大部分场景可以平替为Struc outputs。Function calling本质是把工具调用伪装成结构化输出--输出的是一个函数名加个json参数。如果我只是想要结构化数据而不是真的调用函数，用Structured outputs更直接，输出更干净，少了一层解析。


19. Function Calling 的完整链路是什么？

答：
Function calling是一个”模型决策，代码执行，结果回传“的循环，不是模型自己去调函数。我按一个完整执行周期来讲：

第一步，定义函数并发送请求。在API请求里带上tools数组，每个工具包含函数名、描述和JSON schema格式的参数定义。 比如一个天气查询工具，定义函数名”getWeather“，参数city是必填的string。模型拿到这些定义后，会判断用户的问题需要调用某个函数。

第二步，模型返回调用指令。如果模型判断需要调用函数，响应里的finish_reason是”tool_calls“而不是”stop“，message里包含tool_calls数组。每个tool_call有三个字段：id是这次调用的唯一标识，Function name是指定的函数名，Function arguments是JSON格式的参数字符串。注意这里模型只生成参数，不执行任何代码。

第三步，解析并执行函数。代码解析tool calls，按函数名路由到对应的视线，把arguements做JSON解析后传入。这里要做参数校验和异常捕获。函数执行完以后拿到一个结果，这个结果需要序列化成字符串。

第四步，结果回传并追加对话。把上一步工具调用的结果，以role=tool的消息类型追加到message列表里。这一步有两个关键约束：
1）tool_call_id必须和第二步返回的id精确匹配，否则模型无法关联。
1）必须保留历史tool call消息，对话历史不能断。

第五步，继续循环或结束。把更新后的message再次发给模型。模型拿到函数结果后，要么直接生成最终回复给到用户，此时finish_reason是”stop“；要么继续调用其他函数，继续循环。

工程上几个关键点：

首先，循环必须设置上限，一般设置5到10次。不设上限可能出现模型反复调用函数不满足的死循环，一次对话把API预算烧光。

其次并行调用要处理好。一个响应可能包含多个tool_calls，说明模型想要同时调用多个函数。这是性能优化的好机会，总延迟等于最慢的那个。

再次，函数失败不要把错误信息抛给用户。把错误信息作物tool result正常回传给模型，让模型决定如何向用户解释。

最后，Function calling和Structured outputs的选型。如果我只是要结构化的数据输出，不需要真的调用外部函数，现在我会用Structured outputs代替Function calling--前者不需要伪装工具调用，输出更干净。Function calling只在我确实需要模型触发外部系统操作时才用，


20. Function Calling 和 MCP 有什么区别？

答：它们不在同一层级，是协作而不是替代关系。

Function calling是调用协议层，它定义了模型在一次API调用中如何表达”我要调用函数A，参数是什么“。核心产物是tool calls这个结构--包含函数名和参数。Function calling解决的问题是格式层面的：让模型的输出不再是一段不确定的自然语言，而是结构化的调用指令。

MCP是工具发现与连接层。全称Model Context Protocol，是Anthropic在2024年底发布的一个开放协议。它的核心价值是标准化了”模型如何发现外部世界有哪些工具可用“。在传统Function caliing方案中，每次请求都需要拼接tools数组。MCP的做法是，启动一个mcp server，他对外暴露三种能力--Tools（可执行的函数）、Resources（可读取的数据源）、Prompts（预定义的提示词模板）。客户端通过JSON-RPC协议链接server，自动获取工具列表，不需要手动复制粘贴。

在实际架构中，它们的分工是：

第一层，MCP负责工具发现。你的应用启动时连接各个MCP Server，拉取它们暴露的Tools列表，转成Function calling需要的tools数组格式。

第二层，Function Calling负责调用决策。把tools列表和用户问题一起发给模型，模型输出tool_calls决定调用哪个、传什么参数。

第三层，应用代码负责执行和回传，解析tool-calls，路由到对应的函数实现，把结果以tool message形式传回模型。

MCP的主要优势有三个：

第一，解耦和复用。以前接入一个新工具要手写代码定义函数签名和处理逻辑，代码散落到各处。现在只需要对接一个MCP server，其他人也能复用，不用重复造轮子。

第二，跨模型兼容。MCP是开放协议，不绑定任何模型厂商。同一个MCP server，既可以被Claude用，也可以被GPT用，甚至本地开源模型也可以用。

第三，动态发现。工具列表是Server端实时返回的，server更新工具后客户端自动感知，不需要修改代码重新部署。

现状方面，MCP还在快速迭代器，协议版本、安全机制、权限控制还在建设。生产环境中我现在的策略是：内部工具链先试用MCP接入，面向用户的核心链路继续用成熟的Function calling方案。两者并行，等MCP生态文档后逐步迁移。


21. MCP Tool 和普通 HTTP API 有什么关系？

答：
MCP tool不是替代HTTP API的，而是HTTP API的上层包装。
从功能上讲，MCP tool和HTTP API的关系是三层嵌套：

第一层：描述层。普通HTTP文档是写给人看的，人读懂了再写代码。MCP tool要求为模型提供接口描述、参数描述、输入输出schema，让模型能像人读文档一样理解这个工具的作用。这是面向AI的语义层面。

第二层：连接层。普通HTTP API通常各自独立部署和鉴权。MCP tool部署在MCP server内，统一管理连接和认证，所有tool共享一个安全上下文，不用每个接口单独维护凭证。

第三层：调用和传输层。MCP Tool底层执行时，完全可以就是普通HTTP API的调用，

用代码看更直观：一个MCP Tool的handler函数里，通常就是三步
1）解析模型传来的参数
2）调用对应的HTTP API
3）返回结果给模型
整个过程MCP只是在HTTP API外面加了一层标准化的壳。

MCP tool不能替代HTTP API，但能统一管理HTTP API。以前每接一个新服务，既要看文档写代码、又要配置认证、还要处理错误格式。MCP的做法是：一个Server启动时，生命自己的工具列表，Client自动获取、自动转换为Function calling的tools格式。10个Http API配一次，而不是10次。


22. Agent Skill 和 Function Calling是一回事吗？

答：不是一个问题，解决的问题不在一个层面。
Function calling解决的是”调用格式“问题--模型如何输出结构化的函数调用指令，告诉系统调哪个函数，传什么参数。它是一种API协议层面的约定。

Agent Skill解决的是只是注入的问题--当用户的需求匹配到某个专业领域时，系统自动把一段预定义的prompt片段注入到上下文中，告诉模型”面对这类问题，该以什么角色、按什么流程来思考和工作”

核心差异两点：
第一，skill本身不一定携带工具实现。一个“代码审查”skill的会告诉你应用git_diff获取变更，但它不一定实现这些工具。工具调用仍然走Function calling，由主Agent执行。

第二，Skill是动态匹配嵌入的。不是每轮对话都生效，而是当主Agent识别到用户意图匹配某个skill时，才把对应的prompt注入系统上下文。

两者的关系是配合关系：skill负责告诉模型“现在你是什么角色，该怎么做”；Function calling负责让模型吧“我要调工具”这句话用正确的格式说出来；主Agent负责读懂这个格式、执行函数、把结果传回给模型。

什么时候用哪个：如果只是简单的工具调用，使用Function calling就够了，不需要使用skill。如果是一个需要领域知识、多步骤和固定流程的任务，比如代码审查、竞品分析，就该封装成skill。


23. 结构化输出失败后怎么处理？

答：结构化输出失败后，我不会只做简单重试，而是设计一条预防、解析、校验、重试、降级的五层管道来处理。

第一层，预防。生产环境优先用API原生约束，比如OpenAI的response_format：{type:"json_object"}或者json schema模式，让模型在token采样阶段就受限。这样比prompt里说「请返回JSON」可靠的多。同时prompt里给出完整的JSONSchema示例，设定max_tokens足够大，避免输出被截断。

第二层。容错解析。如果第一层没都住，在代码层做鲁棒提取：用正则从响应中提取JSON块（处理模型常犯的的两种错误：1、JSON前后带上了```markdown标记；2、回答前加上了解释性对话）。对轻微语法错误使用json_repair这类库自动修复。

第三层，Schema校验。解析出对象后用Pydantic或JSON Schema做校验，检测字段缺失、类型错误、多余字段。如果校验失败，构建一条具体的错误描述。

第四层，带反馈重试。把校验失败的具体错误信息注入到下一次调用的prompt里，告诉模型上一轮哪错了。需要设置重试最大次数，配合指数退避+jitter随机波动，防止无限循环。

第五层，业务降级。超过最大重试后不再死磕。根据场景选择策略：
1）关键业务回默认安全值并记录告警；
2）非关键业务降级处理或打日志跳过。

这五层的核心逻辑是：能预防则预防，能修复则修复，修不了就重试，重试不行就降级。


24. 工具调用为什么必须做安全治理？

答：
大模型输出是不可预测的概率结果，但工具执行时确定性的真实操作。从不可预测到真实执行之间，如果不加安全治理，有业务风险。

具体来说有三大风险场景：

第一，prompt注入导致越权调用。外部用户可能通过精心构造的输入诱导模型调用不该调的函数，比如让客服机器人触发退款接口。这是工具层面特有的攻击面--纯文本场景下注入最多污染输出，但有工具调用后注入可以直接产生业务风险，

第二，模型参数不可控。模型可能产生幻觉。而且可能错误的进行多个工具的串连调用，导致意料之外的风险。

第三，调用时刻。Agent循环中如果没有调用计数或者预算控制，模型可能在tool-calling loop里反复调工具，吃光token预算。

我习惯的治理策略分四层：

- 工具白名单：不是所有函数都给模型暴露，对每个对话上下文做工具裁剪，危险操作用户不可见的工具绝不暴露。

- 参数校验层：所有模型返回的参数，在真正执行前必须经过schema校验+业务规则校验。

- 沙箱执行：敏感操作架限流、超时控制、幂等保护，必要时引入人工校验循环。

- 审计日志：每次工具调用记录完整的调用链，出了问题能追溯。

一句话总结：工具调用相当于给了LLM一把能操作真实系统的钥匙，安全治理就是在这把钥匙上装了指纹锁、限速器和监控摄像头。


=== 测评 ===


25. 为什么不能只靠公开 benchmark 评估 AI 应用质量？

答：公开benchmark只能做初筛，不能做最终的质量判断，原因优三个层面：

第一个层面，数据不匹配。公开benchmark的题目是静态、干净、单轮的。真实用户输入是脏的--打字错误错误、指代消解、跨轮上下文依赖、甚至故意对抗性输入。即使用MMLU刷到95分。上线后用户说「帮我把刚才那个改一下」，模型可能一脸懵，因为benchmark从来没考过指代消解。更致命的是数据污染，高分可能是靠背出来的。

第二个层面，维度缺失。benchmark只测准确率，但生产系统要看的维度多得多：首token时延、token成本、结构化输出成功率、工具调用准确率、拒答率和误答率。一个准确率95%但首token时延需要10s的模型，在注重用户体验的场景，可能比准确率90%的效果差得多。

第三个层面，不测管道。生产AI应用是一整条管道----用户输入、意图识别、rag检索、prompt组装、模型推理、结构化解析、国际秩序、结果渲染。benchmark只覆盖其中模型推理这一环。如果rag召回了无关文档，模型再强也答不对；如果结构化解析崩了，模型输出再漂亮也是白搭。

最佳做法是分层评估：
- 选型阶段用公开benchmark做初筛，快速过滤明显不行的模型。
- 研发阶段建领域黄金数据集--从用户真实日志里标注一二百条典型case，覆盖happy path、边界case和已知失败模式。用这套数据集做离线回归测试。
- 上线后做在线评估：A、B实验看业务指标，采集用户行为信号，结合LLM as a judge做自动化质量打分，

一句话：benchmark告诉你这个模型「有多大潜力」，你自己的评估体系告诉你这个应用「靠不靠谱」。两者不是替代关系，是互补关系。


26。 Golden Set 应该怎么构建？冷启动阶段没有生产日志怎么办？

答：构建黄金评测集，我会按照「建框架、找数据、定标准、持续迭代」四步走，核心思路是：先保证覆盖度，再保证精确度；冷启动用替代数据源，上线后用真实数据替换。

第一步，先画任务地图，再采集数据。不要上来就堆样本。先定义清楚这个应用到底需要处理哪些任务类型（意图识别、信息提取、问答、摘要。。。），每种任务下有哪些难度层级（简单直接、多轮依赖、边界歧义、对抗输入）。这种「任务x难度」矩阵就是黄金评测集的骨架，保证数据不是随手抓的一对，而是有结构，可量化的覆盖。

第二步，数据来源按优先级排序：真实日志>历史渠道数据>人工构造>合成数据。
冷启动没有生产日志，但不代表没有真实数据。
第一优先去捞历史非大模型渠道的数据。
第二优先是领域专家手工构造。让懂业务的人对照着「任务x难度」矩阵，每个各自填几个代表性样本，重点补齐历史数据覆盖不到的边界case和对抗样本。
第三优先级是合成数据。用大模型批量生成样本，但必须人工审核过滤，合成数据天然带着模型的分布偏差，只做补量，不做主力。

第三步，标注标准要统一，用一致性检验把关。每个样本的「标准答案」不能拍脑袋决定。先写清楚规则（什么算对，什么算错，部分对怎么算），尽量双人标注，算CK一致性系数，低于阈值就重新对齐标注标准。而不是各标各的。标准答案一旦模糊，整个评测分数就失去意义了。

第四步，把它当做活资产来迭代。冷启动阶段有个小规模的内侧池----内部员工测试+少量种子用户，快速积累第一波真实日志，立刻回填进黄金评测集。上线后更简单，把用户点踩的BadCase、客服反馈、A/B实验里的失败样本持续喂进来，让评测集跟着真实分布一起进化。

总结一句话：冷启动的解法不是「造不出真实数据就瞎造」，而是「先挖历史，再人工补，合成凑数、内测加速」，用最快速度把评测闭环跑起来，再用真实数据滚雪球。


27. LLM-as-Judge 有哪些主要偏差？怎么缓解？

答：偏差主要有5类：

第一是位置偏差：同样两份答案换个位置，评委结论就变，它天然偏好排前面的；
缓解方法：交互位置跑两次，结论一致才采纳，否则取平均或直接丢掉。

第二是冗长偏差：错误但啰嗦的答案往往比正确但简洁的得分高，因为模型把长度当成了质量；
缓解方法：一方面在prompt里明确要求忽略长度，另一方面更倾向于用成对比较，长度偏差在相对判断里影响更小；

第三是自我偏好偏差：评委容易给自己或同家族模型打高分；
缓解方法：换一个独立的大模型来做评委，并且不告诉答案来自哪个模块。

第四是校准偏差：绝对打分分数都挤在一个狭窄区间，区分度低；
缓解方法：用pairwise的胜率或者ELO分代替绝对分数，比单条打分更稳定；

第五是一致性差：因为采样随机性，同一问题两遍结果可能不一样。
缓解方法：固定temperature=0，加评分细则和理由、必要时多次采样取多数。

最后前调下工程兜底：LLM评委不能裸奔上线。我会抽10%样本和人工标注结果做一致性校验，算一致率或者Kappa系数，达标了才敢大规模用它替代人工，否则就用它做粗筛、人工做终审。这样节省成本，又不至于被大模型评委误导。


28. RAG 评测为什么必须分检索和生成两段？

答：核心就一句话：RAG是「检索+生成」两阶段串联，任何一环错，最终答案都错，但修法完全不同，所以必须拆开评测，精准定位瓶颈。

我先讲为什么不能只端到端评估。假设我只看到一个指标「正确率70%」，这个数字没法指导我优化。因为答案错可能是两个完全不同的原因：
1）检索失败：该召回的文档根本没有召回，巧妇难为无米之炊；
2）生成失败：相关文档内容已经召回，但是模型忽略了，或者编造了内容。
这两种情况修法完全相反--前者要换embedding、调chunk、加重排，后者要修改prompt、换模型或加约束。只评端到端，无法定位问题根因。

所以我的做法是分两段指标。

检索段：基于黄金评测集，评召回质量：最核心是看正确文档有没有进TopP；再加命中率、排序准确率，加Context Precison看召回的噪声多不多。

生成段：在给定上下文条件下评生成质量：最核心是忠实度，也就是答案有没有依赖「召回文档」或者出幻觉；再加相关性指标看看是否答非所问，最后用端到端准确率指标做总开关。

最后补一句工程落地：检索段指标用精确匹配或embedding相似度就能算，不一定非用LLM；生成段的忠实度才需要使用LLM as judge，去判断答案能否从检索到的文档推出。


29. Agent 评测为什么比普通问答和 RAG 更复杂？

答：核心一句话：普通问答和rag评的是「一个答案」，Agent评的是一串决策，评估对象从点变成了轨迹甚至系统，维度爆炸。

我分四点讲复杂度

第一，评估对象复杂。普通答案是单次API调用，RAG是检索+生成两阶段串联，但Agent是一个多步循环--思考、调工具、观察结果、再思考决策，中间有很长一条执行轨迹。最终结果对不代表过程对，他可能饶了弯路、用了错误工具但碰巧答对，因此不能只评估端到端答案。

第二，标准轨迹难以确定。Groud Truth很难定义。rag有golden文档，能做recall精确匹配。但Agent任务「预订ktv」多条路径都可以成功，没法用一条标准的轨迹做精确比对，只能退回到「最终任务是否完成」这种相对粗糙的判断。

第三，归因复杂且标注困难。RAG失败就就归因两段：检索or生成。Agent失败可能是规划错、工具选错、参数传错、工具返回没理解、退出条件没设对。。。这些中间步骤都有可能，但全部标注记录成本巨大，且上下文膨胀可能导致准确率下降。

第四。环境不确定性。Agent要真实调工具、调API，外部环境会变，两次运行结果可能不一样，评测不可复现；而且真实环境反复跑有成本、还有误操作风，不能随便试。

对应的工程解法我也分几层：

评测上分三层
组件级评「工具调用准不准」、轨迹级评「整条执行路径合不合理」、任务级评「端到端任务成功率」，而不思只看一个分。环境上用沙箱模拟、保证可复现、能重放、无副作用。归因上引入轨迹级judge，让LLM评每一步决策，定位是规划错还是工具错。最后打分要多目标，不只成功失败，还要看效率（步长、token消耗量）。

总结：Agent评测难得根子，是多步决策带来的-----对象从答案变成轨迹、最佳答案标准从唯一变成多路径、归因从两段变成N步，再叠加环境不确定性和副作用。所以必须分层评、沙箱跑、轨迹级归因、多目标打分。


30. 离线评测、Trace 回放、线上灰度分别解决什么问题？

答：我的理解是：这三个不是同一层面，而是评测体系的三级阶段，从便宜到真实、从无风险到有风险，分别堵住不同环节的漏洞。我逐个讲它解决了什么、以及它解决不了什么。

第一个，离线评测：解决「快速、便宜、可复现的试错」。我改prompt、换模型、调参的时候等改动，需要一个确定的、可重复的、低成本的方式判断改动是好是坏。它跑固定数据集，快速出分，能做回归防止退化、做选型对标、做快速迭代。但它的局限是数据集的质量问题。人工创建甚至合成的离线数据集，和线上真实分布有偏移，离线分高不代表用户体感好。

第二个，Trace回放，解决「离线数据和真实流量脱节」。手写数据集测不到真实用户的query分布、长尾和脏输入。所以我把线上真实请求的完整轨迹抓下来，在离线环境重放，用真实流量做回归。但它有个关键的点：外部依赖会变，搜索结果、API、时间戳都不一样了，所以必须mock掉外部依赖才能保证可复现。同时他只能覆盖「已经发生的问题」，覆盖不了新趋势。

第三个，线上灰度，解决「离线和回放都测不出来的真实世界问题，或者新功能上线无有效数据」。真实用户行为、真实环境依赖、真实副作用，以及转化率、留存这些业务指标，是任何离线手段都测不出来的。灰度就是小流量真实上线，加A/B对比，看的是业务结果而不是答案正确率，用来兜住「离线看这些好，线上翻车」的风险。代价是有真实风险、周期长，需要配套能力开发。

最后我把三者串起来讲工程闭环：先离线评测快速筛掉明显差的方案，再用trace回放对后选方案做真实分布回归，最后用线上灰度验证业务指标，全部通过才全量。


31. CI 里的 AI 评测如何平衡速度和覆盖度？

答：核心思路：平衡速度和覆盖度，考的不是二选一，而是「分层分级，按需触发，便宜指标先行」，把贵的评测放到它该在的位置。

先说分层：我把评测做成三层金字塔。
最底层是规则和断言---输出schema校验、格式校验、关键词匹配、长度限制，这些都是毫秒级，每个PR都跑。
中间层是黄金评测集---精选几十条关键case，用LLM as judge评，控制在分钟级，也每个PR跑；
最顶层是全量benchmark，几百上千条，放夜间或定时跑，不阻塞开发。
这样速度和覆盖都不丢。

第二是按改动范围触发。不要每次都全量跑，而是给评测用例打标签、做依赖分析，改了检索就只跑相关用例，改了prompt就只跑生成段。用「diff命中用例子集」避免无效开销。

第三是便宜指标先行，做漏斗。先用embdeding相似度、精确匹配、规则这些确定性的便宜指标做第一道筛选，把明显退化的改动直接拦下来，通过了再去跑贵的LLM as judge。这样可以节省成本

第四是并行化和缓存。LLM评测天然可并行，用batch+并发把串行的几小时压到几分钟--这一步再不动覆盖度的前提下提速，，再配合结果缓存，模型没变、代码没变的部分复用历史结果，只重跑受影响的用例。

总结下：速度靠「L1规则+并行+缓存」，覆盖靠「全量兜底」，中间用「diff触发+便宜指标漏斗」，把昂贵的LLM用在刀刃上。


32. 如果 LLM-as-Judge 和人工评测结果不一致，应该怎么处理？

答：核心思路是：先量化不一致、再归因、再分流处理、最后持续迭代闭环。

第一步：量化。先算整体的一致率和Kappa系数。如果整体都低，说明大概率是评测标准本身模糊，或者Judge出现系统性偏差。如果整体还行，只是局部case不一致，说明是某类特定的case触发的。

第二步，归因。不一致的case拉出来逐条分析，一般归到四类原因：
1）评测标准模糊：人工标注员之间自己都无法完全对齐，那问题在rubric而不是judge；
2）judge系统性偏差：位置偏差、冗长偏差、自我偏好偏差、校验偏差、一致性偏差；
3）judge能力不足：复杂推理或者专业题裁判不了；
4）人工标注结果本身不准。

第三步，分流处理，四类问题分别处理。
1）标准模糊：优先优化rubric，明确好答案的标准、需要加few-shot示例（评分类，需要给不同分数设定锚点）。这是最高优先级问题，标准模糊，永远无法对齐。
2）judge有系统性偏差：改prompt、加约束、位置交换消除position bias、或者换更强的独立judge。
3）judge能力不足：可以替换模型或者降级人工裁判。
4）人工标准结果不准：多人标注、仲裁机制。

第四步，闭环。我会定期抽样算LLM和人工的Kappa，设一个阈值持续监控。跌破阈值就自动触发上面的归因流程，同时把发现的BadCase沉淀进评测集，修订rubric。

总结一句话：不一致是信号，不是故障--他说明裁判标准、裁判模型、人工标注三者至少有一个有问题。正确做法是「先量化不一致、再归因、再分流处理、最后持续迭代优化形成闭环」。
