# 平台层知识：双端边界规约（dual-end-boundary）

> 层级：平台层 ｜ 用途：clarify（端归属判断）/ plan（架构划分）阶段注入
> 核心问题：一个功能应该进小程序、进 Web 后台、还是双端都做？共享逻辑放哪？

## 1. 端职责划分原则

| 端 | 面向角色 | 职责 |
|---|---|---|
| 微信小程序 | 顾客、一线服务者（如陪玩师） | 浏览、下单、接单、进度查看、消息通知等"高频、移动场景、轻量交互" |
| Web 管理后台 | 店长、管理员、运营 | 配置、审核、派单、结算、报表等"管理类、批量操作、复杂表格表单" |

**判断口诀**：
- 顾客/服务者随手做的事 → 小程序
- 管理者配置、审批、看全局的事 → Web 后台
- 同一业务对象两端都要看（如订单）→ 双端，但**操作权限按角色严格区分**，小程序端通常只读或仅操作自己的数据

## 2. 需求端归属标注（spec 阶段强制）

每条功能需求（Req）必须标注端归属：`【端归属：小程序】`/`【端归属：后台】`/`【端归属：双端】`。
双端需求必须分别写明两端各自的能力边界（谁能看什么、能操作什么）。

## 3. 共享层（shared/）规约 —— Taro 路线的核心收益

`shared/` 是 Web 后台（React）与小程序（Taro）共享的代码层，**只允许放与平台无关的纯逻辑**：

| 允许放入 | 禁止放入 |
|---|---|
| 常量与枚举（订单状态、角色类型、错误码文案映射） | 依赖 DOM / wx API 的代码 |
| 纯工具函数（金额计算、时间格式化、状态机流转） | React 组件（两端渲染层不同，组件各自实现） |
| 数据校验规则（表单校验规则定义） | 路由相关逻辑 |
| API 客户端基座与接口定义（路径、参数、响应类型） | 平台特定的存储（localStorage vs wx.storage 由各端适配） |

**规则**：
- 3.1 同一业务计算逻辑（如结算金额）只允许在 `shared/` 实现一次，双端引用，禁止各写一份。
- 3.2 `shared/` 中的代码必须可被两端构建工具直接消费（ESM、无平台依赖），并有单元测试。
- 3.3 平台差异采用"接口 + 各端适配"模式：`shared/` 定义能力接口，两端各自提供实现注入。

## 4. 后端与双端的关系

- 后端不为某一端定制接口；同一业务接口双端共用，差异通过权限控制体现
- 端特有的展示聚合（如小程序首页聚合多个数据）优先前端聚合，确需聚合接口时在契约中显式标注 `x-audience: miniprogram`

## 5. 冲突裁决

端归属有歧义时，按以下顺序裁决：
1. 角色场景（谁在什么场景用）→ 2. 交互复杂度（重表格表单去后台）→ 3. 合规约束（涉及资质/支付类目能力受限的去后台）。
裁决结果必须记录在 clarify 记录中。
