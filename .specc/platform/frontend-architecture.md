# 平台层知识：前端架构契约（frontend-architecture）

> 层级：平台层（web-admin + miniprogram 跨端通用） ｜ 用途：plan / tasks / implement 阶段注入
> 目标：约束每张前端代码形态统一，解决「多次 AI coding 后风格漂移、架构模糊、难维护难扩展」的痛点。
> 性质：**硬性约束**。条款用「必须 / 禁止」，AI 编码时必须遵守，评审时逐条打钩。
> 与其它文件的关系：本文件只讲「跨端统一的架构形态」；各端特有规范（权限/合规/页面模式）见
> `web-admin-standards.md`、`miniprogram-standards.md`；两端职责划分见 `dual-end-boundary.md`。

---

## 0. 一句话分区（先说清整体形态）

```
┌──────────────────────────────────────────────────┐
│  页面层(pages/)             // 只做组装 + 交互 + 三态    │
│    → 不碰请求、不写业务逻辑、不裸调 wx.*/fetch        │
├──────────────────────────────────────────────────┤
│  业务层(services/)          // 数据流转 + 编排           │
│    → 接 API、做加载/错误/缓存，页面可读的业务入口      │
├──────────────────────────────────────────────────┤
│  接口层(api/)               // 复用 shared/client 基座  │
│    → 只定义「调哪个接口、传什么、返回什么」           │
├──────────────────────────────────────────────────┤
│  跨端共享层(shared/)        // 与平台无关的纯逻辑        │
│    → 常量/工具/校验/API契约，双端唯一实现             │
├──────────────────────────────────────────────────┤
│  平台适配层(platform/)      // 每端各自一份           │
│    → wx.* / fetch 唯一出口，页面与 service 不直接碰    │
└──────────────────────────────────────────────────┘
```

**核心思想**：业务逻辑尽量下沉到 `shared/`；请求差异用「接口 + 各端适配」隔离；
**页面永远是最薄的一层**。这与后端「Controller 不写 SQL」同构。

---

## 1. 硬性分层纪律（F-01）

- **F-01-1 页面（pages/）只允许三件事**：读数据（调 service）、渲染 UI、绑定交互。禁止出现：接口 URL、`fetch`/`wx.request`、业务计算逻辑。
- **F-01-2 service（services/）是页面访问数据的唯一入口**：一个页面业务对应的 `load/刷新/提交` 逻辑收敛到 service，禁止页面自己用 `useEffect` 堆数据流转。
- **F-01-3 api（api/）复用 `shared/api/client.js` 基座**：接口调用只定义「路径、参数、返回契约」，禁止页面/组件裸写 `fetch`/`wx.request`（对应 web-admin 5.2、miniprogram 5.2）。
- **F-01-4 shared/ 只放与平台无关纯逻辑**：常量、纯工具、校验规则、API 契约。禁止放入任何依赖 DOM / `wx.*` / React 组件的代码（对应 dual-end 3 节）。
- **F-01-5 平台适配（platform/）是差异唯一出口**：`wx.*`、`fetch` 统一封装成一枚「request 适配器」函数。**禁止在页面、service、api 里直接调用 `fetch` 或 `wx.request`。**

---

## 2. 防漂移硬规则（F-02）—— 这是对抗「多次 AI 上下文不同」的关键

- **F-02-1 新增页面一律独立文件**：不允许把新页面塞进已有组件、不允许改写复用已有页面。页面文件名=页面语义（如 `QuotePage.jsx`），禁止出现 `Page2`/`tmp`/`newPage` 等占位命名。
- **F-02-2 禁止「拷贝页面」，只允许「抽公共」**：当发现第二个页面要复用某段 UI/逻辑，正确动作是抽成 `components/` 公共组件或 `shared/` 公共函数，**不是复制粘贴**。评审时发现连续 3 行以上重复 JSX / 逻辑，即属漂移，打回。
- **F-02-3 一套写法，只允许一种**：同一概念全项目只能有一种实现。例如「请求适配器」必须放 `platform/request.js`（web 与小程序各自一个），**禁止出现「有的端放 platform、有的端内嵌页面」的混用**——这是已发现的漂移点，必须按 F-01-5 修正。
- **F-02-4 同一概念单一实现**：同一工具函数（时间格式化、金额计算、错误文案映射）全项目只准在 `shared/` 存在一份，双端引用。禁止在页面里重新实现一遍。
- **F-02-5 命名统一**：目录、组件、函数命名遵循「语义化 + 统一后缀」。异步返回用 `xxx`（数据）与 `loading`/`error` 状态；错误处理出口用统一命名。**禁止同一需求里出现多种命名风格**。
- **F-02-6 状态单一来源**：同一份数据全项目只在一个地方有真身。禁止「同一数据在多个组件各自 useState 各存一份」——这与后端「同一数据多处缓存不一致」同构，是 bug 温床。
- **F-02-7 diff 自检**：implement 完成时，AI 应自查「本次是否引入了存量代码里没有的第二套写法」。有则必须合并到既有一种，否则评审打回。

## 3. 触发规则（F-03）—— 何时允许/必须抽象，防止「过早过度设计」

> 这些是"闸门"而非"审美"。不到阈值不强抽，防止过度设计；一到阈值必须抽，防止漂移。

- **F-03-1 必须抽 service**（任一命中即须抽）：
  - 页面数 > 3 且出现「同一接口被多处调用」
  - 某个页面里 `useEffect` + 数据流转逻辑超过 ~40 行
  - 同一套 loading/error/刷新逻辑在 ≥2 个页面重复
- **F-03-2 必须抽公共组件**：同一段 UI 在 ≥2 处重复出现（含结构相似的卡片/表格/弹窗）。
- **F-03-3 必须抽 shared 纯函数**：同一计算/校验/映射逻辑在 ≥2 处重复。
- **F-03-4 页面允许保持"薄"**：单页单接口、无跨页面复用时，允许暂时不建 service（此时页面直接调 api 可接受，但**不允许页面内出现 `fetch`/`wx.request`**，必须走 api 层）。

## 4. 三态与竞态样板（F-04）—— 数据请求的统一范式

- **F-04-1 每个有数据加载的页面/组件都必须有 `loading`（加载中）与 `error`（失败）两态**，且失败时需有可见反馈（文案/兜底），禁止「只有加载中、失败就白屏/静默」。
- **F-04-2 `useEffect` 内必须用 `cancelled` 标志（或等价清理）防竞态**：快速切换/重复触发时，防止旧请求后返回覆盖新数据。这是隐蔽且高发的 bug，评审必查。
- **F-04-3 异步空态**：列表类数据需考虑「空」态（如"暂无数据"），不能只写加载与成功两态。
- **F-04-4 用统一的 hook/样板**：当按 F-03-1 达到抽的条件时，抽取统一的数据加载 hook（如 `useXxxQuery`），供各页面用，禁止再手写第二套 useEffect 样板。

---

## 5. 可观测性对齐（F-05）

- 每个页面/组件（页面层）与 service（如有）都必须标注 `@capability`（对齐 `Req-N`）、`@capabilityPoint`（对齐 `T-XX`）、编排边 `@orchestrate`，编号**必须真实对齐 spec/tasks，禁止臆造**（规范见 `tech-stack.md` §6）。
- DAG 健康度作为架构审查的辅助信号：若新增页面在 DAG 上是「独立叶子」且对齐了一个 `Req-N`，视为健康；若牵出一堆既有节点、或无能力对齐，视为漂移，重点评审。

---

## 6. 评审检查单（F-06）—— 给人类 reviewer 的速查

按顺序打钩，任一不过即打回：

1. 新代码是否遵循了「页面 → service → api → shared」分层，接口调用是否都经由 `shared/` 基座？
2. `fetch` / `wx.request` 是否只出现在 `platform/` 适配器里？（页面/service/api 出现即违规）
3. 是否出现了第二套写法 / 第二处同概念实现？（是 → 漂移，打回）
4. 页面是否保持「薄」，业务逻辑是否下沉到 service/shared？
5. 是否具备 loading / error / 空 三态，`useEffect` 是否有竞态防护？
6. 是否缺了可观测性注解，编号是否真实？
7. 新增内容是否「独立成文件」，而非拷贝/改写既有代码？

---

## 7. 背景与依据（为什么定这些条）

- **漂移根因**：后端有 Spring 分层等框架强约束，前端缺少强制骨架，AI 每次只见局部上下文、无全局方案，按局部最优写，多次后自然风格分裂。
- **本契约的作用**：把后端「框架替你统一风格」换一种形式实现——**用每次注入的硬性条款约束 AI**，让即便上下文不同，产出的形态仍一致。
- **已发现的不一致（推动本契约）**：daily-quote 中请求适配器无法统一——小程序已抽 `platform/request.js`，web 却内嵌在 `QuotePage.jsx` 内（违反 F-02-3 / F-01-5）；页面级数据加载样板在双端重复（提示达触发器前兆）。
