## A. CLI 与初始化（#6）

### TC-A1：init 生成完整资产骨架
- 前置：空目录（或全新仓库）
- 步骤：`specc init`
- 预期：生成 `.specc/`（constitution.md、platform/ 5 文件、project/ 3 占位、templates/ 4 模板、prompts/ 6 指令、config.yaml）、`specs/`、`features/`、`lib/`、`specc.sh`
- 判据：目录与文件清单与《03 文档》6 节映射一致；重复执行 `specc init` 不覆盖已修改的宪法（提示确认）

### TC-A2：new 创建需求工作目录
- 前置：已 init
- 步骤：`specc new order-mgmt`
- 预期：`features/order-mgmt/` 创建，含初始 `state.json`（stage=pending，全部门禁未过）
- 判据：重复 `specc new order-mgmt` 报错且不覆盖

### TC-A3：status 展示进度
- 前置：已创建需求
- 步骤：`specc status order-mgmt`
- 预期：输出当前阶段、各门禁状态、（implement 阶段时）任务完成清单
- 判据：✋ 信息可读、与 state.json 一致

### TC-A4：未知命令与缺参提示
- 步骤：`specc`、`specc foo`、`specc new`（缺需求 ID）
- 判据：输出用法帮助，退出码非 0，不产生副作用

## B. 知识资产完整性（#1 #2 #3）

### TC-B1：宪法条款覆盖
- 步骤：审查 `.specc/constitution.md`
- 判据：✋ 至少包含六类条款——①技术栈锁定（Java17+SB3 / MyBatis / React18+Vite+AntD / Taro / PostgreSQL 全部出现且无矛盾）②安全红线 ③测试标准 ④流程纪律（无 spec 不写码、回链要求）⑤小程序合规 ⑥契约优先

### TC-B2：平台层 5 文件齐备且相互一致
- 步骤：审查 `platform/` 下 tech-stack / dual-end-boundary / miniprogram-standards / web-admin-standards / api-conventions
- 判据：✋ 五文件齐备；tech-stack 与宪法不冲突；dual-end-boundary 包含 `shared/` 双端共享目录约定；api-conventions 定义了统一响应体、错误码、认证方式、分页四要素

### TC-B3：业务层占位可填写
- 步骤：按 `project/` 三文件的填写指引，为一个假想业务填入最小内容
- 判据：✋ 指引清晰，填写后格式可被组装器读取（无解析错误）

### TC-B4：知识资产无密钥泄漏
- 步骤：全仓库检索 API Key 字样（`sk-` 前缀等）
- 判据：`.specc/`、`lib/`、模板中零密钥；`.gitignore` 覆盖密钥可能出现的文件

## C. 模板与提示词（#4 #5）

### TC-C1：spec 模板要素完整
- 判据：✋ `spec.template.md` 含——EARS 句式示例（SHALL/WHEN-THEN/IF-THEN）、需求编号规则（Req-N）、端归属标注（小程序/后台/双端）、"不做什么"章节、验收标准清单、量化约束章节；**不含**任何技术实现字段

### TC-C2：tasks 与 contract 模板要素完整
- 判据：✋ `tasks.template.md` 每任务含：目标/需求回链/依赖/测试先行标记/涉及文件/验证命令；`contract.template.md` 含统一响应体与错误码占位

### TC-C3：6 阶段指令自洽
- 判据：✋ 每个 `prompts/<stage>.md` 含：角色设定、输入清单、输出产物与路径、禁止事项、完成判据；六指令的输入输出首尾衔接（上一阶段产物=下一阶段输入），无断链

## D. 状态管理（#7）

### TC-D1：阶段推进正确写入 state
- 步骤：依次通过 specify、clarify 阶段
- 判据：`state.json` 中 stage 与 gates 字段按序更新；history 追加记录（含时间戳）

### TC-D2：人工审查意见留痕
- 步骤：在 plan 人工检查点输入 reject + 意见，修改后重新 approve
- 判据：history 含 reject 记录与意见摘要；审计链完整（✋ 可回答"谁在何时否决/通过了什么"）

### TC-D3：中断恢复
- 步骤：implement 执行到第 2 个任务时强制中断（Ctrl+C / 断网），重新运行
- 判据：已完成任务不重跑，从首个未完成任务继续；已生成文件不被重复追加破坏

## E. 上下文组装（#8）

### TC-E1：阶段→知识映射正确
- 步骤：分别执行 specify 与 plan，检查组装出的提示词（dry-run 或日志输出）
- 判据：specify 提示词**不含**技术栈/契约等平台层技术规约（保持规格纯净）；plan 提示词包含全部 5 个平台层文件；两者都含宪法与业务层

### TC-E2：上一阶段产物注入
- 判据：tasks 阶段提示词包含 plan.md 内容；implement 单任务提示词只含该任务相关 plan 片段 + 任务定义，不含整个 plan（✋ 抽查体积明显更小）

### TC-E3：超长告警
- 步骤：构造超大业务层文件（>预设阈值）后组装
- 判据：输出告警并提示裁剪，不静默截断

## F. 引擎适配与配置（#9 #12）

### TC-F1：配置可切换模型
- 步骤：修改 `config.yaml` 中 model 字段为另一模型 ID，执行一次阶段调用
- 判据：实际请求使用新模型；代码中无硬编码模型名

### TC-F2：密钥仅来自环境变量
- 步骤：检查 `lib/` 与配置读取逻辑
- 判据：密钥只从环境变量读取；未设置环境变量时报错明确（提示设置哪个变量），不崩溃

### TC-F3：Codex 冒烟（引擎可用时）
- 前置：环境变量与端点可用
- 步骤：`specc specify` 提交一个简单需求
- 判据：产物落盘 `spec.md` 且符合模板结构（含 Req 编号与验收标准）

### TC-F4：Manual 退化模式
- 前置：引擎不可用（或未配置密钥），配置切换为 manual
- 步骤：`specc specify`
- 判据：输出组装好的阶段提示词 + 产物路径清单，流程不崩溃；人工把产物放回约定路径后，`specc status` 正确识别并允许进入下一阶段

### TC-F5：任务失败重试与挂起
- 步骤：构造一个验证命令必然失败的任务，执行 implement
- 判据：自动重试 1 次后挂起，state.json 记录 failed 原因，转人工介入提示清晰

## G. 流程引擎与门禁（#10 #11）

### TC-G1：禁止跳阶段
- 前置：需求处于 specify 未过审
- 步骤：直接 `specc tasks`
- 判据：拒绝执行并提示缺失的前置阶段，不产生产物

### TC-G2：clarify 结构门禁
- 步骤：spec.md 中保留 `[NEEDS CLARIFICATION]` 标记时尝试进入 plan
- 判据：自动门禁失败，列出残留标记位置

### TC-G3：tasks 回链覆盖门禁
- 步骤：构造 tasks.md 遗漏某条 Req 的回链，尝试进入 implement
- 判据：门禁失败并报告未覆盖的 Req 编号

### TC-G4：plan 契约完整性门禁
- 步骤：契约缺少错误码定义时尝试通过 plan 门禁
- 判据：自动检查失败并指出缺失要素（响应体/错误码/认证/分页四要素逐项报告）

### TC-G5：人工检查点交互
- 步骤：在 specify / plan / verify 三个人工检查点分别执行 approve、reject
- 判据：approve 后推进到下一阶段；reject 后停留在本阶段并记录意见，产物可修改后重审（`redo` 可用）

### TC-G6：redo 重置
- 步骤：implement 后执行 `specc redo plan`
- 判据：plan 及之后阶段门禁状态重置；spec/clarify 产物与门禁保留不动
