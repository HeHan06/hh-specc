## 1. 设计目标与原则

### 1.1 目标

给定一段自然语言需求描述，经 specc 流程处理后，输出符合项目规约的「Web 管理系统（React+JS）+ 微信小程序 + Java 后端」代码，全过程可审计、可追溯。

### 1.2 设计原则（源自对标结论）

| 原则 | 说明 | 对标出处 |
|---|---|---|
| 规格即真相 | 代码是规格的编译产物，冲突时以规格为准 | 全部方案共识 |
| 决策显式化 | 每个技术决策落盘，禁止"只在聊天里说过" | BMAD |
| 门禁推进 | 阶段产物通过门禁（自动检查+人工审查）才进入下一阶段 | Spec Kit |
| 上下文分层 | 宪法/平台/业务三层知识按需注入，不全量塞入 | BMAD 分治思想 |
| 规格与引擎解耦 | 规格层是纯 Markdown 资产，引擎可替换 | 自有约束（Qwen/其他模型） |
| 给 AI 验证手段 | 每个任务自带验证命令，AI 自检优先于人兜底 | Anthropic |

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  ③ 编排层（specc CLI / specc.sh）                              │
│     阶段驱动 · 门禁执行 · 状态管理 · 断点续跑                     │
├──────────────────────────────────────────────────────────────┤
│  ② 规格层（本框架的核心资产，纯 Markdown）                        │
│     ┌────────────┐ ┌────────────┐ ┌────────────┐             │
│     │ 宪法        │ │ 平台层知识   │ │ 业务层知识   │             │
│     │ constitution│ │ platform/  │ │ project/   │             │
│     └────────────┘ └────────────┘ └────────────┘             │
│     + templates/（产物模板） + prompts/（阶段指令）               │
├──────────────────────────────────────────────────────────────┤
│  ① 引擎层（可替换）                                             │
│     主选：Codex Harness（codex exec，OpenAI 开源）              │
│           接阿里云百炼 DashScope 兼容端点 → Qwen 模型             │
│     退化：产物模式（只产出规格文件，人在任意 IDE Agent 手动执行）    │
└──────────────────────────────────────────────────────────────┘
```

**数据流**：编排层读取规格层 → 组装阶段上下文 → 调用引擎层 → 引擎产物落盘 → 门禁检查 → 人工确认 → 进入下一阶段。

## 3. 阶段流程定义（核心）

### 3.1 全流程总览

```
需求描述
   │
   ▼
① specify ──► spec.md ──┐
   │                    │ ✋ 人审：需求完整性
   ▼                    ▼
② clarify ──► clarify.md + 回填 spec.md
   │                    │ ✓ 自动：无 [NEEDS CLARIFICATION] 残留
   ▼                    ▼
③ plan ──► plan.md + contracts/ ──┐
   │                              │ ✋ 人审：技术方案
   ▼                              │ ✓ 自动：契约含认证/错误码/分页约定
④ tasks ──► tasks.md ──┐          │
   │                   │ ✓ 自动：每条需求 ≥1 任务覆盖（回链完整）
   ▼                   ▼
⑤ implement ──► 源代码+单测（逐任务）
   │                   │ ✓ 自动：每任务 lint + 单测通过
   ▼                   ▼
⑥ verify ──► verify-report.md
                       │ ✓ 自动：全量测试 + 契约一致性
                       │ ✋ 人审：验收标准逐条对照
                       ▼
                    归档（merge 进系统级规格库，OpenSpec 模式，v0.2 规划）
```

### 3.2 各阶段定义

#### ① specify（需求规格化）

| 项 | 内容 |
|---|---|
| 输入 | 需求描述（自然语言）+ 业务层知识（术语表、角色模型） |
| 产出 | `spec.md`：EARS 格式需求（编号 Req-N）+ 验收标准 + 角色权限标注 + **端归属标注**（小程序/后台/双端）+ "不做什么"清单 |
| 注入上下文 | 宪法 + 业务层知识 + spec 模板 + 阶段指令 |
| 门禁 | ✋ 人审需求完整性与边界 |
| 关键规则 | 规格阶段**禁止出现技术实现细节**（框架、表结构、API 路径一律不写）；必须显式写"不做什么"；量化指标用具体数字（<500ms），禁用形容词 |

#### ② clarify（澄清消歧）

| 项 | 内容 |
|---|---|
| 输入 | `spec.md` |
| 产出 | `clarify.md`（问题清单 + 回答）；答案回填 `spec.md` |
| 门禁 | ✓ 自动：`spec.md` 中无 `[NEEDS CLARIFICATION]` 标记 |
| 关键规则 | AI 主动提问（最多一轮 5 问），只问影响实现分支的问题；无歧义则直接通过 |

#### ③ plan（技术方案）

| 项 | 内容 |
|---|---|
| 输入 | `spec.md` + 平台层知识（双端边界规约、API 契约、小程序规范） |
| 产出 | `plan.md`（前端页面树 / 后端模块划分 / 数据模型 / 双端共享逻辑划分 / 关键技术决策与理由）+ `contracts/*.yaml`（API 契约） |
| 注入上下文 | 宪法 + 平台层知识 + plan/contract 模板 + 阶段指令 |
| 门禁 | ✋ 人审技术方案；✓ 自动：契约包含统一响应体、错误码、认证方式、分页约定 |
| 关键规则 | **数据模型与契约在此阶段锁定**，后续实现阶段不得私改；契约变更必须回炉重审 |

#### ④ tasks（任务拆解）

| 项 | 内容 |
|---|---|
| 输入 | `plan.md` + `contracts/` |
| 产出 | `tasks.md`：原子任务清单 |
| 门禁 | ✓ 自动：每条 `Req-N` 至少被一个任务回链覆盖；每任务标注验证命令 |
| 关键规则 | **原子化**：单任务目标单一、改动面小（对抗模型长程漂移的关键手段）；**顺序**：契约/数据结构 → 测试 → 实现（测试先行）；每任务含：目标、涉及文件、需求回链、验证命令 |

#### ⑤ implement（逐任务实现）

| 项 | 内容 |
|---|---|
| 输入 | 单条任务 + `plan.md` 相关片段 + 宪法 |
| 产出 | 源代码 + 单元测试 |
| 门禁 | ✓ 自动：该任务验证命令通过（lint + 测试）；高风险操作（删文件、改契约、改数据库结构）触发审批 |
| 关键规则 | **一个任务 = 一次有界引擎调用**，上下文只含该任务所需片段（JIT 加载）；任务失败最多自动重试 1 次，再失败则挂起等人介入 |

#### ⑥ verify（验证归档）

| 项 | 内容 |
|---|---|
| 输入 | 全部产物 + 生成的代码 |
| 产出 | `verify-report.md`：测试结果 + 契约一致性检查 + 验收标准逐条对照表 |
| 门禁 | ✓ 自动：端到端冒烟通过（真实启动后端+前端，从前端页面入口验证）+ 契约一致；✋ 人审验收标准逐条对照 |
| 归档 | （v0.2 规划，未实现）本需求规格合并进系统级规格库（`specs/` 目录），防规格漂移 |

### 3.3 门禁汇总

| 门禁类型 | 实现方式 | 示例 |
|---|---|---|
| ✓ 结构检查 | 脚本检查产物格式 | 无 `[NEEDS CLARIFICATION]`、回链完整 |
| ✓ 自动验证 | 跑命令 | lint、单测、契约一致性比对 |
| ✋ 人工检查点 | CLI 暂停，展示产物，等待 approve/reject/modify | spec 审查、plan 审查、验收终审 |

**双闸门控制**（合规场景要求）：
- author-time：规格生成后、代码生成前，人工审查规格中的安全相关决策
- build-time：implement 阶段每任务自动跑检查，不通过不进入下一任务

## 4. 产物规范

### 4.1 目录结构

```
specc/
├── .specc/                        # 框架资产（全局，跨需求复用）
│   ├── constitution.md            # 宪法
│   ├── platform/                  # 平台层知识（双端品类通用）
│   │   ├── tech-stack.md          #   技术栈契约（待决项定稿后填写）
│   │   ├── dual-end-boundary.md   #   双端边界规约
│   │   ├── miniprogram-standards.md  # 小程序平台合规
│   │   ├── web-admin-standards.md #   Web 后台规范（RBAC、表格/表单模式）
│   │   └── api-conventions.md     #   API 契约规范（响应体/错误码/认证/分页）
│   ├── project/                   # 业务层知识（每业务项目一份）
│   │   ├── business.md            #   业务背景 + 术语表 + 角色模型
│   │   ├── data-model.md          #   核心业务实体
│   │   └── flows.md               #   关键业务流程
│   ├── templates/                 # 四类产物模板
│   │   ├── spec.template.md
│   │   ├── plan.template.md
│   │   ├── tasks.template.md
│   │   └── contract.template.md
│   └── prompts/                   # 六阶段指令模板
│       ├── specify.md / clarify.md / plan.md
│       └── tasks.md / implement.md / verify.md
├── specs/                         # 系统级规格库（v0.2 规划，未实现）
├── features/
│   └── <需求ID>/                  # 每需求一目录
│       ├── state.json             # 阶段状态机（当前阶段、已过门禁）
│       ├── spec.md
│       ├── clarify.md
│       ├── plan.md
│       ├── tasks.md
│       ├── contracts/
│       └── verify-report.md
└── specc.sh                       # 编排入口
```

### 4.2 spec.md 格式要点（EARS 记法）

```markdown
# <需求ID> 规格

## 背景与目标
## 角色与权限        <!-- 哪个角色在哪个端能做什么 -->
## 功能需求
### Req-1: <标题>   【端归属：小程序/后台/双端】
THE 系统 SHALL <能力描述>。
- WHEN <事件> THEN <响应>
- IF <异常条件> THEN <降级行为>
### 验收标准
- [ ] AC-1.1: <可测试的断言，含具体数字>
## 不做什么          <!-- 一等公民，防发散 -->
## 量化约束          <!-- 性能/容量等，用数字 -->
```

### 4.3 tasks.md 格式要点

```markdown
### T-03: 实现订单创建接口
- 需求回链: Req-1, Req-2
- 依赖: T-01（数据表）, T-02（契约）
- 测试先行: 是（先写 OrderServiceTest）
- 涉及文件: src/.../OrderController.java ...
- 验证命令: mvn test -Dtest=OrderServiceTest
```

## 5. 三层上下文注入机制

每次引擎调用，编排层按公式组装提示词：

```
阶段上下文 = 宪法（永远注入，红线）
           + 平台层片段（按阶段相关性 JIT 选取）
           + 业务层片段（术语/角色/数据模型）
           + 上一阶段产物（或其相关片段）
           + 本阶段模板 + 阶段指令
```

| 阶段 | 注入的平台层片段 |
|---|---|
| specify | （不注入技术规约，保持规格纯净） |
| clarify | 双端边界规约（帮助判断端归属类问题） |
| plan | 全部平台层（技术栈/双端边界/契约规范/小程序规范/后台规范） |
| tasks | 契约规范 |
| implement | 宪法 + 与该任务文件类型相关的规范片段 |
| verify | 宪法 + 契约规范 |

**设计意图**：平台层知识是"双端品类"的通用规约，写一次跨项目复用；业务层知识每个项目初始化一份；两者分离使同一框架可服务多个业务项目。

## 6. 引擎接入设计

### 6.1 主选：Codex Harness + DashScope（Qwen）

```toml
# ~/.codex/config.toml（本地，不入仓库）
model_provider = "dashscope"
model = "<待确认的模型ID>"        # 用户所述 qwen3.8 max → 需确认实际 ID
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[model_providers.dashscope]
name = "DashScope"
base_url = "https://dashscope.aliyuncs.com/compatible-mode/v1"
wire_api = "chat"                  # Qwen 只支持 Chat Completions
env_key = "DASHSCOPE_API_KEY"      # Key 存环境变量，绝不入库
```

**调用模型**：编排层为每个阶段执行一次有界调用：

```
specc <stage>  →  组装上下文  →  codex exec --skip-git-repo-check "<组装后的提示词>"  →  产物落盘
```

**对中等能力模型的适配设计**（已在流程中体现）：
- 原子任务 → 每次调用目标小、上下文短
- EARS 强格式 → 格式约束弥补推理不足
- 每任务自带验证命令 → 模型可自检
- 阶段产物落盘 → 不依赖长会话记忆

### 6.2 退化：产物模式

无可用引擎时，`specc <stage>` 只输出"组装好的阶段提示词 + 应产出的产物清单"，由人在任意 IDE Agent 中手动执行。规格层完全不受引擎影响。

### 6.3 状态管理与断点续跑

- `features/<需求ID>/state.json` 记录：当前阶段、已通过门禁、失败任务列表
- 任意阶段可重跑（`specc specify --redo`）；人工修改产物后门禁重新校验
- implement 阶段按任务粒度记录进度，中断后从首个未完成任务继续

## 7. 流程裁剪（Profile）

| Profile | 适用 | 路径 | 版本 |
|---|---|---|---|
| **full**（默认） | 新功能、跨端需求 | 六阶段全走 | v0.1 实现 |
| light | 小改动、Bug 修复 | specify(简化) → tasks → implement → verify | v0.2 规划 |
| change | 存量系统的增量变更 | OpenSpec 式变更提案 → apply → archive | v0.2 规划 |

v0.1 只实现 full profile，跑通端到端后再补裁剪。

## 9. 实施路线（评审通过后执行）

1. **搭规格层骨架**：宪法 + 平台层 5 文件 + 业务层占位 + 4 模板 + 6 阶段指令
2. **搭编排层**：`specc.sh`（阶段驱动 + 门禁脚本 + state.json）
3. **接引擎**：Codex CLI 安装 + DashScope 配置 + 单阶段冒烟测试
4. **端到端演练**：选一个真实双端需求（如"订单管理"）走完全流程
5. **迭代**：根据演练暴露的问题修订宪法/模板/门禁
