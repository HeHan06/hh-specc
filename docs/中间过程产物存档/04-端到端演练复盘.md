> 复盘目的：不以「做完了」为终点，而以「哪些设计真的起作用了、哪些假设被现实击穿了、下一步怎么改」为终点。

## 一、一句话结论

**流程骨架是成立的，但「verify 只读 + 单测 + 构建」这个设计有一个致命盲区——它验证的是「代码看起来对」，而不是「系统真的能跑」。这次演练靠一次「本不该存在」的人工端到端补验，才把 3 个运行时缺陷和 1 个阻断项暴露出来。这暴露的不是某一行代码的问题，而是平台在「完成判据」与「验证手段」上的系统性缺口。**

## 三、设计「起作用了」的部分（值得保留与强化）

1. **逐任务循环 + 断点续跑**：implement 阶段的 13 个任务按依赖顺序逐一执行，每个任务一次有界引擎调用，失败重试 1 次后挂起。中途引擎切换模型、多次重跑，靠 `state.json` 的 `tasks.T-NN` 状态位实现了「已完成的跳过」，没有重头再来。**这是本次演练最扎实的一块**。

2. **需求↔任务回链门禁**：tasks 阶段自动校验 8 条需求全部被任务覆盖，从机制上杜绝了「需求写了但没人实现」。verify 阶段复核时回链完整性为 100%。

3. **契约四要素 + 跨端一致性**：`contracts/quote.yaml` 定义了接口路径/响应结构/错误码，最终 `QuoteController`、`QuoteView`、`shared/types/quote.js` 三处字段严格一致，`/api/quotes/today` 前后端映射无偏差。**契约先行让双端「各写各的」没有跑偏**。

4. **测试先行（TDD 顺序）**：T-04/06/08/10/12 先写失败测试、对应实现任务转绿。这个顺序保证了「有实现必有测试」，24 个用例覆盖了兜底/正常/无登录/格式非法等关键分支。

5. **三层上下文注入按工程 JIT 选择**：implement 阶段按任务所属工程注入对应平台规范（backend → api-conventions，web-admin → web-admin-standards 等），避免了「一把梭全量塞」导致的上下文污染。

## 四、被现实击穿的假设（本次复盘的真正价值）

### 4.1 致命盲区：verify 验证「代码对」而非「系统跑」

verify 阶段的指令是「只读 + 跑测试 + 跑构建 + 契约/宪法抽查」，**它默认「单测过 + 构建过 = 可运行」**。但这次 4 个缺陷全部藏在「单测过、构建过」的表象之下：

| 缺陷 | 为什么单测/构建没暴露 |
|---|---|
| 后端缺 `@SpringBootApplication` 启动类 | `mvn package` 的 repackage 失败本该在构建阶段暴露，但 verify 阶段对 backend 只跑了 `test` 和 `compile`，**没跑 `package`** |
| MyBatis `Invalid bound statement` | 单测用 Mockito mock 了 Mapper，**根本没走 MyBatis 真实装配**，XML 没加载也测不出 |
| 异常被静默吞错 | `GlobalExceptionHandler` 不打印堆栈，单测只断言了响应体，没断言日志 |
| Web 静态托管 500 | 单测只测组件渲染，没测「后端托管前端产物」这条真实链路 |

**核心教训：单测通过是「必要非充分条件」。** 一个平台如果只靠「单测 + 构建」做验收，交付的必然是一堆「看起来能跑」的代码。真正的验收必须包含一次**真实启动 + 真实请求的冒烟**（boot smoke test）。

### 4.2 平台的宪法，被平台自己生成的代码违反了

宪法 7.3 明确写着「前端统一拦截器处理错误码，禁止静默吞错」。但 `GlobalExceptionHandler.handleUnexpectedException` 恰恰静默吞掉了所有未预期异常的堆栈——**这正是导致我端到端排查时无法定位 500 根因的直接原因**。

这说明一个更深的问题：**宪法目前只是「注入上下文的提示词」，不是「可被门禁强制校验的规则」。** 模型生成代码时「知道」宪法，但「遵守」与否没有任何机器可执行的检查。宪法要有牙齿，必须把「禁止静默吞错」「无密钥硬编码」「MyBatis 参数化」这类**可静态判定**的条款，从「提示词」升级为「自动门禁」。

### 4.3 任务的「完成判据」写成了「可编译」，而非「可运行」

回顾 tasks.md 里 T-03（backend 工程骨架）的完成判据，是「测试可编译并运行」。结果 T-03 交付的骨架**漏了启动类**，直到 verify 阶段 `mvn package` 才报 `Unable to find main class`。

**教训：工程骨架类任务的完成判据，应该是「`mvn package` 产出可运行 JAR」，而不是「`compile` 通过」。** 完成判据的措辞差一个字，引擎交付的完整性就差一个「能不能启动」的边界。

### 4.4 环境依赖未纳入流程前置检查

`psql`/`postgres` 缺失，导致 T-01/T-02（数据库迁移）的验证命令实际未执行，但任务仍被标记为 `done`——因为引擎执行返回码是 0，而验证命令「没跑起来」和「跑起来失败了」对引擎来说是同一个「非零退出」吗？**不是**：`psql: command not found` 在 bash 里返回 127，但当时引擎的验证命令把它当作「环境缺失」而非「验证失败」，于是放行了。

**教训：流程需要「环境自检」环节，在 verify 前确认 psql/java/mvn/node 等运行时依赖可用；引擎执行的验证命令必须区分「验证失败」（非零退出且命令存在）和「验证无法执行」（命令不存在）。**

### 4.5 模型/引擎的稳定性是流程的隐形依赖

specify 阶段引擎执行失败 4 次重试、qwen 中途欠费被迫切换模型、deepseek 元数据缺失降级。这些都不是平台逻辑问题，但它们反复打断流程，且每次都需要人工介入「充值/换 key/手动续跑」。

**教训：引擎层的失败应该被更优雅地处理——specify 这类「单一有界调用」阶段需要明确的「失败重试上限 + 可恢复快照」，而不是靠人工盯着日志救火。**

| 平台设计缺陷 | 环境依赖无前置检查 | 流程缺环境自检环节 | 🟠 中 |

## 六、可落地的改进行动项（映射到梯队）

### P1（质量加固，优先级最高）

1. **新增「启动冒烟门禁」（boot smoke gate）**：verify 阶段在「单测 + 构建」之外，强制要求后端 `java -jar` 真实启动 + `curl` 核心接口断言 200 与关键字段。这是本次最痛的教训，必须立刻补。

2. **宪法可静态判定条款 → 自动门禁**：
   - 无密钥硬编码（已有 TC-B4，扩展到全流程）
   - 「禁止静默吞错」→ 静态检查 `catch` 块是否无日志/无上抛
   - MyBatis 无 `${}` 拼接（已有，扩展到 verify 阶段强制）
   - 缺 `@SpringBootApplication` → 扫描主类是否存在

3. **环境自检环节**：新增 `./specc.sh doctor`，在流程启动前检查 node/npm/java/mvn/psql/postgres 可用性，缺失项给出明确安装/启动指引。

4. **统一任务模板的「完成判据」措辞**：工程骨架类任务判据必须含「可运行」验证命令（如 `mvn package` 产出可运行 JAR），禁止用「可编译」代替。

### P2（体验增强）

5. **引擎失败的可恢复快照**：specify/clarify 等单一调用阶段增加「失败重试上限 + 快照恢复」，减少人工救火。

6. **单测防 mock 过度**：对「集成类」任务（如 Mapper XML 加载、静态托管）强制要求至少一个「真实装配」测试（`@SpringBootTest` / 不 mock Mapper），避免 mock 掩盖集成问题。

### P3（演进能力）

7. **遗留项自动登记**：verify 报告的「遗留项」自动写入进度看板，避免散落在 md 里被遗忘。

---

## 七、结语

这次演练最大的价值，不是「跑通了一个每日一句」，而是**用一次真实交付，戳穿了平台设计里「单测过 = 完成」的幻觉**。

specc 的定位是「从自然语言到合规代码」。但「合规」不能只停留在「代码符合规范」——真正的合规，是「代码 + 系统真的能跑起来，且运行时不违背宪法」。

下一版平台最该补的一课，就是：**把「能跑」写进验收的门禁里，把「宪法」从提示词升级成规则。**
